## 本表是什么、不是什么

**是**：一张「每项能力现在走到哪一步」的登记面——入口在哪、证据等级几级、证据链接指向哪份可复查的落盘件、**现在还不能做什么**、来源卡与核验 SHA、以及哪些文件一变动就要把它降级。

**不是**：不是功能清单，不是可用性承诺，也不是逐声明审计。本表登记的是**已落盘证据支持到哪一级**；「这条证据是否真支撑这句话」由 G1-6 逐声明审计链裁决，本表与承重门都不代判。

## E 级判定规则（本版口径）

沿计划书 §12.5（L583-590）与 schema `evidence_level` 枚举，本版落地为：

| E 级 | 本仓判定条件（本版实际使用的口径） |
|---|---|
| **E0** | 只有 goal / OpenSpec / PRD / 卡文，无代码入口 |
| **E1** | 有代码入口 + 单元 / 契约 / 变异测试；**不得写「可用」** |
| **E2** | 真实入口经隔离服务跑通且核心依赖无 mock——本仓具体指：7692 测试容器、`tmp_path` 真实 LanceDB、真跑被测脚本的 `subprocess`、真 `git` 仓、真变异改文件后跑门。可标 Experimental，**必须列限制** |
| **E3** | 参考环境验证：证据须指到 `docs/release-evidence/<rc>/journeys/J<nn>/manifest.json` 且该 manifest `provenance.mode = "live"`、`candidate.dirty = false`（R-EVD S13/S17） |
| **E4** | E3 + 用户按真实场景完成 UAT（§12.5 L587） |
| **E5** | 全部硬门 + 14 天 dogfood + 恢复演练 |

**本版 E3+ 行数硬性为 0。** `9c4e7e82` 的 `docs/release-evidence/` 下只有 `example-backfill-d5/journeys/J08/`，其 manifest `"rc": "example-backfill-d5"` / `"mode": "reconstructed"` / `"evidence_level": "E2"` ——**没有任何真 rc 目录**，没有一条 clean rc 可指。这条不是自律而是被门锁死的——但**锁的范围要说清楚**：门保证的是「解析器识别到的这张能力表里，没有 E3+ 行」。一份 markdown 文件能用很多方式把文字排得看起来像一张表，门不做版式取证；L13（表格结构契约）、L14（两个解析器必须看到同一批行）、L15（自述条目数 == 解析到的行数）三条合起来堵住了已知的六种「把行挪到检查范围之外」的写法（见 `evidence-g13/negctl-13-*`），但**不声称封闭**。`ledger_lint.py` 的 **L3** 对每个 E3+ 行强制要求：证据里引用到的**每一份** journey manifest 都存在且 `mode=live`、`dirty=false`，并至少有一份（全称判据 —— 只要求「有一份合格」的话，把一份 reconstructed 混进同一行就不会被拦下），写不出来就 `LINT: FAIL` rc=1。真 rc 由 P10-B（CARD-R-RC）产出后，本表才可能出现 E3 行。

计划书 L590 的兜底同样适用：**文件名含 `e2e`、模型代验、历史 UAT、fixture、CI 绿或「代码存在」都不自动提升等级。**

## `uat` 列的语义（⚠️ 易被读高）

`uat` 列只有两种取值：`no`，或 `yes(<验收单相对路径>)`。

`yes(...)` 的语义是**「该能力有一份验收单落盘、可复查」**，**不是**「用户已签字确认」。用户签字面在验收单内部，本表不代判、也不因此升 E 级。

**产品口径待裁（如实记，不悄悄二选一）**：`_bmad-output/implementation-artifacts/goal-cards/2026-08-28-主goal全量分goal总账-v2.md` L242 的旧口径是「用户 UAT 勾选 = E4」；而 §12.5 L587 定义 E4 = **E3 + 用户 UAT**，R-EVD 的 S13 又要求 E3+ 必须 `provenance.mode = live`。两者在「无 clean rc 时能否凭 UAT 直接给 E4」上冲突。本版取**保守默认**：UAT 只记 `uat` 列，**不升 E 级**。此项待用户裁定，已登记进 `_bmad-output/验收单/UAT-CARD-G1-3-2026-09-18.md` 的「台账待登记条目」第 3 条。

## 降级规则与 `状态` 列

`状态` 列只有两种取值：`current`（证据在 `核验 SHA` 上成立）、`implemented-unverified`（§12.5 L590 的降级态）。

`入口` 列的 `⇩` 之后是该行的**降级触发面**：这些文件中任何一个在 `核验 SHA` 之后发生实质变化（入口、依赖、schema、UI），该行就应改判 `implemented-unverified` 并在新 RC SHA 重跑。

⚠️ **本卡只登记触发面，不做自动降级**——没有任何 hook 或门会在触发面变动时自动改这一列。落地为机械门是后续卡的面，在此如实声明，避免把「登记了」读成「会自动执行」。

### 证据列里三类锚的语义（易误读，写明）

- **路径**：树内真实存在的文件（承重门 L4 用 `os.path.exists` 真核，不接受「链接格式合法」）。
- **`主干 <sha8>`**：该行入口在 `核验 SHA` 上的**最后改动 commit**，必是 `核验 SHA` 的祖先（L11 用 `git merge-base --is-ancestor` 真核）。这是判断「这条能力的代码真在主干上」的锚。L12 另核它**是否真改动过本行入口列里的文件** —— 祖先关系只说明这个 commit 在主干上，任何一个主干 commit 都能过 L11，不说明它和这条能力有关。
- **`核验 SHA` 列**：它是本表自己填的，而 L11 / L12 又都以它为基准 —— 所以 L9 额外要求它是**外部传入的 `--trunk`** 的祖先。不加这一层的话，把核验 SHA 换成某个未合入的车道 tip、证据 SHA 换成它的祖先，整条链会自洽地全部落在主干之外而三道门全绿（Codex r2 HIGH-2 实测）。
- **表结构本身**：L13 扫全文，要求与本表同列数的表格行不得出现在本表之外。没有这条，把能力行挪进文件后面的第二张表就等于让它们完全不受检查——解析器只读第一张表，行数门只看下界，于是 `rows=15` / `L3` 空转 / 整体 PASS，而被挪走的行里可以写着无证据的 E5（Codex r2 HIGH-1 实测）。
- **`merged-squash/<branch>`**：原车道分支的追溯 tag。⚠️ 它**不是**主干 commit——squash 合并会在主干产出一个新 SHA，原分支不进主干历史，所以**所有** `merged-squash/*` tag 都不是主干祖先。这是 squash 工作流的常态，**不能**用「tag 非祖先」推出「未合入」。判「是否合入」要看主干上有没有该卡的 squash commit（本卡实测：21 行中 CARD-G6-9c-R2 是唯一一条主干无 squash commit 的，已按此改写 CAP-TZ-SRC-07）。
