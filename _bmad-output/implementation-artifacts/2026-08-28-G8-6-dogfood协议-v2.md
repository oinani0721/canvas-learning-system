## 1. 窗口定义与完成判定

- **窗口** = 连续 **14 个日历日**（宿主本地日，基准见 §0-A7）。
- **启动条件**（AND）：①§7 全部锁版项完成（含语义裁定项）；②§0 启动档案建档齐全；③§8 残余中标「开窗前置」的脚本已落库并通过其验收门。
- **窗口完成判定（正向 AND，逐项机械可查；任一不成立 = 窗口未完成）**：
  1. **14 日全部「日通过」**：D1-D14 **每一天**都满足 §5.2 的日通过式（五项 AND），且每日均有当日或合规补核（§5.2）的 git commit 回执。仅有回执但当日 C1 判 FAIL 的日子**不算通过**——`generate:FAILED` 日即使写了事件登记也不能计入完成；
  2. **最低活动量达标**：§7 表 B 锁版值逐项达标（计数按 §6.2 口径）；
  3. **三零达标**：事件登记表中 `violation_status=确认` 的「数据丢失」「串 vault」「静默假成功」三类事件计数**各为 0**（§4——确认即入账，closure 不改写 violation_status）；
  4. **零悬置裁定**：窗口结束时事件表 `violation_status=待裁` 的行数**为 0**（每条事件必须落定为「确认」或「误报」并附依据）。缺此门则「永久挂待裁」可使判定 3/5 恒成立——不允许；
  5. **degraded 全可见可恢复**：窗口内每条 degraded 事件（§6.2 C9 枚举）都有登记行，且「可见面证据 + 恢复动作 + **恢复结果=成功并附复测证据**」三件齐全、`closure_status=closed`。仅填字段而恢复结果为「仍失败」或 open **不算达标**（计划书 L348「所有 degraded 都可见且可恢复」）；
  6. **变更全闭合**：变更登记表每行的 `verify_status` 必须落在 `VERIFIED_GREEN`（受影响裁判测试重跑绿）或 `ACCEPTED_UNVERIFIED`（用户书面接受该未验证面并记理由）；不得有 `OPEN`（尚未处置）或 `UNVERIFIABLE`（无 harness 且未经接受）残留（四态定义见 §3 第 4 条）。**`ACCEPTED_UNVERIFIED` 永不改写为 `VERIFIED_GREEN`**——接受是风险决定，不是验证事实；
  7. **无手工救火**：事件表「其他救火」类 `violation_status=确认` 计数为 0（G6 退出门 L326 由此机械导出；G6-12 消费本计数）。
- **全局接受集 `N`（四类并集，缺一即漏计）**：`N` = ①变更登记表中 `verify_status=ACCEPTED_UNVERIFIED` 的行数 + ②C2 判 `UNVERIFIABLE` 的（日期, vault）条目数（`vault_id` 缺失致身份未验） + ③若 §7 表 A「完成一张板」锁 (a) 分支：该锁版项本身计 1 项接受（机械面无 `board_completed` 事件，板名系人工背书） + ④若 §7 表 B 末行锁 (a)（C6/C7 计入硬门）：该锁版项本身计 1 项接受（ingest→board 与 skill 次数系人工登记）。**③④在锁版时即生成接受行**（写入台账区二，`verify_status=ACCEPTED_UNVERIFIED`，理由=对应审查发现），不待窗口结束补记。
- **窗口总状态二选一（不得混称）**：七门全过且 **`N = 0`** → **`VERIFIED_COMPLETE`**；七门全过但 **`N > 0`** → **`ACCEPTED_WITH_UNVERIFIED(N)`**，结案报告须列出全部 N 项清单与理由（§8 R-EVD 合同）。对外只能按实际状态名陈述，不得把后者简称为「窗口完成」。**注意**：只统计变更表行会让「空变更表 + C2 全 null + 两项都锁 (a)」这种全人工背书的窗口被标成 `VERIFIED_COMPLETE`——四类并集正是为堵此路。
- 判定 3/5/7 不达标 → 窗口判 **FAIL**（如实出结案报告，不得洗白）；剩余天数是否跑完、是否重开新窗口 = 用户裁定。一次长 E2E 或闲置 14 天不算窗口完成（L613 原义保留）。

## 3. fix-forward 规则（对抗审查裁定，v1 重置规则废止）

1. **不重置**：窗口内修 bug 或合并在途卡的缺陷修复**不重置 14 天**、不清零任何计数。计划书 L613 末句「任何影响产品行为的修改…从新 SHA 重新开始 14 天」**在本协议中显式废止**（总账 v2 §五 SUPERSEDED 台账在案）。新**能力**不在 fix-forward 覆盖面（§2）。
2. **变更登记（字段契约）**：窗口内每次落到**运行链**上的变更（代码、`.env`、wrapper/plist 重装、容器镜像/重启）须在台账变更登记表记一行，字段：日期、dev 主线 SHA（如适用）、**runtime SHA + dirty 指纹**（`git -C "$CODE_WT" rev-parse HEAD`；`status --porcelain | wc -l`；**diff 内容 hash**：`git -C "$CODE_WT" diff HEAD | shasum -a 256`——dirty 计数不绑定字节，仅计数会让"改了内容但文件数不变"的变更无法区分）、`.env` 摘要（§0-A6 同法，变更前后对比）、安装件 checksum（§0-A5 同法，如重装）、**容器加载证据**（后端容器以 bind mount 挂源码且 uvicorn 无 `--reload`（`docker-compose.yml:202`、`backend/Dockerfile:27`）——**改代码不重启 = 长驻进程仍跑旧代码**；本行须记 `docker inspect -f '{{.State.StartedAt}}' canvas-learning-system-backend` 的重启时间，或显式注明"该变更不涉及后端进程"）、部署时间、影响面一句话、受影响裁判测试、重跑结果。**dev 主线 commit 列表只是辅助线索，不等于运行链变更**——同步/重装/重启动作本身必须登记。
3. **当日 commit 辅助命令**（排他上界，不漏日终 59 秒）：`git -C <dev主线checkout> log --oneline --since="<D> 00:00" --until="<D+1日> 00:00"`。fast-forward 并入的旧日期 commit 以**合并动作日**登记。
4. **受影响裁判测试重跑（行状态四态）**：每个变更行记 `verify_status ∈ {VERIFIED_GREEN, OPEN, UNVERIFIABLE, ACCEPTED_UNVERIFIED}`——重跑绿 = `VERIFIED_GREEN`；尚未处置 = `OPEN`；无 harness 覆盖 = `UNVERIFIABLE`（不得默认视为无影响）；用户书面接受未验证面并记理由签字 = `ACCEPTED_UNVERIFIED`。**窗口完成要求每行落在 `VERIFIED_GREEN` 或 `ACCEPTED_UNVERIFIED`**（§1 判定 6），且后者永不改写为前者，其数量决定窗口总状态（`VERIFIED_COMPLETE` vs `ACCEPTED_WITH_UNVERIFIED(N)`）。受影响 J 旅程（若已有 harness）在新 SHA 重跑，不重开窗口。
5. **变更后必须重采 A4**：每个变更行的 runtime SHA / dirty 计数 / 已跟踪 diff hash / 未跟踪内容指纹四项都要按 §0-A4 的**修正后命令**完整重跑填入（不能只更新 SHA）。容器 `StartedAt` 只能称作**部署一致性证据**——它证明进程在该时间点之后启动，不证明长驻进程加载的就是这些 exact bytes；后者需运行时 attestation 或不可变镜像（不在本卡范围）。
6. **未登记变更 = 事件**：发现运行链行为变化但变更表无对应行 → 按 §4「静默假成功」类登记（登记缺失本身是违规现象）。
7. **重开窗口唯一裁定人 = 用户**：协议中不存在任何自动重置或自动延长路径。
8. **与 RC/E5 的分层（两种 soak 不混称）**：本窗口是**滚动 candidate soak**——跨 SHA 累计暴露，台账逐日记录当日 runtime SHA，结案报告按 SHA 分段列暴露天数，**不得宣称单一冻结 SHA 覆盖 14 天**。E5 发布门的**冻结 RC soak**（窗口与冻结 RC SHA 绑定 + E5 门报告归档 R-EVD）归 j-e2e-release 切片 RC 阶段执行卡，届时同样适用本协议 fix-forward 语义，是否重开由用户裁定。

| 字段 | 取值 | 说明 |
|---|---|---|
| 日期 / 类别 | 丢失 \| 串 vault \| 静默假成功 \| degraded \| 其他救火 | degraded 单列（不属三零，走可见可恢复门） |
| 现象 | 自由文本 | 用户视角一句话 |
| 机械证据 | 路径/粘贴 | log 行 / 文件 diff / shasum / 测试输出 |
| **violation_status** | 待裁 \| **确认** \| 误报 | 「确认」「误报」**一经裁定不可改写**；「待裁」是**临时态**：窗口结束时必须清零（§1 判定 4），不得用永久待裁规避三零 |
| **closure_status** | open \| closed（链接 §3 变更行） | 与 violation_status 独立；closed 只表示缺陷已修，不改写违规事实 |
| 恢复三件（degraded 类必填） | 可见面证据 + 恢复动作 + **恢复结果（成功/失败 + 复测证据）** | 计划书 L348「所有 degraded 都可见且可恢复」的入门字段；结果为失败 = 该门不达标 |

- **三零判定只看 violation_status**：「丢失」「串 vault」「静默假成功」任一类出现 `确认` → 该类计数非零 → 窗口三零 FAIL（§1 判定 3）。closure 不参与三零判定——修复能闭合缺陷，不能把已发生的违规改判为 0。**待裁不是避风港**：§1 判定 4 要求窗口结束时待裁清零，逐条落定为确认或误报（误报须附依据）。
- **「其他救火」**：任何需人工介入才恢复正常运行的操作（手工清缓存/改 state/改 frontmatter/重启服务/修投影）逐次登记；`确认` 计数非零 → §1 判定 7 FAIL。G6-12（消费卡）只读取本表计数，不另立表。
- **degraded 事件**：C9 枚举信号（§6.2）每次出现登记一行，补齐恢复三件且 `closure_status=closed`、恢复结果=成功（附复测证据，如次日 C1/C2 判定 PASS 的输出）；窗口结束时存在恢复失败或 open 的 degraded 行 → §1 判定 5 FAIL。

## 5. 每日核对与漏日语义

### 5.1 每日核对清单（每一天都执行，含无到期日；健康无变更日的核对+打卡 overhead ≤3 分钟——学习本身、异常处置、变更重跑不计入此上界）

1. **开总览页**：`http://127.0.0.1:${API_PORT}/api/v1/review/overview/page`（`API_PORT` 取 §0-A11 冻结值，勿硬编码——发行示例配置为 8011）——active vault（页面暂不标注 active，按 §0-A2 认准卡片名）状态为 **ok**；stale/no_projection/corrupt 任一 → 登记 degraded 事件并处置。
2. **健康自检行（原 G6-12 裁定并入）**：对 **覆盖集内每一个 key** 各跑一次 C1 与 C9（§6.2；每个 key 用 §0-A2 同一 `send_bark.vault_key()` 方法从目录名派生，启动档案一并冻结）。
   - **覆盖集 = A3 清单 ∪ {active vault}**：wrapper 只在 `DAILY_REVIEW_VAULTS` 缺省时才回退到 `ACTIVE_VAULT`（`daily-review-wrapper.sh:35-36`，`${REVIEW_VAULTS:-${ACTIVE_VAULT:-canvas-vault}}`），显式配置的清单**可能不含 active vault**——此时 active 库当日根本不会被推送。若 A3 清单不含 active key，本步须把它并入覆盖集，且当日 active C1 因「无 generate 行」判 FAIL（日通过式随之 FAIL，见 §5.2），并登记事件说明配置与协议预期不符（这是真实的配置问题，不是判据缺陷）。
   - active key 的 C1 结果进日通过式（§5.2）；**覆盖集内任一 key 的 C9 命中即登记 degraded 事件**——只查 active 会让 B 库的 `push:failed/fallback:fail` 完全漏记。**非 active key 的 C1 FAIL 同样必须登记事件**（类别按现象判：无 generate 行且该库在清单内 = degraded），不得因「不影响日通过式」而略过。
3. **preflight 日志检查（无论单库多库，每日必做；证据缺失 = fail-closed）**：wrapper 对非法/越界/不可读的库只写 BOOTLOG 后继续（`daily-review-wrapper.sh:58-60,71-74,91-95`），单库场景同样会静默；而 child push 的 key/owner-token preflight 只写 stderr（`daily-review-push.sh:38,75`），经 wrapper（只保留退出码，`:112`）落到 plist 指定的 err.log（`com.canvas.daily-review.plist:19`）。**两个日志源都要查，且 err.log 必须按游标读增量**（该文件**无时间戳前缀**，`grep 日期` 命中不了、`tail -N` 会漏掉被后续输出挤出窗口的当日行，历史错误又会天天重复命中）：
   - BOOTLOG（有时间戳）：`grep "$(date +%F)" "$HOME/Library/Logs/canvas-daily-review.boot.log" | grep PREFLIGHT-FAIL`
   - err.log（游标法，**必须先冻结终点再读，否则会永久跳过字节**）：D1 前在启动档案冻结其 **inode + byte offset**（`stat -f '%i %z' <file>`）。每日按下列顺序执行——
     ```sh
     F="$HOME/Library/Logs/canvas-daily-review.err.log"
     E=$(stat -f '%z' "$F")                      # ① 先冻结本次读取终点 E
     dd if="$F" bs=1 skip="$OFFSET" count=$((E-OFFSET)) 2>/dev/null > slice.txt   # ② 只读 [OFFSET, E)
     [ "$(wc -c < slice.txt)" -eq $((E-OFFSET)) ] || echo "SLICE-SHORT"           # ③ 校验切片长度
     shasum -a 256 slice.txt                     # ④ 切片 hash 入台账
     NEW_OFFSET=$E                               # ⑤ 只推进到 E，绝不用「读完后再 stat」的 size
     ```
     **为什么不能读完再取 size**：`tail` 读到 EOF 返回后、`stat` 取值前，launchd 可能追加新行（含 `PREFLIGHT-FAIL`）；把那一刻的 size 当新游标，会让这段字节永远落在两次读取的缝隙里，而 inode 未变、size 未回退，下面的 fail-closed 规则也发现不了。禁止用 `tail -N`。
   - **fail-closed 规则**：err.log 缺失 / 不可读 / inode 变化（轮转）/ `E` 小于上次 offset（被截断）/ 切片长度校验失败，任一情形都登记 `degraded · evidence_gap` 事件并重置游标——不得因为「grep 报 No such file 但管道 exit 0」而当作无异常放过。**`evidence_gap` 的后果**：该日**不构成日通过**（§5.2）；若字节确实无法恢复，只能由用户按 §1 判定 6 同款流程记入**全局接受集**（计入总状态的 `N`），不得靠事后 `closed` 把该日改判为已验证。
   任一命中 → 登记 degraded 事件。**当日已有较早成功行时 C1 仍会 PASS**，故本步不可省。
4. **投影核对（C2，覆盖集每库各跑一次）**：跑 §6.2 C2 —— 判定投影的时间格式、本地日与 vault 身份三项。**active 库的 C2 结果进日通过式**（§5.2）。三类结果：
   - PASS；
   - `vault_id` 为 null（C1a 前的旧产物）：判 **UNVERIFIABLE**，台账当日行必须备注「vault_id 缺失，身份未验」——命令放行不等于已验证；
   - `vault_id` 非空且与目录名不符：这是**跨 vault 串扰的直接现象**，必须按 §4 登记为「串 vault · 待裁」（不能只当 degraded 处理）。
5. **有到期项 → 完成门**：按 §7 锁版的「完成一张板」语义执行（锁版前本条无机械判定，是启动条件的一部分）。
6. **payload 归档**：`cp "$VAULT_PATH/outputs/今日复习.json" <窗口目录>/payloads/<D>-<VAULT_KEY>.json`——runner 每日覆盖同一文件（`daily_review_run.py:135-158`），不归档则次日无从补核。
7. **台账打卡与回执**：在每日打卡表当日行填写全部列 → **当日将台账文件（含 payload 归档）commit 进 git**。机械核验：`git log --since="<D> 00:00" --until="<D+1日> 00:00" --format=%H -- <台账文件>` 非空，且该 commit 版本的 D 行已填（`git show <sha>:<台账文件>` 目检）。**证据等级 = `SELF_ATTESTED_GIT`**：git 提交时间可用 `GIT_COMMITTER_DATE`/`--date` 回填（只读实测确认），故本回执**不证明该 commit 在 D 日已存在**，它是低成本防误与自律锚点，使「D15 一次性补勾 14 天」需要刻意伪造而非顺手完成。对自用 dogfood 这一强度足够；如需可证明的时间锚定须外部时间戳服务/透明日志（不在本卡范围）。

### 5.2 日通过式与漏日

- **日通过（正向 AND，五项全真 = 正常日）**：①当日打卡行存在且 D 行已填、有当日 commit 回执（§5.1-7，等级 `SELF_ATTESTED_GIT`）；②active 库 C1 判定 PASS（当日最后 generate 非 FAILED；当日完全无 generate 行 = FAIL）；③**active 库 C2 判定 PASS 或 UNVERIFIABLE**（PASS = 三项全中；null 身份 = UNVERIFIABLE 且台账已备注，仍算日通过；身份错配 = FAIL，日不通过并登记串 vault）；④有到期日则完成门达成；⑤payload 已归档。**14 日全部日通过是窗口完成的硬前提**（§1 判定 1）——`generate:FAILED` 日即使登记了事件也不构成日通过。
- **内建补救不算异常**：RunAtLoad 开机补跑、A7 生成成功推送失败→补跑只补推送、过窗只落盘——只要当日五项最终为真。
- **补核（宽限）**：当日未 commit，**次日 12:00 前**补打卡行（标「补核」）+ 补 commit + 依据 = 昨日归档 payload（若昨日第 6 步（payload 归档）也漏，依据只剩 log 行与 state 文件，补核行如实注明证据降级）。每窗口补核 ≤N 次（§7 表 A 锁版）。**注意 09:05 起 runner 已进入次日调度并覆盖 payload**（plist 首档 09:05）——补核依据以归档副本为准，不以 live payload 为准。
- **漏日**：当日与补核期均无 commit 回执，或 C1 判定当日无任何 generate 行且无事件登记解释 → 漏日。漏日 → 窗口失败，是否重开由用户裁定。漏日不适用 fix-forward（fix-forward 只管变更，不管活动缺失）。
