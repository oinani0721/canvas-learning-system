# CARD-G2-7b round-8：两次被本机 OOM 杀掉（**不是配额**）
# ⚠️ 批级环境事件 —— 其它并发车道跑 codex 时同样会撞，建议主 session 通告。

## 成因判别（与 09-09 17:32 那次 0 字节**形状相同、成因不同**）

stdout 两次都是 **0 字节**，但：
  $ grep -c 'usage limit' codex-review-CARD-G2-7b-r8.stderr   → **0**
  stderr 末尾不是服务端错误，而是**推理摘要**戛然而止：
    尝试 1 末行: `**Refining fd protection checks**`
    尝试 2 末行: `**Reviewing exported path scope**`
  harness 的任务通知明确写：`stopped because the system is running low on memory`

⇒ 是**本机内存不足被杀**，不是账号配额、也不是命令没跑成。

## 三种成因给出同一个观测，必须分开

| 成因 | 观测 | 判别依据 | 处置 |
|---|---|---|---|
| 账号配额（09-09 17:32） | stdout 0 字节 | stderr 有 `usage limit ... try again at` | 探针复测；重发无意义 |
| 本机 OOM（本次） | stdout 0 字节 | stderr 停在推理摘要 + harness 报 low memory | 等内存恢复后重发 |
| 命令没跑成（`timeout` 那次） | stdout 0 字节 | **rc=127**，stderr 是 `command not found` | 改命令 |

**「0 字节」永远只是现象**。协议 §1 的「0 字节重发一次，再 0 字节 → 人审」是为**配额**
写的（那种情形重发只会撞同一堵墙）；本次成因是**瞬时资源压力**，重发有实质意义，
故不直接套用该条出口，而是先降低并发再重试。
