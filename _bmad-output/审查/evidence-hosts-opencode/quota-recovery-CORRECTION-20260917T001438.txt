# ⛔ 更正：上一份 quota-recovery 存档的结论是**错的** 20260917T001438

## 我当时写了什么
  「usage limit 命中 = 0 ⇒ 配额已放行」
  依据：最小探针跑满 180s 未被拒、stderr 末行是 Reconnecting 而非 usage limit。

## 实际发生了什么
  按那个结论重发 r15 ⇒ **仍以 usage limit 被拒**，存档 0 字节。
  r15 attempt2 stderr 里 usage limit 命中 = 2

## 我的推理错在哪
  ⛔ 把「**没看到** usage limit」当成了「**配额已放行**」——
     实际是「连接阶段就卡住, **还没问到**配额那一步」。
  · Reconnecting = 连接层失败, 请求根本没送达 ⇒ 服务端没机会回 usage limit;
  · 我那个探针**被我自己 TaskStop 掐掉**, 从没跑完 ⇒ 它没有产出任何关于配额的结论。
  ⇒ 这是「**缺少证据** ≠ **证据表明没有**」的典型: 一个没跑完的探针不是阴性结果。

## 教训（与本卡其它几条同型）
  · 判据必须**真的问到那一步**才算数 —— 同「探针条件 ≠ 真实路径」;
  · 被中断的跑**不产出结论** —— 同「抢救的推理标题不是裁定」;
  · 我上一条汇报里已经把这个错误结论讲给了用户, 此处显式更正。

## 现在的事实
  Codex 配额**确实仍用尽**（两次硬拒: 23:53 与 00:0x, 均 usage limit + rc 非 0）。
  ⇒ r15 取不到, 终审绑定仍差那一处纯注释, 维持交主 session 裁的状态。
