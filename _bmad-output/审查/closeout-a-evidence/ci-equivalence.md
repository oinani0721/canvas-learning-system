# ② CI 本地等价验证 — 原始取证

跑法：完全复刻 .github/workflows/test.yml::Run tests 的 env / 选择集 / flags。
唯一偏差：--junitxml 落到 scratchpad（避免在被 Codex 审阅的工作树里新建未跟踪 backend/reports/）。
解释器：本地 backend/.venv = Python 3.14.4（CI 矩阵为 3.11/3.12，差异见验收单如实声明）。

```
########## A) 现行 CI 清单（15 文件）基线 ##########
====================== 303 passed, 661 warnings in 16.23s ======================
EXIT_A=0
########## B) 拟议 CI 清单（15+2 文件） ##########
================ 516 passed, 1 skipped, 661 warnings in 21.40s =================
EXIT_B=0
########## C) 仅两个新文件（隔离归因） ##########
================= 213 passed, 1 skipped, 10 warnings in 5.72s ==================
EXIT_C=0
```

## 加法自洽核对

    A(现行15文件) 303 + C(仅2新文件) 213 = 516 = B(15+2) ✅
    skipped: A 0 + C 1 = 1 = B 1 ✅

⚠️ **这个等式能证明什么、不能证明什么**（本卡自审 MEDIUM-2 更正了此处原本过强的措辞）：

- **能证明**：本次运行里，两段独立跑的通过数严格可加 —— 没有出现「合跑时少了几条」这种
  最常见的交叉污染症状（共享 fixture 被复用、ContextVar 残留导致后跑的用例行为改变）。
- ⛔ **不能证明**「零交叉污染」这个全称命题。集合相同但**顺序不同**：
  本地 runner 把 2 个新文件放在 15 个旧文件**全部结束之后**；
  而 workflow 里它们位于最后两个 `tests/unit/` 文件**之前**（`test.yml:138-141`）。
  相同计数只说明**那一次执行顺序**没失败，无法逻辑上排除全局状态污染。
- **补强**：合并后已按 **workflow 的真实顺序**独立复跑，得 **517 passed + 1 skipped**（见 merge-readiness §五）。
  这条实测比等式更有力——它跑的就是 CI 将要跑的那个顺序。
