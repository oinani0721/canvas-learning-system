## §2 main 独有提交逐条对账（判据 b）

### 2.1 判定方法与其可靠性边界

本对账用了三种独立手段交叉验证，**任何单一手段都不足以定论**：

| 手段 | 能证明什么 | 不能证明什么 |
|---|---|---|
| `git cherry -v HEAD main` | patch-id 匹配 ⇒ 该补丁已被等价应用（`-`） | 报 `+` **不代表**未覆盖——等价实现写法不同即报 `+` |
| 文件级 `git diff --quiet main HEAD -- <f>` | 两侧该文件终态是否逐字节一致 | 一致 ≠ 意图已实现（可能两侧都没实现） |
| 符号级 `git grep <symbol> HEAD` | 符号是否存在 | 存在 ≠ 语义等价；**缺失 ≠ 意图缺失**（可能被重命名或被显式裁掉） |

**补充手段（本轮对抗验证新增，且决定了 3 条改判）**：
- `git log --all --oneline -- <path>` —— 查**文件历史**，识别重命名与孪生提交。只看"旧文件名在 HEAD 是否存在"会把**重命名**误读成**从未带入**。
- `git merge-base --is-ancestor <sha> HEAD` —— 判断 HEAD 线上是否已有同内容的独立提交。
- `git rev-parse <sha>:<file>` 比对 **blob OID** —— 比 diff 更硬的同一性证明。

> **该文件的 5 个 hunk 必须逐 hunk 人工审阅。**

**为什么**：main 版本**整文件覆盖**到 HEAD 会同时抹掉 6 处 loopback 绑定与 3 处绝对路径 bind-mount —— 这是一次性把两个已修 P0 全部回退的安全倒退，且回退后**不会有任何测试报错**（服务照常起，只是端口对局域网敞开）。

### 3.3 精确化：风险的确切来源（`git merge-tree` 实证）

必须把话说准，否则会误导操作：

| 场景 | 是否倒退 | 依据 |
|---|---|---|
| 正常 3-way merge | **否** | `git merge-tree` 实测合并树 `fe963e3541ebaf0f`，读取合并后文件：**6 条 loopback 绑定与 3 条 neo4j 绝对路径全部原样保留**，未进冲突区。唯一冲突块在 volumes 段 |
| `-X theirs` / 整文件取 main 版 | **是** | 直接用 main 侧文件替换，6+3 处全部丢失 |
| `-X ours` | 否（但会丢 main 侧本就为零的净贡献） | main 侧对该文件净贡献为 0（见 §2.3②）|

**结论**：危险不在 merge 算法本身，而在**图省事的批量冲突解决**。这就是 §3.2 禁令的实证根据——`git merge-tree` 证明只要老老实实逐 hunk 审，这 9 处安全配置一处都不会丢。

## §4 三方案对比（判据 c）

### 方案 A — merge（`git merge main`）

| 维度 | 评估 |

### 方案 B — rebase（把 468 个提交 rebase 到 main）

### 方案 C — 弃置 main + 分区 cherry-pick（**本卡推荐**）

把 `main` 视为已停滞的旧线，只把对账认定"需带入"的内容按分区挑进 HEAD：

| 维度 | 评估 |

## §7 方法论教训（如实记录，供后续对账卡复用）

本卡的 9 条初判中**错了 3 条**，全部由对抗验证纠正。三个错误同源于一句话：**把"我没看见"当成了"它不存在"。**

| # | 错误 | 根因 | 正确做法 |
|---|---|---|---|
| 1 | `44113f54` 误判"7/7 文件一致" | `git show --name-only` 对非 ASCII 路径输出**八进制转义 + 引号**，把它喂回 `git diff -- <path>` 匹配空集，`--quiet` 返回 0，与"真的没差异"退出码相同 | 用 `-z`（NUL 分隔不转义）或 `-c core.quotePath=false` |
| 2 | `066da2a7` 误判"HEAD 侧完全不存在" | 只查了**旧文件名**在 HEAD 的存在性，未查文件历史，把**重命名**读成**从未带入** | 必查 `git log --all --oneline -- <path>`；用 `git show --stat` 看 `A => B` rename 标记 |
| 3 | `a4ff09f4` 误判"需用户裁定" | 只证明了**符号不存在**，未回答**意图是否已实现**。缺失可能是被显式裁掉，而非遗漏 | 搜决策文档（`git grep <symbol> HEAD` 不限代码目录）；查该功能的**消费者**是否还在 |

**共同的反制手段**：任何"两侧一致 / 不存在 / 已覆盖"的结论，都要问一句「**我是怎么知道的？这个判据在目标真的存在时会不会也给出同样的输出？**」——若会，这个判据就不成立。
