## §2 main 独有提交逐条对账（判据 b）

### 2.1 判定方法与其可靠性边界

本对账用了三种独立手段交叉验证，**任何单一手段都不足以定论**：

| 手段 | 能证明什么 | 不能证明什么 |
|---|---|---|
| `git cherry -v HEAD main` | patch-id 匹配 ⇒ 该补丁已被等价应用（`-`） | 报 `+` **不代表**未覆盖——等价实现写法不同即报 `+` |
| 文件级 `git diff --quiet main HEAD -- <f>` | 两侧该文件终态是否逐字节一致 | 一致 ≠ 意图已实现（可能两侧都没实现） |
| 符号级 `git grep <symbol> HEAD` | 符号是否存在 | 存在 ≠ 语义等价；**缺失 ≠ 意图缺失**（可能被重命名或被显式裁掉） |

**补充手段（本轮对抗验证新增，且决定了 3 条改判）**：
- `git log --all --oneline -- <path>` —— 查**文件历史**，识别重命名与孪生提交。只看"旧文件名在 HEAD 是否存在"会把**重命名**误读成**从未带入**。
- `git merge-base --is-ancestor <sha> HEAD` —— 判断 HEAD 线上是否已有同内容的独立提交。
- `git rev-parse <sha>:<file>` 比对 **blob OID** —— 比 diff 更硬的同一性证明。

`git show --name-only` 对含非 ASCII 的路径输出**八进制转义并加引号**的形式：

```bash
# 我原来的（错误）做法
$ git show --name-only --format="" 44113f54 | while read f; do
```

### 3.2 ⛔ 硬约束（必须遵守）

> ## ⛔ STOP 条款（合并 `docker-compose.yml` 前必读）
>
> 1. **禁止整文件取 main 版**。具体指：`git checkout --theirs docker-compose.yml`、
>    `git checkout main -- docker-compose.yml`、`git restore --source=main -- docker-compose.yml`、
>    以及任何把 main 那份复制覆盖过来的操作。**这类操作会一次性丢掉全部 9 处安全配置。**
> 2. **`-X ours` / `-X theirs` 禁止盲用**。（语义澄清见下，它**不等于**整文件替换）
> 3. **合并后必须机械验证**，否则不得提交：
>    ```bash
>    git show :docker-compose.yml | grep -cE '^[[:space:]]+- "127\.0\.0\.1:'   # 必须 = 6
>    git show :docker-compose.yml | grep -cE '^[[:space:]]+- /Users/'            # 必须 = 3
>    ```
> 4. 该文件的 5 个 hunk 必须逐 hunk 人工审阅。

**为什么**：main 版本**整文件覆盖**到 HEAD 会同时抹掉 6 处 loopback 绑定与 3 处绝对路径 bind-mount —— 这是一次性把两个已修 P0 全部回退的安全倒退，且回退后**不会有任何测试报错**（服务照常起，只是端口对局域网敞开）。

**⚠️ 语义澄清（本文档初稿在此处说错过，Codex 审查纠正）**：
`-X theirs` 是 merge **策略选项**，只在**冲突块**内偏向对侧，**不是**整文件替换——
非冲突区仍走正常 3-way 合并。所以"`-X theirs` 会让 9 处归零"这个说法是**错的**，
本文档已删除该表述。真正会丢 9 处的是上面第 1 条列出的**整文件操作**。
之所以仍把 `-X` 列为"禁止盲用"，是治理上的保守要求（冲突块里同样可能有安全行），
而不是因为实测会丢 9 处。把正确的整文件风险和错误的 `-X` 风险混在一起说，
反而会让熟悉 git 的人连真正危险的那条也一起忽略——这正是初稿的问题。

### 3.3 精确化：风险的确切来源（`git merge-tree` 实证）

⚠️ **本节是给 §3.2 禁令补充证据的，不是给它开口子的。读完请回到 §3.2。**

| 场景 | 9 处安全配置 | 依据 |
|---|---|---|
| 正常 3-way merge + **逐 hunk 人审** | **全部保留** | `git merge-tree` 实测合并树 `fe963e3541ebaf0f`，读取合并后文件：6 条 loopback 绑定与 3 条 neo4j 绝对路径原样保留，未进冲突区。唯一冲突块在 volumes 段 |
| `git checkout --theirs docker-compose.yml` | **9 处全丢** | 整文件取对侧 |
| `git checkout main -- docker-compose.yml` | **9 处全丢** | 同上 |
| 把 main 那份复制覆盖过来 | **9 处全丢** | 同上 |
| `-X theirs` | 非冲突区保留；**冲突块内偏向对侧** | 它是 merge 策略选项，只作用于冲突块，**不是**整文件替换。本文件唯一冲突块在 volumes 段，9 处安全配置不在其中——但仍禁止盲用 |
| `-X ours` | 同上，方向相反 | 会丢 main 侧净贡献（该文件净贡献本就为 0，见 §2.3②）|

**这张表要读出来的意思不是"正常 merge 很安全，放心合"，而是**：

> 这 9 处安全配置的存活，**取决于你没有对这个文件动整文件替换**。
> git 的 3-way 算法会替你保住它们——`merge-tree` 已经实证了。
> 而 `docker-compose.yml` **一定会冲突**（volumes 段），也就是说：
> **你一定会走到那个必须做选择的路口。** 危险在于在那个路口图省事，
> 用 `git checkout --theirs docker-compose.yml` 之类"整个文件听对面的"来收场——
> 9 处配置一次归零，而且**不会有任何测试报错**：服务照常起来，只是门对着局域网开着。

所以 §3.2 的禁令不是"别 merge"，是**"别在那个路口用整文件替换收场"**，
并且**合并完必须跑一次 STOP 条款第 3 条的两行验证**。

## §7 方法论教训（如实记录，供后续对账卡复用）
