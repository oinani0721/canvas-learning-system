> ### ⛔ 自我更正（Codex round-1 #8 证伪，命令已核）
>
> 我原写「⇒ `/api/v1/rag/query` 在 Dredd 下**必然 422**」——**在这条命令下不成立**。
> `api-spec-sync.yml:394-399` 的实际命令是：
>
> ```
> dredd openapi-current.json http://localhost:8000 \
>   --hookfiles scripts/spec-tools/dredd-hooks.js \
>   --method GET \
>   --names || true
> ```
>
> `--names` **只列出用例名称、不发送任何请求**；`--method GET` 又把 POST 排除在外。
> 所以那条 RAG POST **根本不会被执行**，谈不上 422。
>
> 而且这条命令还带 `|| true`，job 本身又是 `continue-on-error: true` ——
> ⇒ **这个 job 即使启用，也既不会失败、也测不了任何东西。**
> 这让台账里「历史 24/24 全红」的记载与命令形态**对不上**；本卡没有能力核实那段历史
> （日志不可考），只能如实登记这个矛盾。
>
> **仍然成立的部分**：payload 缺 `vault_id` 是**潜在的恢复障碍**——若将来真要复活
> Dredd（去掉 `--names`、放开 method），这三处必须先修。它只是不能被写成「必然 422」。

**更难的那一半**：历史上该 job **24/24 全红**，且当时的日志已不可考（台账记为
「410 不可考」）。也就是说，即使修好 payload，**也没有任何证据能说明它修好之后会绿**——
剩下 23 个端点各自会不会红是未知数。要选甲，就必须先回答：
**「在一个从未绿过、且失败原因不可考的 job 上，怎么证明它能绿？」**
本卡认为这个问题只能靠「真的把它跑一遍」来回答，而那正是它一直做不到的事。

**代价**：`contract-test` job 有 **123 行**，含 Neo4j service 容器、`npm install -g dredd`、
真实起服务、hooks 装载。复活等于把这条链重新拉起来并让它一直绿。

## 三 无论选哪个都必须如实说的一件事

**schemathesis 不等价于 Dredd，退役是有净损失的。**

| | Dredd | schemathesis（本仓现有用法） |
|---|---|---|
| 传输 | **真实 HTTP 栈**（起服务 + 网络） | `from_asgi`，**进程内**，不过网络栈 |
| 用例来源 | 按 OpenAPI 的 **example 回放** | 按 schema **生成**，`max_examples=10` |
| 中间件 / 鉴权 / hooks 流转 | 覆盖 | **不覆盖** |
| 检查项 | 回放响应与 example 比对 | status/content-type/headers/response-schema 四项一致性 |

⇒ 退役后**确实丢失**的是「真实 HTTP 栈按 example 回放 + hooks 流转与鉴权」这一层。
本页与后续验收单**禁止**把 schemathesis 写成「已完全覆盖契约」。

## 五 执行乙案时已知的风险（供合并前逐项批 diff 时对照）

1. **CI/CD 变更属破坏性操作**：按全局 CLAUDE.md，车道只落 commit、**不 push**；
   合并前由用户逐项批 diff。本卡遵守。
2. **白名单口径不可动**：`test.yml` 的 17 文件显式清单是历史上「小而确定的绿门」
   换来的（该 workflow 曾连续 12 次全红、四个月没绿过）。加文件必须做**可加性验证**
   （现有 17 个 + 新文件全绿，收集数严格可加），不得改成目录级或 marker 级。
3. **`from_asgi` 会在进程内起 app**：本地验证前后必须对账 `data/` 目录
   （历史教训：TestClient lifespan 会往真实 data 目录写东西，而 `.gitignore` 会让
   `git status` 看不见）。本卡已在跑前拍快照。
4. **运行时长是硬约束**：本卡在本机实测该测试的耗时（结果与后续处置见验收单
   §「乙案可行性」）。若它在 CI 预算内跑不完，乙案不能按原样落地——那会把
   「一个必红的 job」换成「一个会挂住的 job」，比现状更糟。

### 6.1 实测发现（三条，全部本机复现）

**(1) 那个"替代品"在**当前已装的版本上**跑不通——它是照 3.x 后期写的，环境漂到 4.x 就坏了。**

`test_openapi_contract.py` 用到两处 API：

| 位置 | 用法 | 3.39.0 | 4.14.3 |
|---|---|---|---|
| `:26` | `schemathesis.openapi.from_asgi(...)` | ✅ 有 | ✅ 有 |
| `:60-65`（改前） | `schemathesis.checks.status_code_conformance` 等四个**模块属性** | ✅ 有 | ❌ **全没有** |
| （改后本卡用的） | `checks.load_all_checks()` + `CHECKS.get_by_names(...)` | ❌ 无 | ✅ 有 |

> ### ⛔ 自我更正（本页初稿写错，已由本卡自己的证伪实验推翻）
>
> 初稿写的是「**任何** schemathesis 版本上都跑不通」「从未被真正执行过」。**这是错的。**
> 我在一个**一次性 venv**（不碰共享 venv）里实测 `schemathesis==3.39.0`：
> `openapi.from_asgi` 与四个 `checks.*_conformance` **两套 API 并存**，
> 即该文件在 3.x 后期版本上**是能跑的**。
> 「从未被真正执行过」同样无法证明——它可能在某个 3.x 环境里跑过。
>
> 正确的口径是：**这个文件是照 3.x 后期写的；4.x 把 checks 从模块属性挪进注册表，
> 于是它在 4.x 上碎了。而 `>=3.0` / `>=3.19.0` 这两个没有上界的 pin，正是让环境
> 漂到 4.x 的原因。** 本机已装的就是 4.14.3。
>
> 教训与本车道前两张卡同型：把「我测到的那一个版本」当成「所有版本」。
> 分辨办法就是这次用的——**造一个能翻转结论的对照环境去打自己的断言**。

本机 4.14.3 实测：`dir(schemathesis.checks)` 里那四个名字**一个都没有**；
`hasattr(schemathesis, "from_asgi")` = **False**（顶层的在 4.x 已移除）。
而 3.39.0 里**没有** `load_all_checks` / `CHECKS` ——
⇒ 本卡改后的写法是 **4.x 专用**，因此把 pin 抬到 `>=4.0` 是**必要**的，不是顺手。

**(2) `importorskip` 掩盖了它，机制比"静默 skip"更具体。** 最小演示：

```
模块不存在      -> 1 skipped, rc=5   (pytest 的"没收集到测试")
模块在但版本不对 -> 1 failed,  rc=1   (精确 AttributeError)
```

rc=5 单独跑会让 CI 步骤红；但一旦放进 `test.yml` 那个 17 文件白名单，其余文件有真实
通过的用例，**整步就是 rc=0 绿，那条 skip 被无声吸收**——这正是"接进 CI 却毫无意义"的形态。
（这也说明卡文要求的 `python -c 'import schemathesis'` 硬前置是必要的，只是它挡不住
"装了但版本不对"，那需要断言 API 而不只是 import。）

**(3) 即使把 API 修好，它也跑不完。** 逐层计时（同一 operation `GET /api/v1/health`）：

| 测量 | 耗时 |
|---|---|
| `import app.main` + `from_asgi` 建 schema | 7.1s（一次性） |
| 收集 206 个 operation | 35.8s（一次性） |
| **schemathesis `case.call()` 单次** | **20–50s** |
| 其中 checks 部分 | 0.00s（`call` 占满） |
| 对照：`httpx.ASGITransport` 直调同端点 | **0.01s** |
| 对照：`TestClient` 直调同端点 | **0.00s** |
| 对照：`TestClient` 跑一次 lifespan | 7.1s |

> ### ⛔ 自我更正（Codex round-1 #6 证伪，源码已核）
>
> 我原写「慢的**不是应用**，是 schemathesis 4.x 的 ASGI 传输层」——**归因错了，方向正好反过来**。
> 读 4.14.3 的源码：
>
> ```python
> # schemathesis/transport/asgi.py
> class ASGITransport(RequestsTransport):
>     def send(self, case, *, session=None, **kwargs):
>         ...
>         with asgi.get_client(application) as client:      # <- 每次调用新建
>             return super().send(case, session=client, **kwargs)
>
> # schemathesis/python/asgi.py
> def get_client(app):
>     from starlette_testclient import TestClient as ASGIClient
>     return ASGIClient(app)
> ```
>
> `with TestClient(app)` **进入时跑 app 的 lifespan startup、退出时跑 shutdown**，
> 而我自己测过这个 app 的 **lifespan 一次就要 7.1s**（它要初始化 MemoryService、
> Graphiti 等）。所以 `case.call()` 的 20s 里，**大头正是应用自身的初始化**，
> 不是传输层的额外开销。
>
> **准确的说法**：schemathesis 4.x 的 ASGI 传输**每次调用都新建一个客户端**，
> 于是这个 app 昂贵的 lifespan 被乘以了调用次数。两个因素都在，主项是应用。
> 而我拿「`httpx.ASGITransport` 直调 0.01s」作对照是**不公平**的——那个对照
> 复用了同一个客户端、只跑一次 lifespan。
>
> 这也指出了真正的修复方向（留给新卡）：让合约测试复用一个已 startup 的客户端。

206 operations × **1** example × 20s ≈ **70 分钟**；按文件里写的 `max_examples=10` 则以小时计。
（这个外推是**假设性估算**，不是实测——我没有跑完整套。）

两个曾经想用来解释慢的假设，**试验没有支持它们，但也不足以排除**（Codex round-1 #7）：
本机服务全 closed（7691/7692/11434/12341），但端口 closed 不排除连接尝试与重试退避，
且 `health.py:142` 存在按运行状态 ping Neo4j 的分支；禁系统代理（`NO_PROXY='*'`）
后反而更慢（49s vs 22s），但在已知大方差下单组结果不能排除代理相关开销。

### 6.2 重裁结果

> **用户 2026-09-05（前提推翻后重裁）**：**本卡只落已完成的、不依赖该前提的部分，不退役。**
>
> 即：**保留** `contract-test` job（仍 `if: false`）与 `dredd-hooks.js`，**不动** `test.yml`；
> 本卡交付 = 本裁决页 + `test_openapi_contract.py` 的 API 修复 + schemathesis 版本口径
> 统一到一处 + 全部实测证据；把「schemathesis 每次调用 20–50s」立**新卡**。

**为什么不是"先退役再说"**：乙案的退役是**有条件的**——条件是替代品真能接上。条件不成立时
单做退役，会把「一个已停用但还在树上、随时可复活的 job」变成「什么都没有」，
这是**单向的覆盖面减法**，且它减掉的正是用户当初选乙想保住的东西。
