## 二 三个选项与各自的实测前提

**先决条件（不是可选的）**：`scripts/spec-tools/dredd-hooks.js` 的 payload 已经与
现行契约不符，复活前必须先修。本卡实测（证据取自 `backend/openapi.json` 快照，
即权威真相源，不是推断）：

RAGQueryRequest.required   = ['query', 'vault_id']
dredd-hooks.js:38-41  发的是  { query, top_k }
dredd-hooks.js:152-158 的 before 钩子改成 { query, top_k, subject }

⇒ `/api/v1/rag/query` 在 Dredd 下**必然 422**，与它是否「曾经能绿」无关。

**更难的那一半**：历史上该 job **24/24 全红**，且当时的日志已不可考（台账记为
「410 不可考」）。也就是说，即使修好 payload，**也没有任何证据能说明它修好之后会绿**——
剩下 23 个端点各自会不会红是未知数。要选甲，就必须先回答：
**「在一个从未绿过、且失败原因不可考的 job 上，怎么证明它能绿？」**
本卡认为这个问题只能靠「真的把它跑一遍」来回答，而那正是它一直做不到的事。

**代价**：`contract-test` job 有 **123 行**，含 Neo4j service 容器、`npm install -g dredd`、
真实起服务、hooks 装载。复活等于把这条链重新拉起来并让它一直绿。

## 三 无论选哪个都必须如实说的一件事

**schemathesis 不等价于 Dredd，退役是有净损失的。**

| | Dredd | schemathesis（本仓现有用法） |
|---|---|---|
| 传输 | **真实 HTTP 栈**（起服务 + 网络） | `from_asgi`，**进程内**，不过网络栈 |
| 用例来源 | 按 OpenAPI 的 **example 回放** | 按 schema **生成**，`max_examples=10` |
| 中间件 / 鉴权 / hooks 流转 | 覆盖 | **不覆盖** |
| 检查项 | 回放响应与 example 比对 | status/content-type/headers/response-schema 四项一致性 |

⇒ 退役后**确实丢失**的是「真实 HTTP 栈按 example 回放 + hooks 流转与鉴权」这一层。
本页与后续验收单**禁止**把 schemathesis 写成「已完全覆盖契约」。

## 五 执行乙案时已知的风险（供合并前逐项批 diff 时对照）

1. **CI/CD 变更属破坏性操作**：按全局 CLAUDE.md，车道只落 commit、**不 push**；
   合并前由用户逐项批 diff。本卡遵守。
2. **白名单口径不可动**：`test.yml` 的 17 文件显式清单是历史上「小而确定的绿门」
   换来的（该 workflow 曾连续 12 次全红、四个月没绿过）。加文件必须做**可加性验证**
   （现有 17 个 + 新文件全绿，收集数严格可加），不得改成目录级或 marker 级。
3. **`from_asgi` 会在进程内起 app**：本地验证前后必须对账 `data/` 目录
   （历史教训：TestClient lifespan 会往真实 data 目录写东西，而 `.gitignore` 会让
   `git status` 看不见）。本卡已在跑前拍快照。
4. **运行时长是硬约束**：本卡在本机实测该测试的耗时（结果与后续处置见验收单
   §「乙案可行性」）。若它在 CI 预算内跑不完，乙案不能按原样落地——那会把
   「一个必红的 job」换成「一个会挂住的 job」，比现状更糟。

### 6.1 实测发现（三条，全部本机复现）

**(1) 那个"替代品"从未被真正执行过——它在任何 schemathesis 版本上都跑不通。**
`test_openapi_contract.py` 把两代 API 混写在同一个文件里：

| 位置 | 用法 | 形态 |
|---|---|---|
| `:26` | `schemathesis.openapi.from_asgi(...)` | **4.x** |
| `:60-65`（改前） | `schemathesis.checks.status_code_conformance` 等四个**模块属性** | **3.x** |

本机 4.14.3 实测：`dir(schemathesis.checks)` 里那四个名字**一个都没有**；
`hasattr(schemathesis, "from_asgi")` = **False**。所以：
3.x → `:26` import 期 `AttributeError`；4.x → `:60-65` **每个用例**都 `AttributeError`。

⇒ **CI 侧覆盖为零不只是"没接进去"，而是"接进去也是红的"。**
这与本页第二节甲案里那个"24/24 全红且原因不可考"的 Dredd **是同一种病**。

**(2) `importorskip` 掩盖了它，机制比"静默 skip"更具体。** 最小演示：

```
模块不存在      -> 1 skipped, rc=5   (pytest 的"没收集到测试")
模块在但版本不对 -> 1 failed,  rc=1   (精确 AttributeError)
```

rc=5 单独跑会让 CI 步骤红；但一旦放进 `test.yml` 那个 17 文件白名单，其余文件有真实
通过的用例，**整步就是 rc=0 绿，那条 skip 被无声吸收**——这正是"接进 CI 却毫无意义"的形态。
（这也说明卡文要求的 `python -c 'import schemathesis'` 硬前置是必要的，只是它挡不住
"装了但版本不对"，那需要断言 API 而不只是 import。）

**(3) 即使把 API 修好，它也跑不完。** 逐层计时（同一 operation `GET /api/v1/health`）：

| 测量 | 耗时 |
|---|---|
| `import app.main` + `from_asgi` 建 schema | 7.1s（一次性） |
| 收集 206 个 operation | 35.8s（一次性） |
| **schemathesis `case.call()` 单次** | **20–50s** |
| 其中 checks 部分 | 0.00s（`call` 占满） |
| 对照：`httpx.ASGITransport` 直调同端点 | **0.01s** |
| 对照：`TestClient` 直调同端点 | **0.00s** |
| 对照：`TestClient` 跑一次 lifespan | 7.1s |

⇒ 慢的**不是应用**，是 schemathesis 4.x 的 ASGI 传输层（它继承自 `RequestsTransport`）。
206 operations × **1** example × 20s ≈ **70 分钟**；按文件里写的 `max_examples=10` 则以小时计。
排除过的假设：本机服务全 closed（7691/7692/11434/12341）所以不是"真在查库"；
禁掉系统代理（`NO_PROXY='*'`）反而更慢（49s vs 22s），所以也不是代理超时。

这是**单向的覆盖面减法**，且它减掉的正是用户当初选乙想保住的东西。
