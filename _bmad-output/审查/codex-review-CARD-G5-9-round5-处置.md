## 二、⛔ HIGH-1 的教训：**我创造了一个区分，却没在消费端用它**

round-4 我把 `_fsync_dir` 从二态改成三态，**专门**为了区分「不支持」与「失败」。
但调用方只写了：

```python
dsync_err = dsync_msg if dsync_state == "failed" else None
```

⇒ `"unsupported"` 照样走到 `os.unlink(target)`。

而 `"unsupported"` 的语义恰恰是**「无法证明留痕目录项已落盘」**——此时删源，
崩溃后可能两端皆空，**丢的是不可重生的用户原件**。

> **三态返回值的价值全在调用方怎么分派。只改函数不改调用方，
> 等于把风险从「看不见」变成「看得见但没人看」——甚至更糟，因为它制造了「已经处理了」的错觉。**

## 三、逐条处置

| # | 发现 | 整改 | 变体 |
|---|---|---|---|
| **HIGH-1** | undo 只阻断 `"failed"`，`"unsupported"` 继续删源 ⇒ 特定 FS + 崩溃即可致**不可逆数据丢失**（不需要攻击者） | 删源是不可逆动作 ⇒ **`"unsupported"` 与 `"failed"` 同样 fail-closed**；拒绝文案改为「持久化未获确认」并提示换 `--undo-dir` | **T** |
| **HIGH-2(a)** | 第一次撤销返回 `kept` 设下 `rollback_note`；外层第二次**成功删掉**时既不清旧 note 也不重算状态 ⇒ 回执说「目标仍在 vault 里」而**实际已删** | 以**最后一次**结果为准：成功即清除旧 note | **U** |
| **HIGH-2(b)** | `unlink` 后未 fsync 目录就返回 `"deleted"`，调用方据此明确声称「已撤销」——崩溃后目标可能**重现**，声称就成假话 | 对已在手的 `dir_fd` 直接 fsync；失败不改结论（文件确已移除）但**降级为 `"deleted_unsynced"`**，让调用方如实措辞 | **V** |
| **MEDIUM-2** | `_fsync_dir` 按路径重开目录用裸 `O_RDONLY` ⇒ 路径被换成 symlink 时会 fsync 到别处 | 补 `O_DIRECTORY\|O_NOFOLLOW` | **X** |
| **LOW-1** | tmp 已被并发清掉时，成功路径仍报「未能清理、请手动删除」（失败路径早已单列 `FileNotFoundError`，成功路径漏了） | 成功路径同样单列，消除误告警 | **W** |
