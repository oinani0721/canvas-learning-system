## 二 本轮改动：一处 r9 没抓到的**双向**口径错

r9 之后我按「参数空间逐维枚举」自查接受域，发现 ⑦ 名字长度写的
「**每个**名字 ≤507 UTF-8 字节」是把一条**和式**约束塌成了单名上限。

真口径（macOS tzcode 把两个名字连同各自的 NUL 终止符存进同一个 `TZ_MAX_CHARS=512`
缓冲区）：

```
带 dst ⇒ len(std) + len(dst) + 2 ≤ 512
无 dst ⇒ len(std) + 1 ≤ 512
```

**220 例网格实测零分歧**（std 名 × dst 名各取边界两侧，含多字节名）。

507 这个数字的来历：当时所有样本的 std 名恒为 `AAA`（3 字节），
507 = 512 − 3 − 2 只是**那个子族**里的特例。两个方向的错都真实存在：

| 方向 | 串 | 旧口径 | C 库 |
|---|---|---|---|
| **误拒** | `<A×507>-1<BBB>,M3.2.0,M11.1.0`（和 512） | 拒（507 判超限） | 收 |
| **误收** | `<A×512>-1`（无 dst，和 513） | 收（**该支根本没进检查**） | 拒 |
| **误收** | `<A×507>-1<B×507>,…`（各 ≤507、和 1016） | 收 | 拒 |

误收方向更糟：它让本实现接受 C 库拒绝的串，从而与机器本地时区给出不同的归日。

### ⛔ 一处我先写错、又自己推翻的判断（请重点核这一条的最终结论）

我一度把 **③ 那条拒 NUL 的检查**判成「不可达死分支」并照此改了注释——**是错的**。

- 错的依据：我只测了 NUL 在**串尾**、和在 **std 偏移与 dst 名之间**两个位置，
  两处都由正则先拒，于是结论「这条永不执行」。
- 推翻它的事实：正则的引用名写作 `<[^<>]+>`，而 `[^<>]` **放行** NUL ⇒
  `AAA0<B‹NUL›BB>` 这类**引用名内部**含 NUL 的串能一路匹配进来，只有 ③ 能拒。
- 负控复核：变异掉 ③ 后 `test_omitted_rule_branch_does_not_widen_the_accepted_offset_domain`
  变红，失败正文逐字指出 `parse_posix_tz('AAA0<B\x00BB>')` 被接受。

错因与本轮另外两处同形：**样本在某一维（NUL 在名字内 / 名字外）只取到一个值，
而那一维恰好决定结论**。注释已改回「活防线 + 唯一显形位置是引用名内部」。

### 一处如实登记

**① `len(spec) > 1024`** 是**性能**防线不是正确性防线：去掉它接受域一字不变，
只是 4000 字符的坏串从 0.000s 退回 0.475s。它在负控里是**唯一**一段期望 GREEN，
如实登记「它不由 pytest 守，由计时判据守」，而不是假装有门。

⚠️ 这里有个我踩到的陷阱值得你一并核：**期望 GREEN 的段，绿只证明「我跑的那几个
nodeid 没红」，不证明「没有任何门守它」**。③ 那次的绿就是这么来的——我给它绑的
nodeid 所在的表里根本没有引用名内含 NUL 的用例。

### 已枚举过、确认零分歧的维度

切换时刻的**符号位**：正则的 `stime`/`etime` 是 `\d{1,3}` 无符号位，
而 macOS libc 对 `/-1`、`/-167`、`/+2` **全拒**（实测），两侧一致。
（注：glibc 支持 `-167..167`；本卡判据是对齐**本机** C 库，D-18 钉的是机器本地时区。）
