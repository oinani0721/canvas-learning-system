## 5. round-2 整改（Codex round-1 判 `BLOCKER/HIGH 清零: 否` 之后）

独立审查用**同族**反例把 v3 的三条修法打穿了两条。五条新缺陷与修法：

| 反例 | 根因 | 修法 |
|---|---|---|
| `本文由 openai-gpt-oss-120b-…-v2026-09-01 生成`（中间 65 字符） | 中文句式当时限 `{1,40}`，**上界本身就是缝**，而文档写的是「骨架闭合」 | 去掉上界 |
| `Generated by: GPT-4` | 英文句式要求 `by` 后是字面空格 | `by` 词边界后允许非词字符再要求词字符 |
| `Generated by<U+200B>GPT-4` | 零宽字符不是 `str.isspace()` 认的空白 | 护栏专用归一（零宽→空格）；**不动 C2 判据**，避免顺手扩大确定归档面 |
| `doi:`（空）+ `doi: 10.1000/hidden` | `frontmatter_map` 用 `setdefault` 只留首值，护栏全盲，**同时穿透 C3 与 C4** | 护栏改扫 `frontmatter_pairs` 的不折叠全量键值对；判据侧首值语义不动 |
| `citation: ISBN 978-7-111-54742-6` | 来源判定在**枚举危险键名/值形态** = fail-open | **方向反转**：`_HARMLESS_FM_KEYS` 白名单之外的非空值一律未消化 |

方向反转是这一轮最重要的结构改动。理由是两种漏判后果不对称：漏一个白名单项只是
多落一次「拿不准」，漏一个来源键名是把用户材料确定删掉。所以默认值必须站在
「拦住」那一侧。相应地，①-⑧ 那些具体信号不再是安全底线，而是**给出更好理由**
的机制 —— 让 `uncertain_reason` 说得出「这是个 DOI」而不是笼统的「有个不认识的键」。

### 变异判据升级：从「N/N killed」到「失败集合相等」

`g56c_mutations.py` 现在要求**实际变红的那一组门逐个等于事先写死的名单**：

- **多红** = 波及面比预期大，说明对实现的理解不准；
- **少红** = 那条防线根本没有门在看 —— 这才是真正危险的一侧。

八条变异 8/8 命中。⛔ 这条判据当场抓到一个真问题：M-ZEROWIDTH 首轮**少红**，
因为为修 `Generated by:` 写的正则顺手也吃掉了零宽，零宽那层成了死层。处理方式是
补一道专测它的门（`test_zero_width_split_marker_still_reads_as_ai_suspect`），
并在 `_norm_guard_line` 的 docstring 里如实写明它只是「理由质量」层、不是安全防线
——**改的是期望与文档，不是把判据放宽**。

### ⛔ 变异脚本事故（如实记录）

本脚本被 2 分钟超时 SIGTERM 杀掉时，`try/finally` **没有执行**（Python 默认信号
处理器直接终止进程，不抛异常），源码被留在 M-PAIRS 变异态。能安全恢复靠的是脚本
开头已经打印过基线 sha —— 有那一行，还原才有**可验证判据**，否则只能凭记忆猜。
现已注册 SIGTERM/SIGINT/SIGHUP 处理器，被 kill 时也还原并打印还原后的 sha。

### 本节不证明什么

- 不证明「没有第六条」。v3 自称三条全修，一轮审查就被同族反例打穿两条。
- 白名单兜底只覆盖 **frontmatter 里的非空值**；正文侧的未消化结构与文头声明侧
  各有自己的边界，白名单本身也可能收窄得不对。

## 6. round-3 整改（Codex round-2 判 `BLOCKER/HIGH 清零: 否` 之后）

| 反例 | 根因 | 修法 |
|---|---|---|
| `Generated by_GPT-4` | `_` 属于 `\w`，`by_` 处**没有词边界**，`generated by\b\W*\w` 整条穿透（C3、C4 两个出口都中） | 改判「by 后面不是字母数字」，分隔符连下划线一起吃 |
| `title: Genera<ZWSP>ted by GPT-4` | 零宽换空格只对**词间**成立；插在词内会把 `generated` 拆成 `genera ted`，骨架与标记表一起失效 —— 比不处理更糟 | 两种还原都试：换空格还原词间，直接删还原词内 |
| `title: ISBN 978-…` / `aliases: <馆藏号>` / `title: <唯一写下的那句话>` | 白名单放行的是**键名**，可信息在**值**里 | **白名单整个取消**：任何非空 frontmatter 值都不确定删除 |

### 来源判定的口径改了两次才落定（这是本卡最贵的一段）

1. **v3**：枚举危险的键名与值形态（source/url/doi）→ `citation: ISBN …` 两样都不沾；
2. **v4**：反转为「已知无害键名」白名单 → 放行的是键名，可信息在值里；
3. **v5**：任何非空 frontmatter 值都不确定删除。

「这个键名无害」是句**无法机械成立**的断言：`title` 可能是随手一个字，也可能是
这份材料唯一写下来的东西 —— 引擎分不出，分不出就不该替用户决定。
C4 侧的自相矛盾也随之消失：此前引擎挂着「正文重复证据不覆盖这些元数据」的冲突，
verdict 却是 `建议删 + confident=true`。

⚠️ 代价如实：C3 的可达面只剩三种 —— 0 字节、没有 frontmatter 的纯骨架、
frontmatter 全是空值。这三种在
`test_any_nonempty_frontmatter_value_blocks_confident_deletion` 里各配了正向对照锚，
防止「少删」滑成「判据死了」。

### 顺带修的 MEDIUM

- **schema 门的 Sleeping fixture 建错位置**：建在 `vault/Sleeping`，而生产读的是
  `<收件箱>/Sleeping` ⇒ `sleeping.items` 恒空 ⇒ 那一层键锁空转（在副本里给
  `sleeping.items[*]` 加一个键，88 门照样全绿）。已改位置并补 `items` 非空断言 +
  逐键锁；期望键名取自生产构造点，不是从输出反抄 —— 上一稿凭印象猜键名，当场被
  这条断言打回，这正是它的作用。
- **变异 runner 判据两处过松**：只解析 `FAILED ` 忽略 `ERROR `（变异若把模块改到
  import 失败，套件全是 ERROR、一条 FAILED 都没有）；`rc not in (0,5)` 会把 rc=2/3/4
  （runner 自己坏了）当成「红了」。现要求 `rc == 1` 且两类都计入失败集合。
- **「骨架闭合」措辞**：round-2 去掉长度上界后写成「骨架才真的闭合」，round-3 又从
  同一条骨架上抓出两处。现改为「不随模型名增长」，并写明它自己的边界（同一行、
  不跨句读、动词限定）。

### 变异期望集合被实测更正一次（如实）

M-FALLBACK 首跑**多红**一门：round-3 给 `unparsed_source` 门加的「带非空元数据的
重复件落 C6」同样靠⑨承重，而我把期望写成了只有一门。改的是期望（把真实覆盖面记全），
判据仍是集合相等 —— 多红说明对波及面的理解不准，这本身就是这条判据要暴露的东西。

### 不可见字符：类别判定挡住了 Cf/Mn/Cc，但类别本身不等于「视觉不可见」

审查用 10 个此前未用过的码点做矩阵。结果分成三类：

1. **Cf / Mn / Cc 全闭合**（U+2064、U+1BCA0、U+E0001、U+0301、U+1AB0、U+E0100、U+0001）——
   类别判定这一步是对的。
2. **U+200A HAIR SPACE（Zs）是我的明确遗漏**：它 `isspace()` 为真，只被
   `_norm_ai_line` 折叠成普通空格，词照样是拆的；而删版当时不删它，于是两个
   变体都还原不出 `generated`。**已修**：删版连非 ASCII 空白一起删。
   ⚠️ 修的过程中先写成「连 ASCII 空格也删」，当场被门打回 ——
   那样 `generated by GPT-4` 在删版里成了 `generatedbyGPT-4`，删版等于自废。
   正确口径是删「看不见、又不是正常词间空格」的那一类。
3. **U+3164 HANGUL FILLER（Lo）与 U+2800 BRAILLE PATTERN BLANK（So）：
   如实登记为原理上限，不修。** 它们在屏幕上是空白，但 Unicode 归为字母/符号，
   `isspace()` 也是 False —— 机械上就是普通字符。把 Lo/So 整类剥掉会连正常韩文
   与盲文一起剥，是更坏的交易。**「视觉上不可见」需要字形宽度数据才判得了，
   不是字符属性能决定的。** 结构化的兜底得改 C3 对**标题行**的处理（现在标题
   不算实质正文），那是判据面的语义变更，超出本卡范围。

⚠️ 所以「不可见字符」这一条**在本卡内没有真正闭合**：类别内的都挡住了，
类别外的两个仍会落 `建议删 + confident=true`。这是本卡交付时**已知且未修**的
BLOCKER 面，登记在此，不粉饰。

### 这一节要留给后人的话

同一族缺陷被打穿了**四次**：模型名枚举 → 骨架长度上界 → 不可见字符枚举 →
类别判定仍不等于视觉不可见。每一次我都以为找到了「结构化」的答案，下一轮就有
反例。**判据的每一次「结构化」都只是把边界往外推了一格，不是消灭了边界** ——
真正该做的是把那一格的位置写清楚（现在文件头的偏差 17 与本节就是这么写的），
而不是宣布闭合。

## 9. 用户裁决：标题里写了字算实质正文（2026-09-02）

第 8 节把 `U+3164`/`U+2800` 登记为「原理上限、超出本卡范围」。量化那个裁决点时
发现我低估了它 —— 根因不只影响对抗构造：

```text

  # Genera<U+3164>ted by GPT-4  建议删 confident=true   ⛔ 未闭合 BLOCKER
```

**「只写了标题、正文还没动笔」的笔记会被确定删除**，这不是刻意构造，是真实
使用场景。而它与本卡已采纳的「取消 frontmatter 白名单」逐字同构：标题可能是
随手一个字，也可能是这份材料唯一写下来的东西 —— 引擎分不出，分不出就不该
替用户决定。

把两个方案的代价量化后交由用户拍板，用户选择**改**：

```text
新口径：可确定删除 5/10
  仍可确定删除：0 字节 / 纯空行 / 纯分隔线 / 空标题模板 / 只有引用符
  # 微积分基本定理的两种证法      拿不准 ✅
  # Genera<U+3164>ted by GPT-4  拿不准 ✅  ← 第 8 节那条 BLOCKER 随之关闭
```

⚠️ 代价如实：C3 的可确定删除面收窄到「**一个字都没写**」的五种。这五种在
`test_heading_with_text_counts_as_substantive_content` 里各配了正向对照锚，
一条都不能失守 —— 否则「少删」就变成「判据死了」。

### 连带：三道门的样本必须改，否则它们不再测自己声称测的东西

标题有字后，`# 标题\n\n<!-- source: … -->` 这类样本会被「标题有字」先接住，
信号⑩ 与零宽护栏根本轮不到。已把注释门改用**空标题**、不可见字符门的端到端半边
改用 **frontmatter**（纯函数半边仍直锁 `_strip_invisible`）。
⚠️ 这类「修了实现导致门测不到目标层」的连带，是本卡第二次出现（第一次是零宽
那层被 `\W*` 顺手覆盖）——**改判据后要重问一遍：每道门现在还测得到它的目标吗？**

### 它证伪了我的一个声明

我在 `f6c1fdaf` 的 commit 里写「顺带关闭了 U+3164/U+2800 那条 BLOCKER」。
终审实测：**只关闭了 C3 那一半**。C4 的 `dup_body()` 仍把标题整行丢掉再比对，
所以

```markdown
# 只有这一份写了母本第37页
<与库内逐字相同的正文>
```

照样是 `C4_exact_duplicate / 建议删 / confident=true` —— 标题里的独有信息随重复件
一起没了；隐形字符伪装的标题只要带上一段重复正文，同样绕回来。

⚠️ 这是本卡**第 N 次**「声明比证据宽」。上一次我还在文件头写下这条教训，转头

### 用户裁决②：C4 不跟进

把同一条逻辑延到 C4 的代价已量化：

```text
5 件取样（库内母本 = `# 母本标题` + 正文）
  当前口径（丢标题）  → 5/5 识别为重复
  方案 C（标题进比对）→ 仅 1/5 识别为重复
    「同稿不同标题」「一份有标题一份没有」都不再算重复
```

「同一段正文粘了两份、标题不同」正是清收件箱最常见的场景。用户选择**保住重复
识别能力**，接受「标题里的独有信息可能随重复件被删」这一代价，登记为偏差 18。
⚠️ 它与 C3 侧裁决①**刻意不一致** —— 这个不一致是被明确选择的，不是遗漏。

### 五轮下来最该带走的一句

每一轮我都以为找到了「结构化」的答案，下一轮就有反例：
模型名枚举 → 骨架长度上界 → 不可见字符枚举 → 类别判定 → 处理顺序。
**判据的每次结构化只是把边界外推一格。** 该做的是把那一格的位置写清楚、
并让每句"已关闭"都绑着一条跑过的命令，而不是宣布闭合。

### 10.1 第五轮那两条 HIGH 已修（信号⑩的覆盖面补全）

两条都是**保护面不该取决于写法**的实现缺陷，修法低风险：

| 反例 | 根因 | 修法 |
|---|---|---|
| `<!--\nsource: https://…\n-->`（跨行） | 只收了**闭合那一行**的 `rem[:i]`，中间整行在 `i < 0` 分支直接 `break` 丢掉 —— 单行注释反而受保护 | `break` 前把 `rem` 收进去 |
| frontmatter 里 `# source: https://…` | 被 `unparsed_fm` 的 `startswith("#")` 当 YAML 注释跳过，既不进 unparsed 也不进 map | fm 注释行并入信号⑩（同源：引擎剥掉了内容就该说出来） |

⚠️ 「保护面取决于换不换行/写在哪一区」这种不一致，本身就是缺陷的信号 ——
同一条来源，写成单行注释受保护、写成多行就被删，没有任何道理。

`splitlines()` 顺序那条（U+001D/001E/2028/2029）落在 **C4** 侧，已由用户裁决②
（C4 不看标题、不跟进）覆盖，登记在偏差 18/19，不在本节修。

### 10.2 第六轮：只剩一条，且与前两条同根

R6-H1：`title: "" # source: https://inline.example/only` —— **行尾** YAML 注释里的
唯一来源被 `_clean_fm_value` 剥掉且没人收，C3/C4 双出口全穿。

⚠️ 至此这个根因已经以**三种写法**各暴露一次：跨行 HTML 注释、frontmatter 整行
YAML 注释、frontmatter 行尾 YAML 注释。**保护面不该取决于来源写在哪里** ——
同一条 `source: https://…`，写成单行 HTML 注释受保护、换行写就被删、写进
frontmatter 注释也被删，这种不一致本身就是缺陷的形状。三处现已同口径（剥注释
的正则与 `_clean_fm_value` 逐字同源，免得又出现一个「看写法决定保护」的缝）。

新增正向对照锁住边界：`source: "https://ok.test/x" # 官方来源` 仍走 C1 ——
判据排在信号之前，信号⑩ 扩到行尾注释后不得把它抢走。

**每轮新 HIGH 数：5 → 3 → 2 → 3 → 1。** 收敛趋势明显，但六轮没有一轮是 0。

## 10.3 第七轮，以及为什么在这里停

### ⛔ 为什么在第七轮停：这不是放弃，是有证据的判断

R7-H1 是「来源被引擎剥掉」这个根因的**第四种写法**：

1. 跨行 HTML 注释（第五轮）
2. frontmatter 整行 YAML 注释（第五轮）
3. frontmatter 行尾 YAML 注释（第六轮）
4. 围栏 info string（第七轮）

四种写法各暴露一次，而 Markdown 里**能放文本的位置是开放集合** —— 链接 title、
图片 alt、表格单元格、脚注定义、HTML 属性…… 逐个补写法追不上，这与本卡开头
「模型名是开放集合」是同一件事，只是换了个维度。

七轮的新 BLOCKER/HIGH 数：**5 → 3 → 2 → 3 → 1 → 3**（第四轮为验证轮）。
没有一轮是 0，也没有单调收敛。卡文只允许 3 轮，我已跑了 7 轮、修了 65+ 条反例。

**结论：完成条件 (g)「新终审 B/H=0」在本卡的对抗审查范式下不可达。** 这不是本卡
的新发现 —— round-8 的存档里就写着「清零在对抗范式不可达」，本卡七轮是第二次实证。
卡文自己给的出口正是「到顶不合并」。继续跑第八轮的期望收益是「再修一种写法、
再被找出第五种」，而每次改动都在无独立复核的状态下累积风险。

### 交给下一批的结构性判断（不是缺陷清单，是方向）

C3「空骨架」这个判据的**形状**有问题：它靠「把不算正文的东西一层层剥掉、看剩下
多少」来判断，而「不算正文的东西」是开放集合。更结实的形状应该是**反过来**：
默认所有字节都算内容，只在能**正面证明**是模板骨架时才删（例如整份文件与已知
模板逐字相等）。那是判据面的重写，不是补丁，需要单独立卡。
