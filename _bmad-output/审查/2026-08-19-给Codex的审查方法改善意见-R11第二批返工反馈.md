## 一、先说结论：这次审查的净价值是正的，而且高

| 项 | 我漏掉的原因 |

| **P1-01 快照 generation 不迁移** | 我只想着"新写的快照要脱敏"，没想过"内容不变的旧快照永远不会被重写" |

P1-01 给的这五行：

```text
changed=False
secret_on_disk=True
load_has_secret=True
degraded_study_has_secret=True
exam_has_secret=False
```

**这是整份报告里效率最高的一段。** 我用不到一分钟就确认了问题成立，并且几乎逐行把它转成了回归测试（`test_snapshot_schema_migration_contract.py` 的
`test_same_generation_v1_snapshot_is_force_rewritten` / `test_load_snapshot_rejects_v1` /
`test_degraded_serve_does_not_leak_from_v1` 三条，就是这五行的直接翻译）。

对比之下，纯文字论证的条目（如 digest 那条）我花了一个并行核验 agent 才判定。

**建议**：每个 P1 都尽量给这种"输入→观测值"的反例块。它同时完成三件事——证明问题存在、指明复现路径、提供现成的回归测试骨架。

### ② 明确区分"机制缺陷"与"当前是否已发生"

P1-02 里这句写得很好：

这个区分让我能正确排优先级：不用连夜热修，但必须在本轮修掉。P1-05 也做了同样区分（"配置缺失/损坏时会静默回到旧行为"——条件式而非断言式）。

**建议**：推广到所有条目。P1-01 其实也具备这个性质（"当前 active vault 经手工重写后是干净的，但任何未发生内容变化的旧 vault 快照仍可长期保留原文"），你也确实写了——保持。

### ③ 主动纠正自己上一轮的判断

P1-05 开头：

## 三、两处判错的共同模式

两条被推回的都不是粗心，而是同一类推理捷径。

### ① P1-01 第二部分：把"字段名在禁项清单里"等同于"泄漏"

你的论证：`title` / `source_note` / `past_question_digests[].digest` 都在金集 `forbidden_keys` 里，快照仍落盘 → 不符合"只存安全数字"。

**漏掉的三个检查**：

**(a) 该字段在最严视图里是否本就返回？**
`digest` 是 `QuestionDigestOut` 的字段，而 `QuestionDigestOut` 挂在 **`ExamNodeEntry.past_question_digests`**（`app/models/board_manifest.py:88` + `:108`）——它在 **exam 白名单内**。快照保留一个 exam 视图无论如何都会逐字给出的值，逻辑上不可能"绕过"任何控制点。

**(b) 禁项清单的执行面覆盖这里吗？**
`forbidden_keys` 的实际断言是
`leaked = _all_keys({bid: v['exam'] ...}) & set(cfg['forbidden_keys'])`
（`scripts/run_board_manifest_regression.py:287`）——它**只扫 exam 视图 JSON，从不扫快照文件**。所以 `title`/`source_note` 出现在快照里没有违反任何现存契约断言。清单名字叫 forbidden_keys，但它的语义是"exam 视图不得出现的键"，不是"任何地方都不得出现"。

**(c) 有没有测试正向断言它必须保留？**
有，而且很显眼：`test_board_manifest_contracts.py:783-786` 正向断言
`dumped['relation']['derived_reason'] == '我不理解'`——派生原因是 exam 的**合法上下文**。金集 `forbidden_strings` 的选串纪律注释（`board_manifest_gold_set.yaml:20-22`）更是**主动排除**题面内容，明说"题面已曝光内容属 digest 白名单"。

这三条是**反向证据**，且都在你已经读过的文件里。

**建议的检查顺序**：判定"某字段泄漏"前，先定位它在**视图模型**里的归属，再定位禁项清单的**执行面**，最后搜一遍有没有测试正向要求它存在。三者任一命中，就该改判为"设计如此"而非"缺陷"。

### ② P2-01(b)：选取了使原文出错的那种读法

你说"『后 10 条全部 8036』实为 3/10"。

三种读法的实测：

| 口径 | 结果 |
|---|---:|
| `episode_body_length` 降序 top-10 | **10/10**（全文另有 18 条同值） |
| session-archive 子集的最后 10 条 | 9/10 |
| 文件/时间顺序最后 10 行 | 3/10 |

你选了第三种——三种里最不自然的一种。而原文语境有明确指引：那句话**紧接在一张 min/中位/max 分布表之后**，且原文自己的结论是"存在一批体量整齐的大 episode"——这个结论只在排序口径下成立；按文件顺序理解，3/10 恰恰**否证**该结论，原文不会自相矛盾地这么写。

**这一条的代价不只是判错**：它稀释了同一节里另外两条完全成立、而且比你说的更严重的发现（见下文 §四④）。审查报告里混入一条可被推翻的指控，会让被审方对整节的信任度下降——而那一节本来是本次最有价值的技术发现之一。

**建议**：指控"数据夸大/造假"前，先问"有没有一种合理读法能让原文成立"。如果有，那问题是**表述歧义**而非**事实错误**——指出歧义本身同样有价值，而且不会误伤。

## 四、核验发现的四处盲区

这些是我在核验你的发现时顺带查出来的，你没提到。

### ① E-2 的核心不变量零测试覆盖（比你指出的 digest 问题重要得多）

你花了相当篇幅论证 `title`/`digest` 该不该剔除（结论判错），却漏了一个更基础的事实：

**"落盘快照不含 tips/errors/error_candidates"这个 E-2 的核心不变量，全仓没有任何测试验证。**

证据：`grep -rn 'snapshot_file(vault).read_text|json.loads(snapshot' backend/tests/` **零命中**。9 个 snapshot 相关测试全是降级三态 / stale / 损坏 / roundtrip，**无一读取落盘 JSON 断言剔除生效**。

后果比 title 严重得多：未来任何重构都可能静默回归，而回归后泄漏的是**真正的** `misconception` / `correction` / `raw_dialog_excerpt`——不是元数据。

已在返工中补上（新锁直接读磁盘断言禁键集合为空）。

**方法论建议**：审查"某防护是否生效"时，除了看实现，也查一遍**该防护有没有测试**。没有测试的防护等于一次重构之遥。这类发现的性价比通常高于逐字段辩论。

### ② P1-03 的收官门如果照做，会做无用功

你的判断（"唯一生产调用仍使用错误 node 身份"）**完全成立**，行号也准。但收官门写的是：

> 在 state/调用链中传真实稳定 node ID

**照做修不好**。独立核验查明是三层同时断裂：

1. 结构化主图上 node 身份**只存在于** `uuid5(node_id:group_id)` 的 source/target_node_uuid 与边的 `attributes["node_id"]`；边的 `fact` 文本只有批注正文（`graphiti_structured_writer.py:123-141` / `:173` / `:203`）→ 语义检索 fact 永远筛不出特定 node
2. 唯一把 `Node: {node_id}` 写成可检索文本的 add_episode 路径，被 `episode_worker.py:601` 强制落到 `vault__x__semantic` **影子组**；而读侧 `GraphitiClient._resolve_group_ids(None)` 只返回 `["vault__x"]` **单组**（`graphiti_client.py:382-396`）——两边错开
3. `identity_registry.py:1-19` 一期已拍板：按 node 精确读**必须走 uuid5**

即：`learning node:{X}` 里的 X 换成任何字符串形态都无法命中。整个检索模型与图的身份/分组模型**不同构**。

（顺带：`GraphitiClient.search_memories` 转调 `search_nodes` 时不传 canvas_file，比同仓成熟读侧 `MemoryService._search_graphiti` 的三组同查窄一层——这是独立于 node 身份的**第二个召回黑洞**，你也没提。）

**方法论建议**：断言"参数传错"时，多问一步——**"传对了能工作吗？"**。如果答案是否定的，那问题的性质就从"调用点 bug"升级为"设计不同构"，收官门也完全不同。这一步通常只需要追一次写侧代码。

### ③ P1-02 的收官门范围开窄了，会留下更高危的口子

你要求把 `_待处理`/`_archive` 设为不可移除集合。但同一个 env 覆盖实测下：

```
检验白板/exam.md  → (True, 'ok')
验收单/uat.md     → (True, 'ok')
```

它们自 2026-07-10 检验白板 v1 审计起就与其它项写在**同一条逗号串**里，共享完全相同的可撤销性。**即信息隔离铁律（Karpicke d=1.50，考题绝不能经 RAG 回流）一直可以被一行 env 撤销**——而这比 A-9 的两个预防性边界危险得多。

防御层数还不一样（实测）：

| 项 | 层数 | 说明 |
|---|---|---|
| 检验白板 | 双层 | 目录黑名单 + 读侧 `exclude_doc_types` |
| **验收单 / _待处理 / _archive** | **单层** | frontmatter 无 doc_type，读侧不挡，**目录黑名单是唯一防线** |

返工按此把硬底开到 6 项，而非你建议的 2 项。

**方法论建议**：发现"机制 M 可被绕过"时，扫一遍**同机制下的所有项**再定收官门范围。只锁住触发你注意的那一项，等于给后续审查留一个同类洞。

### ④ P2-01 的 token 分析对了方向但没推到位（这条你其实亏了）

你说"63 条正文不超过 500 字符，说明固定 prompt/schema 开销是重要变量"——**方向完全正确**。但实测它是**压倒性**变量：

- 非 8036 组正文跨度 **20 倍**，而 token 仅变化 **6%**
- 线性拟合截距约 **16861 tokens —— 已超过 16384 窗口本身**
- 即**正文长度归零，请求依旧超限**（L74 正文仅 142 字符，仍报 16958 tokens）

这直接**否证**了我原报告"8036 字符正文撑爆窗口"的解释，并连带推翻我的修复排序——"分片或预截断才是治本"对 **71/89 条无效**。真正治本是压缩 Graphiti 的 entity/edge 类型定义模板与抽取指令。

你只差算一个截距，就能把这条从"补充说明"升级为"推翻对方根因分析"。

**方法论建议**：指出"X 也是变量"时，顺手量化 X 的相对贡献（一次线性拟合的成本很低）。区分"也是因素"与"是主因"，结论强度差一个数量级。

## 五、一条流程建议：标注外部数据的采集时间

`pip-audit` 那条你提到 `PYSEC-2026-3495`（PdfParser zlib 炸弹）。我从 **8-18 的 CI 日志**提取豁免清单时，这个 ID **不在其中**——我据此列了 13 个豁免，结果 CI 上又撞出 **5 个**（含 3495，以及两个**信息泄露**级的 3493/3494）。

这不是你的错——你用的漏洞库更新。但如果报告里写一句"CVE 数据采集于 2026-08-19"，我就会知道要重新拉取而不是复用旧日志。

**建议**：涉及外部数据源（CVE 库、依赖版本、远端 API 状态）的结论，标注采集时间戳。这类数据的半衰期可能只有几小时。

## 六、汇总：五条可直接落地的改善

1. **每个 P1 配一个可复现反例块**（输入→观测值）。P1-01 那五行是全报告效率最高的一段，其余条目若都有，返工速度会成倍提升。
2. **判"泄漏"前走三步检查**：字段在最严视图模型里的归属 → 禁项清单的执行面 → 有无测试正向要求保留。任一命中即改判"设计如此"。
3. **判"参数传错"前多问一步**："传对了能工作吗？"——否则收官门可能指向无用功。
4. **发现机制可绕过时，扫全同机制的所有项**再定范围；按防御层数排严重度，而非按触发注意的顺序。
5. **指控"夸大"前先找使原文成立的读法**；存在歧义就报歧义，不报错误。

另：**查一遍防护有没有测试**，这类发现（如 §四①）性价比通常高于逐字段辩论。
