## 0. 这一轮在修什么

第十批集成树的门在 `tests/regression` 目录级跑里抓到的**第二个主干既有偷连**
（第一个是 `test_story_38_3`）。根因一行：

```
测试 patch 的是 svc.search_memories（memory_service.py:2450）—— 那是**兼容壳**，
它自己反过来委托 search_memories_with_status。
而被测路径 search_error_memories → search_error_memories_with_status(:2477)
在 :2496 **直接**调 self.search_memories_with_status —— 压根不经过那层壳。
⇒ patch 落在一条没人走的路上，真实链路一路走到底：
   :2496 → :2319 initialize() → :278 self.neo4j.initialize()
        → neo4j_client.py:402 health_check() → verify_connectivity() → bolt 7691
```

连接异常被 `health_check` 吞成 "Falling back to JSON storage mode"，
**在这道门存在之前，用例照样绿** —— 所以它一直在偷连正式库而没人发现。

### 2.3 防回归断言与门的分工（(d)）

`mock_search.assert_awaited_once()` 与门是**两层**，不能互相替代：

- **门（结账哨兵）**只在真的发生了连接尝试时才说话 —— 它管**后果**；
- **本断言**管**原因**：patch 有没有打在被测路径上。目标一旦被改回兼容壳，
  它当场报 `Expected to have been awaited once. Awaited 0 times.`，直接指向根因；
  而门那边给出的是一条 health_check 警告，要顺着链路读半天。

⚠️ **别把「删掉断言会不会红」当它的价值判据**：实测只删断言仍
`4 passed` + `blocked=0`（链路没变）。它防的是**下一个人把 patch 目标改回去**。

## 4. 诚实边界

### 4.1 这一改动不比什么

- 它只修**这一个文件**。同型问题（patch 打在兼容壳上）在别处有没有，本卡未做全仓扫描。
- 它证明的是「这四条用例不再连 7691」，不是「`search_error_memories` 的实现是对的」——
  四条用例的断言语义一字未改，覆盖面也就没变。

### 4.2 本卡未证明什么

1. **没做全仓同型扫描**：`search_memories` / `search_memories_with_status` 这一对
   「兼容壳 + 状态方法」在 `memory_service.py` 里不止一处（`search_error_memories`
   自己就是同样的结构）。别的测试有没有 patch 错壳，**未验证**。
2. **没碰 `app/services/memory_service.py`**（卡文硬边界）。`:2450` 那层兼容壳继续
   存在，下一个人照样可能 patch 它。真正的收口是让壳与状态方法**不可能被搞混**，
   那是另一张卡的范围。
3. **单例污染只在本文件断绝**：`MemoryService()` 不传 `neo4j_client` 就抓进程单例 ——
   这个默认行为没变，别的测试文件仍可能污染它。
4. **反证只覆盖「改回旧写法」这一种回归**。别的回归形态（例如有人把 `_call` 拆开、
   或直接在用例里 new 一个 `MemoryService()`）不在反证射程内。
5. **未送 Codex**（卡文 (h) 的默认档，反证成立）。所以本卡的改动**没有独立复核**。
6. **`neo4j_memory.json` 只做了「不再新写」的验证，没有清理**（§2.8）。它是开工基线跑
   留下的空壳，本卡未删除（破坏性操作、未获授权）。若主 session 要求恢复到开工态，
   删掉它即可 —— 它 git-ignored、内容为空。
7. **本卡是靠人工目录对账才发现那次写入的**，不是靠门。监视清单不含它 ⇒
   同型的运行时写入在别处发生时，同样没有门会说话（T-15）。
