### 2.1 判据从黑名单改成正面白名单

新增常量（`live_port_guard.py`）：

```python
ALLOWED_TEST_PORTS = frozenset({7692})
_DRIVER_DEFAULT_PORT = 7687
_DRIVER_DEFAULT_HOST = "localhost"
```

`assert_test_uri_not_blocked()` 现在**显式三分**，没有"其余情况"这种灰地带：

| 情形 | 处置 |
|---|---|
| 没配 `NEO4J_TEST_URI` | 射程外，返回 |
| 驱动口径解析不出 int 端口 | **拒**（fail-closed） |
| canonical 端口 ∈ `ALLOWED_TEST_PORTS` | 放行 |
| 其余一切 | **拒** |

⛔ **黑名单一侧一字未动**，理由写进了常量注释（两处语义不同，不能统一）：

- `BLOCKED_PORTS` 管的是 `_audit_hook` 里**每一次** `socket.connect`。那里改白名单会把
  测试进程的出站流量一并拦死 —— 仓内至少 Ollama `localhost:11434`（`app/config.py:531`）、
  `tests/contract/test_pact_provider.py`、`tests/unit/test_embedder_factory.py` 会连
  非 7692 的本地端口，探针自己还会临时往受拦集合里加端口；
- 黑名单常量还是 `audit_hook_alive(:547)` / `assert_guard_live(:572)` 的**自证锚点**，
  取值一动，门就从 fail-closed 变恒真。

白名单适用的是另一件事：`NEO4J_TEST_URI` 这个**配置值**只有一个正确答案，
所以「默认拒绝 + 列出唯一允许项」才对。黑名单要挡住 `:0`，就得枚举 `0`、`00`、空、
以及一切会被驱动归一成 7687 的写法 —— 那是必输的方向。

### 2.2 canonical port 按**驱动自己的**解析链复算

驱动的真实链路（2026-09-05 于本车道 venv 内实读 + 实跑）：

1. `neo4j/_api.py::parse_neo4j_uri` → `urlparse(uri)`；
   `parsed.username` / `parsed.password` 非空**直接** `ConfigurationError`（驱动不接受 userinfo）；
2. 同处校验 scheme 白名单，其它 scheme `ConfigurationError`；
3. `_sync/driver.py:276` 把 **`parsed.netloc`** 交给 `_Direct._parse_target`
   → `Address.parse(netloc, default_host='localhost', default_port=7687)`；
   **但 `neo4j*` 走的是 routing 分支** → `_Routing._parse_targets`
   → `Address.parse_list(netloc, …)`，后者**按空白拆分多个地址**。

`canonical_target_ports()` 走的是**同一条**，并按 scheme 分流到对应入口，
参数与 `_sync/driver.py:446-452` / `:470-479` 一字不差。

⛔ **刻意不自己切字符串**：直接把 tail 喂给 `Address.parse` 得到的东西与驱动的真实行为
（在第 1 步就 `ConfigurationError`）是两回事 ——「看起来也拒了」的巧合不能当判据，
它在别的输入上就会分叉。这正是旧判据栽跟头的原因：`_port_of_uri` 是**另一个解析器**
（本卡已把它**删除**，见 §5.6）。

⛔ **direct/routing 分流是 round-1 打回后才有的**（见 §5.3）：第一版对所有 scheme
统一用 `Address.parse`，于是 `neo4j://127.0.0.1 :7692` 被算成 7692 而放行，
而驱动实际连 `127.0.0.1:7687`。

实测（`neo4j.Address.parse(default_port=7687)`）：

| URI | canonical port |
|---|---|
| `bolt://127.0.0.1:0` | **7687** |
| `bolt://127.0.0.1:00` | **7687** |
| `bolt://[::1]:0` | **7687** |
| `bolt://127.0.0.1`（无端口） | **7687** |
| `neo4j://host` | **7687** |
| `bolt://127.0.0.1:7692` | 7692 |

**延迟 import 的合法性**：本模块刻意不在模块层 import 任何重物（装门必须早于业务
import，`tests/conftest.py:28`）；而预检只在 **session fixture**（`conftest.py:106`）
里跑，那时 neo4j 早已可 import。所以 import 写在**函数体内**合法，模块层新增则禁止 ——
裁判 6 会数（实测 **0**）。

### 2.4 tuple 子类：端口从**底层槽位**读（X4 §7.10 A 类 HIGH #2，本卡两次修才对）

`len()` 与 `[1]` 走的是可重载的 `__len__` / `__getitem__`，而 CPython 的 socket 读**底层槽位**
—— 覆写 `__getitem__`（对 guard 报端口 1、对 C 层仍是 7691）就能让门判安全而连接照常建立。

⚠️ **第一版修法「tuple 子类一律不可信」被 round-1 打回，它误拦真流量**（详见 §5.4）：
neo4j 驱动的 `Address` 家族就是 tuple 子类且直接被 `s.connect()` 使用。
当时的注释还写着「Python 层读不到 C 层看见的那个值」—— 这句也是错的，
`tuple.__getitem__(addr, 1)` 就读得到，**我自己的测试里就在用它**。

正解：`extract_port` / `port_is_trustworthy` 都用 `tuple.__len__` / `tuple.__getitem__`
绕开重载读槽位 —— 伪装骗不过，真驱动地址也不误伤。

五条测试：覆写 `__getitem__` 的子类被读出真实 7691 / 覆写 `__len__` 同理 /
**真驱动地址 `IPv4Address(7692)` 必须放行**（round-1 反例）/ 同类型 7691 仍拦 /
对照：普通 tuple + 11434 不拦。

另有 `TestSelftestAddressClassification` 六条，钉住 round-2 HIGH-1（自证分类的两种伪装
必须**不**被当成自证；真自证地址仍能走进拦截分支）。

## 4. 诚实边界

### 4.1 这道门不比什么

- 门**只按端口判定**。射程之外的库（别的主机、别的端口上的 Neo4j）它拦不住 ——
  负控用 `W4_GUARD_REQUIRE_BLOCKED_TARGET=1` 单独收这一面。
- `is_exempt()` 对 `tests/integration` / `tests/e2e` **只记不拦**是**有意的旁路**。
  本卡堵的是「配置误写成 0 让 advisory 用例连上现网」这条，**旁路本身仍在**。
- 白名单只管 `NEO4J_TEST_URI` 这一个配置值，不管 `NEO4J_URI`（那是另一条判据）。
- ⚠️ **routing 模式下 canonical 端口只是「第一跳」**（本 session 自查发现，如实登记）：
  `neo4j://` / `neo4j+s://` 的驱动会先连 URI 里那个地址要**路由表**，之后按服务器
  返回的地址连后续连接。所以本预检证明的是「**初始**连接的目标端口是 7692」，
  不是「这个驱动此后只会连 7692」。兜底仍在 —— `_audit_hook` 对**每一次**
  `socket.connect` 都按黑名单判，路由表把它引到 7691/7687 时照样拦。
  也就是说：预检管配置，hook 管流量，两层各管一段，缺一不可。

### 4.2 本卡未证明什么

1. **W4-④（最终结算原子性）没修** —— `os._exit(3)` 前的 `repr`/`print`/IO 可能抛、
   `_FINALIZING` 检查 / `record()` / ledger 快照三者未同锁线性化。卡文明确另立卡。
2. **B 类 AST 门的 5 条 HIGH 没修**，**C 类 `BASH_ENV` 一节没修** —— 均另立卡。
3. **`EXEMPT_MARKERS` / `EXEMPT_PATH_PREFIXES` 的覆盖面没动**（放宽/收紧另裁）。
   所以「新写的测试只要放进 `tests/integration/` 就自动免拦」这条**仍然成立**。
4. **没有起真 Neo4j 验证端到端**。canonical 端口的正确性证据是「读驱动源码 + 用驱动
   自己的 `Address.parse` 实算」，不是「真连一次看它去了哪」。
5. **tuple 子类的修复覆盖 `extract_port` / `port_is_trustworthy` / `_is_selftest_address`
   三处**（第三处是 round-2 打回后补的）。若别处还有读取 socket 地址的代码，未逐一排查。
6. **驱动版本绑定**：`_DRIVER_DEFAULT_PORT = 7687` 是从**本机 venv 里这一版** neo4j
   （6.1.0）读出来的。驱动升级后若改了默认端口，这个常量不会自动跟着走（契约测试会红，
   但那是事后发现）。scheme 集合已改成从 `neo4j.api` 的公开常量取，不受此限。
7. ⛔ **round-2 HIGH-2（advisory 窗口）未修** —— `begin_item(exempt=True)` 早于 session
   fixture 的 URI 预检，存在「advisory 已生效、URI 尚未校验」的窗口。卡文硬边界
   **禁改 `tests/conftest.py` 装门时机**，故只登记移交（T-10）。复核自己也写明
   「六文件内没有确认到这样的消费者，因此不升级为已确认 BLOCKER」。
8. ⛔ **两轮复核之后的整改本身未再经独立复核。** BLOCKER（direct/routing 分流）、
   HIGH（读底层槽位）、HIGH（自证分类）、两条 MEDIUM 与一条 LOW 的修法，证据只有
   我自己跑的六项裁判 + 契约测试里的反例。**「修完了」不等于「修对了」** ——
   本卡自己就出过两次：`tuple 子类一律拒绝`（误拦真流量）与

### 5.3 BLOCKER 整改：direct / routing 分流

驱动对 `neo4j[+s|+ssc]` 走 `_Routing._parse_targets` → `Address.parse_list`，
后者**按空白把 netloc 拆成多个地址**。实测（本机 neo4j 6.1.0）：

| URI | 修前判据 | `parse_list` 实际 | 驱动取 `[0]` |
|---|---|---|---|
| `neo4j://127.0.0.1 :7692` | **放行**（算 7692） | `[('127.0.0.1', 7687), ('localhost', 7692)]` | **7687** ⛔ |
| `neo4j://[::1]:7691 [::1]:7692` | **放行**（算 7692） | `[('::1', 7691), ('::1', 7692)]` | **7691** ⛔ |
| `neo4j://127.0.0.1:7692 localhost:7692` | **误拒** | `[('127.0.0.1', 7692), ('localhost', 7692)]` | 7692（合法） |

修法：按 scheme 分流到对应入口，返回**全部**初始候选端口，判据要求**每一个**都在白名单
（只看 `[0]` 会漏掉 `neo4j://ok:7692 evil:7691`）。函数随之改名
`canonical_target_port` → `canonical_target_ports`。修后三条陷阱全拒、误拒那条放行。

### 5.4 HIGH 整改：端口从**底层槽位**读，而不是拒绝子类

我第一版的修法「tuple 子类一律不可信」有两个错：

1. **误拦真流量** —— `neo4j._addressing.Address`（`IPv4Address` / `ResolvedIPv4Address` …）
   就是 tuple 子类，`_bolt_socket.py` 直接 `s.connect(resolved_address)`。实测
   `Address.parse('127.0.0.1:7692')` 经本 hook 抛 `RuntimeError` ⇒ **合法容器连接被门拦死**。
2. **注释是错的** —— 我写「Python 层读不到 C 层看见的那个值」，而
   `tuple.__getitem__(addr, 1)` 就读得到；**我自己的测试里就用了这一行**。
   典型的「声明比证据宽」。

正解：`tuple.__len__` / `tuple.__getitem__` 绕开重载读槽位 —— 伪装子类骗不过，
真驱动地址也不误伤。实测：`IPv4Address(7692)` 放行、`IPv4Address(7691)` 拦截、
覆写 `__getitem__` 谎报端口 1 的子类被读出真实的 7691。

### 5.5 round-2 HIGH-1 整改：自证分类绑定合成身份

`_is_selftest_address` 决定「拦截要不要记账」，所以必须比端口判据更严。
三道钉死：`type(address) is tuple`（不认子类）、`tuple.__getitem__` 读槽位（不走重载）、
`type(host) is str`（不认 `str` 子类的 `__eq__`）。两种伪装各配一条反例测试。

### 5.6 round-2 MEDIUM 整改：删掉第二个解析器

`assert_neo4j_target_blocked` 改用同一个 `canonical_target_ports`，并**删除**
`_port_of_uri` 本体（不是留着不用）。它身上已攒了两条实证缺陷（`:0` → 0；
query/fragment 里的数字被当端口），而生产调用已归零 ——
留着一个零调用、已知有缺陷、名字又像"正经解析器"的函数，只会让下一个人再捡起来用。

实测修前/修后：

| URI | 旧解析器 | 驱动口径 | 新判据 |
|---|---|---|---|
| `bolt://127.0.0.1:11434#tag:7687` | 7687（假通过） | 11434 | 拒绝装门 ✅ |
| `bolt://127.0.0.1:7692?x=:7691` | 7691（假通过） | 7692 | 拒绝装门 ✅ |
| `bolt://127.0.0.1:7691` | 7691 | 7691 | 放行 ✅ |
