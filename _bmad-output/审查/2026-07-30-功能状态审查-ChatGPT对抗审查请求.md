    全系统功能状态审查做**独立对抗性复核**。你不信任 Claude 的结论，逐条用附件里的

  </role>

  <goal>

    你的价值在于推翻或修正，不在于复述认同。
  </goal>

  <environment>
    - 单用户桌面学习系统，架构已从 Tauri+React 转向 "Obsidian Hybrid"：
      用户在 Obsidian vault 里学习，Claude Code skills（8 个 SKILL.md）驱动学习流，

      每日复习 Bark 手机推送（launchd + 纯 stdlib 脚本）。
    - 附件结构（42 文件）：
      00-审查产物/ = 被审对象：三分类报告 + 82 条原始结论 JSON（含每条的证据 file:line 与对抗验证 verdict）
      01-锚点账本/ = CURRENT_TASK、项目 CLAUDE.md、known-gotchas（20 坑）、mvp-plan（14 项+用户批注）、6 张关键验收单

    - 注意：包已脱敏，[REDACTED:xxx] 是占位符；少数是误伤（如 Python 的 key=lambda、key: str 参数），

  </environment>

    - usable 29 条（已可用：代码接通 + 用户 UAT 打勾或有真实使用数据）
    - needs_uat 17 条（技术就绪但用户本人未上手验证）
    - broken 25 条（断裂/假实现/僵尸/废弃）
    - not_built 11 条（有决策计划但代码不存在）
    审查方法：6 维度并行盘点 → 5 批怀疑者逐条对抗验证（0 条被推翻、3 条被改判）→ 完整性检查。
    核心发现（详见 00-审查产物/三分类报告）：
    - MEM-0 自动化静默死亡：5 个 launchd job 全部 exit 126/78（TCC 拦截），验收后从未成功跑过
    - 4 个「用户以为能用其实不能」陷阱（Cmd+Shift+Q 假评分 / 11 个学习法命令指旧 Windows C:/ 路径 /
      旧考察文件退役指引残留 / deploy-vault 错端口）
    - Tier B 退役清单五项僵尸全部存活，MCP mastery 工具是危险暴露面

    已知方法局限（诚实申报，请针对性攻击）：
    a) 对抗验证「0 条被推翻」可能说明怀疑者不够狠，也可能盘点与验证共享了相同盲区

    c) 完整性批评家 agent 反复 stall，最后由主 session 手动完成，深度不如其他阶段
    d) 「usable」高度依赖验收单勾选痕迹，而审查同时发现验收单会撒谎（MEM-0 勾了但死了）——
       这个标准的自洽性值得攻击

  </problem>

  <already_tried_and_concluded>

      但你可以检查 82 条 JSON 里是否有哪条的证据路径其实指向了陈旧副本
  </already_tried_and_concluded>

  <key_files>
    附件：feature-audit-review_pack_2026-07-30.md（repomix 打包，markdown 格式，已脱敏，42 文件）

  <research_questions>
    Q1【分类挑错】82 条结论逐类抽查：
       - usable 里有没有像 MEM-0 那样「勾了但实际已死」的漏网者？重点攻击依赖后台服务/定时任务的条目。
       - broken/not_built 里有没有其实活着/已实现的误判？用 router.py、main.ts、SKILL.md 反向核对。
       - needs_uat 的 17 条里，有没有技术上根本没 ready、应降级 broken 的？

       「0 条被推翻」在统计上意味着什么？给出改进这类 AI 自审的具体方法建议。
    Q4【优先级裁决】报告建议的行动顺序（先 FDA 授权救 launchd → 四技能 UAT → 跨天验证 →
       三个拍板 → 顺手修）是否最优？从「单用户学习系统的实际风险」视角重排，
       并对 Tier B 僵尸退役 vs 继续新功能给出明确裁决建议。
  </research_questions>

  <case_requirements>
    仅当你提出新的架构级风险判断或修复方案时需要外部证据：每个关键主张附 1-3 个成熟案例/文献，
    字段：url_primary / accessed_date / info_type(fact|opinion|benchmark) / tier(T1官方|T2权威|T3社区) /
    与本系统的 fit 说明。审查性结论（对着附件源码就能验证的）不需要外部案例，直接引用附件 file:line。
  </case_requirements>

  <deliverable>
    输出四段，对应 Q1-Q4：
    1. 分类修正表：| 条目 | 原分类 | 你的判定 | 证据(附件 file:line) | —— 只列你不同意的，全同意就明说
    2. 遗漏清单：漏掉的功能/子系统，每条带证据和建议分类

  </deliverable>

</review_request>
