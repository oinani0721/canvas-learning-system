# ⛔ 现网复习链停摆（2026-09-05 实测）

> 在做乙案设计时由 workflow 勘探面发现，主 session 逐条独立复现。
> **这不是设计问题，是线上事故：用户的复习页今天没有更新过。**
> 全部为只读观测；未修改任何文件、未碰 live vault。

## 一 现象

| 观测 | 值 |
|---|---|
| `launchctl list \| grep canvas` | `-  78  com.canvas.daily-review`（**78 = 失败**，其余 4 个服务均 0） |
| live 投影 `generated_at` | **2026-09-04T09:05:05+08:00** |
| live 投影文件 mtime | **2026-09-04 09:05:05** |
| 复习链最后一次成功 | `backups/daily-review.log` → **2026-09-04 20:05:05** |
| 今天（2026-09-05）已跑档次 | 09:05、10:05 —— **两档都 PREFLIGHT-FAIL** |

`~/Library/Logs/canvas-daily-review.boot.log`：

```
[2026-09-05 09:05:04] PREFLIGHT-FAIL: fsrs_bridge.py_version_skew (canvas-vault) — worktree 与活 vault 副本不一致, 需 cp 部署
[2026-09-05 10:05:04] PREFLIGHT-FAIL: fsrs_bridge.py_version_skew (canvas-vault) — worktree 与活 vault 副本不一致, 需 cp 部署
```

## 二 根因（精确到唯一一个文件）

`scripts/launchd/daily-review-wrapper.sh:98-106` 有一道**双副本一致性门**
（Code-Review M4 + FSRS-V2 H1）：逐字节 `cmp` 开发树与活 vault 里的
`decay_beta.py` 与 `fsrs_bridge.py`，不一致就 `continue` 跳过整档、退出码 78。
它的存在理由正是「worktree 改了忘 cp 会造成静默行为漂移」——**门是对的，它抓到了真问题**。

比较对（wrapper 的 `WT` = `feature-obsidian-hybrid-dev`，:17）：

| 文件 | 开发树 | 活 vault | 一致 |
|---|---|---|---|
| `decay_beta.py` | `3bf4ed94…` | `3bf4ed94…` | ✅ |
| **`fsrs_bridge.py`** | `80679678…` | `66a75527…` | ❌ **漂移** |

部署版 wrapper（`~/Library/Application Support/CanvasReview/bin/`）与仓库版 sha 相同
（`d78d16be…`）⇒ **wrapper 本身没问题，漂移只有 `fsrs_bridge.py` 一个文件**。

漂移内容：**166 行差异**，活 vault 版停在 `Aug 27 05:37`；开发树版含 CARD-G3-2 的
**时刻契约修复**（统一 UTC / naive 时刻拒收 / 整秒对齐），随第十批 X7-A `e85d4ade` 合入。

时间线自洽：09-04 20:05 仍成功 → X7-A 合入 → 09-05 09:05 起 skew 失败。

## 三 为什么本车道不能自己修

修法是把开发树的 `fsrs_bridge.py` **cp 到 live vault**。这一步撞三条边界：

1. **本车道所有卡的硬边界都写着「live vault 只读」**；
2. `fsrs_bridge.py` 是 **Z2 面**（`CARD-G3-3` 正在改这个文件）；
3. **Z2 卡文 §三 明写「禁把改动 cp 部署到 live vault（G8-7 冻结）」**。

⇒ 需要主 session / 用户裁决。

## 四 对乙案的意义

**先修这个，比先写乙案的代码重要。**

乙案（无论哪条路线）都是「让投影及时重建」。但现在的状况是
**投影一次都建不出来**——链在更上游就死了。不修的话：

- 乙案做完，线上仍然不更新（唯一裁判根本没在跑）；
- 而且任何端到端验收都会被污染：「卡片出现了」可能来自乙案新加的重建路径，
  而不是被验证的那条机制——归因不成立。

## 五 建议处置顺序

1. **先修部署漂移**（cp 一个文件 + 重跑一档验证 `launchctl list` 归零）——需授权；
2. 修完后**先观察一天**：定时链恢复后，白天 12 档、每档间隔 1 小时，
   看「答错的卡多久出现」的真实基线是多少；
3. 再决定乙案要不要做、做哪条路线——因为基线变了之后，
   收益（把 ≤1 小时压到 ≤5 秒）值不值那些风险，判断依据也变了。
