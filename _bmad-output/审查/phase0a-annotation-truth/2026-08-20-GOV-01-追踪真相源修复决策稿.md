### 2.3 Stop 链当前具有越权写入风险

`.claude/settings.json:55-98` 的文本排列是：

```text
stop-test
→ stop-auto-sync-to-remote
→ decision-router
→ annotation scanner
→ sync_links
→ story file map
→ update-current-task
```

这个排列**不是执行顺序保证**。Claude Code 官方说明，同一事件命中的 Hook 会并行运行，完成顺序不确定，一个 Hook 的 deny 也不会阻止 sibling 已经产生副作用；直接编辑 settings 通常会被 watcher 热加载，但 watcher 可能漏掉，届时必须重启 session（[Claude Code Hooks 官方文档](https://code.claude.com/docs/en/hooks-guide)）。因此 auto-sync、decision router、scanner 和 updater 之间存在竞态，不能用“先校验再提交”或“先提交再更新”任一假设证明安全。`stop-auto-sync-to-remote.sh:105-153` 会：

- `git add -A` 整个工作树；
- 只排除两个特定目录；
- 生成不含当前精确 Plan ID 的自动 commit；
- 触发 post-commit 远端推送，并额外推送 `wip/auto-sync`。

若 updater 较晚完成，它会给下一次 Stop 留下新脏文件；若较早完成，它可能在同一轮被 auto-sync 一并吸收。两种 interleaving 都会形成不可控提交或循环。2026-08-20 本次只读快照在新增本决策稿之前已有 10 个 tracked 变化和 71 个 untracked 路径；它们均先视为用户资产，不能被 `git add -A` 自动吸收。

此外，`scan_feedback.py --mode=batch-silent` 会向 `docs/_meta/annotations/` 写带当前时间的 YAML；`sync_links.py`、story map 和 updater 也属于生成/写入动作。Stop 阶段不能继续混合“结束响应”和“修改仓库”。

## 3. 三个方案

| 方案 | 做法 | 优点 | 主要缺陷 | 裁定 |
|---|---|---|---|---|
| **A. 根文件唯一 canonical** | 根 `CURRENT_TASK.md` 加严格 frontmatter；所有 reader/writer 原子迁根；旧路径只留弃用指针 | 对齐实际维护历史；最少概念；容易证明单一真相 | 需要一次治理 bootstrap 和完整 Hook fixture | **推荐** |
| B. `_decisions` 唯一 canonical | 把根文件内容迁回 `_decisions`，根文件改生成镜像 | 旧 Hook 改动较少 | 人工长期维护根文件；仍需镜像/生成，容易再次漂移 | 不推荐 |
| C. 新建 state JSON，两份 Markdown 都生成 | 结构化状态为源，两个 Markdown 均为 projection | 长期架构最规整 | 迁移面最大；在 Phase 0A 前引入第三真相，bootstrap 风险过高 | 暂不采用 |

不接受 symlink、双写或“两个文件都可编辑”：它们没有消除第二真相源，只把漂移换了形式。

## 4. 推荐方案 A 的冻结设计

### 4.1 唯一任务状态

根 `CURRENT_TASK.md` 是唯一 canonical。最小 strict frontmatter 至少包含：

```yaml
schema_version: cls-current-task-v2
program_plan_id: PLAN-CLS-PRODUCTIVITY-2026-08-20
program_plan_path: _bmad-output/审查/2026-08-20-Canvas-Learning-System-生产力化长期Goal计划书.md
active_change_id: repair-agent-governance-v2
active_change_path: openspec/changes/repair-agent-governance-v2
execution_mode: governance-bootstrap
phase: GOV-01-BOOTSTRAP
server_enforcement_state: pending
state_revision: 1
base_head: 019443469f198286b9b40b2eb54c15c366f3e123
next_action: apply-governance-bootstrap
approval_receipt_id: pending-user-confirmation
updated_at: 2026-08-20T00:00:00Z
```

上例只冻结字段和语义，不是当前可写值；真实 `state_revision/base_head/updated_at/approval_receipt_id` 必须在用户批准后的 OpenSpec apply 中由验收脚本生成或验证。

约束：

1. `program_plan_path` 与非空的 `active_change_path` 必须是 repo-relative、已跟踪、存在的文件或目录；不得含私人绝对路径。
2. `program_plan_id` 必须与长期 Goal 声明一致；`active_change_id` 必须与当前 OpenSpec change 一致。二者不得再压缩成一个含义不清的 `active_plan_id`。
3. `state_revision` 单调递增；写入使用 expected-revision CAS。旧 revision 写者必须失败。
4. 同一输入重跑必须 byte-identical；禁止每次 Stop 用 `now()` 制造无意义 delta。
5. 仅一个 tracked resolver 决定 Git 根与 canonical path；所有命令禁止各自硬编码。
6. 从仓库根、子目录和 `_bmad-output` 调用时必须得到同一文件。
7. `server_enforcement_state` 固定为 `pending/verified`；没有实际远端 required-check receipt 时只能是 `pending`，不得把本地 workflow 检查写成 server-side 硬门。`pending` 可用于完成本机 Agent 治理 bootstrap，但会继续阻断 OBJ-07 和最终发布门。

旧 `_decisions/CURRENT_TASK.md` 已是 tracked Git blob；迁移只记录它当前可达的 Git blob OID 与最后提交，不把含本机路径的原始 bytes 复制到新的公开证据文件。原路径随后只留无 YAML frontmatter 的 `DEPRECATED` 指针。任何程序继续读取或写入旧路径，必须由同一个 shared governance checker 在本地 Hook、lefthook 和 CI 三个入口拒绝；在 checker、workflow 与 required-check 证据全部落地前，不得声称已有 server-side 硬门。

### 4.2 Stop 变成只读边界

Stop 默认只允许：

- 读取状态并给出诊断；
- 对本轮明确变更运行只读/临时目录测试；
- 检查 Plan、OpenSpec、规则引用和 pending receipt；
- 输出下一步建议。

Stop 禁止：

- `git add`、commit、push、force-with-lease；
- 改写 `CURRENT_TASK` 或任何计划文件；
- scanner、link sync、story map 等落盘生成；
- Graphiti 或其他网络写；
- 把 fail-open 解释成 pass。

备份/提交改为用户显式触发的 checkpoint：先 dry-run，显示路径 allowlist、排除的 pre-existing dirty 项，以及精确 `program_plan_id/active_change_id`，经用户授权后才可提交。`git add -A` 永久不作为 Agent 自动 checkpoint 的实现。

### 4.3 规则与 Hook 必须可分发

1. 在现有引用路径重建并跟踪 `.claude/rules/development-discipline.md` 与 `.claude/rules/plan-traceability.md`，内容版本标为 v2；历史 Git blob 和本机草稿只作为有来源标注的输入。
2. 规则正文逐条声明：规范、可执行门、失败语义、fixture 和 waiver authority；不能再把不存在的 Hook 写成硬门。
3. `.gitignore` 只 allowlist 经审计的目标文件；clean clone 不依赖 `~/.claude`、父目录规则或 `settings.local.json`。
4. tracked settings 引用的每个脚本/规则都必须 tracked、存在、可执行并有内容 hash；settings 中不得再直接调用 PATH 上的裸 `node`，只能调用经测试的 tracked runner。
5. Node 版本选择在 governance OpenSpec 中依据官方支持矩阵锁定为一个可复现值；`.nvmrc` 必须只含合法 resolver token，非交互环境也须使用同一 runtime。
6. 每个 JavaScript Hook 先过语法门，再跑正例、反例、runtime-missing 和 malformed-payload fixture。
7. Claude Hook 与 Codex enforcement channel 分开记录：Claude 由 tracked Hook runner 执行；Codex 不得假装自动继承 Claude Hook，必须在写入/提交前显式运行同一 governance checker。二者共享同一规则和 canonical task，不建立第二套规范。

运行时缺失时：写入门必须 fail-closed 并给出可操作诊断；Stop 的安全回退是“不写任何状态”，不能静默继续外部写入。

### 4.4 Commit 追踪必须匹配当前计划

推荐规则：

- governance bootstrap commit 必须包含精确 `PLAN-CLS-PRODUCTIVITY-2026-08-20`；
- Phase 0G 治理实施还必须包含精确 `@spec:repair-agent-governance-v2`；后续 Execute Mode commit 必须包含 canonical `program_plan_id` 和对应 `active_change_id`/FR/Story 追踪；
- `Co-Authored-By` 只是作者 trailer，绝不是追踪 waiver；
- 任意旧 Plan、任意另一个合法格式 Plan、缺计划或缺要求的 Story/spec 都应失败；
- waiver 只能绑定用户 receipt、精确 commit intent 与时限，不能由 commit message 中一段普通字符串旁路。

### 4.5 Graphiti 只作为可重建镜像

Git 中的 Goal/OpenSpec/decision ledger 是治理决定 canonical；Graphiti 只是 derived mirror。

在 repo-level namespace 通过独立 OpenSpec 明确定义前：

- 治理决定记录 `graphiti_mirror_state=pending`；
- 不写 `canvas-dev`、`vault:default` 或自动猜测的 vault；
- Stop 不因 Graphiti 不可用而阻断，也不得把 pending 标成 archived；
- 后续 publisher 使用 outbox 状态 `pending → sent → acknowledged/failed`；
- 只有实际返回 episode UUID，并校验精确 group、payload commitment 与 ACK，才能成为 `acknowledged`。

Phase 0G 本身对 `canvas-dev`、default 或任何 Vault group 的运行时读写调用均为 0；它只做本地静态迁移与 fixture。未来若需读取历史 `canvas-dev`，必须另立隐私/root receipt，限定 allowlisted migration/audit reader，强制 `exclude_invalidated=true` 并把结果标为 noncanonical，不能作为当前状态或完成证明。项目要求的每轮记忆搜索若因 MCP/runtime 不可用而无法执行，canonical 状态必须记录 `memory_search_state=unavailable` 和 pending action，禁止回退到默认 vault 或伪称已搜索。

vault-specific 产品数据仍必须调用 `build_vault_group_id()`，Cypher 仍必须通过 `cypher_with_group_filter()`；GOV-01 不放宽任何跨 vault 规则。

## 5. 解除启动循环的状态机

通用治理纪律要求“OpenSpec 先于实施”，但 GOV-01 必须先隔离一个会自行写入/推送且不可复现的旧治理链。长期 Goal 已将下列流程定义为一次性、不可复用的 Phase 0G bootstrap 状态机：

```text
DRAFT-USER-DECISION
  └─ PREAPPROVAL-CENSUS → first-receipt envelope
      └─ 用户引用 envelope SHA，确认 Goal §12 + S1–S4 + GOV-01 方案 A 与精确授权
      → GOV-01-DESIGN-LOCKED
          → BOOTSTRAP-0-SAFE-MODE（只改 tracked settings，先移除 Stop 写副作用）
              → GOV-01-EXECUTION-QUARANTINED
                  → CLI 创建 repair-agent-governance-v2 OpenSpec
                      → 第二阶段 exact manifest receipt
                          → runtime/trackability/canonical/DD/Graphiti 修复
                              → GOV-01-IMPLEMENTED-UNVERIFIED
                                  → GOV-T00–T12 + 独立红队
                                      → GOV-01-VERIFIED
                                          → 创建 annotation-truth-ledger-v2
```

target bytes 不得包含尚未知的用户 message ID、时间戳或 outer-envelope hash。需要进入目标状态的只能是预先生成的 `approval_challenge_id`；用户回复/平台 receipt 留在外部或本机私密 receipt 层，不得在批准后回写已冻结 target bytes。若确需提交新的 receipt projection，必须作为新的证据 revision 单独获批，不能偷渡进本次 candidate。

repo file entry 与环境证据严格分型：`repo-object` 才允许 repo-relative path；`git-config`、`resolved-tool`、`external-hook-set` 等只进入 environment evidence，不能伪装成文件 entry。raw dirty inventory、B2 snapshot、user/managed settings、`core.hooksPath`、installed hook locator 和任何本机绝对路径仅存 0600 私密层；public control artifacts只保存状态、计数与 domain-separated keyed commitment。没有私密层 receipt/key 或 public/private checker 过门即停止，不把裸 locator/raw digest 提交到 repo。
