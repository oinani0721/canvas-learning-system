## A1. 读时时效项数学 — FIX-BEFORE-BUILD

- μ 不变性只在 FLOOR 未生效时成立。逐坐标 `max(..., 0.05)` 后一侧先触底 → 比例破坏 → μ 向 0.5 漂移：先验 a=0.9,b=2.1 时 a·f 约 288 天触底、b·f 约 372 天触底，之后 μ 从 0.30 上漂；双触底后 Beta(0.05,0.05) μ 被强改 0.50。高掌握 a=9,b=1 同理（298 天后 μ 从 0.90 向 0.50 下漂）。
- 「σ 半衰期 69 天」不准确：0.99^d=0.5 解得 d=68.97 天，是**证据质量 n=a+b 的半衰期**。σ² = μ(1-μ)/(n·f+1)，σ 向上限渐近回升，无统一半衰期（n=3 时"半程回升"约 134 天，n=10 约 198 天）。
- 最小 diff：读时折扣删掉 FLOOR，仅同比缩放（a,b 为正时有限天数不会产生无效 Beta 参数）；对非正 a,b 报错。
- 补测试：μ 保持性（参数化 days 0/30/69/365/3650）、σ 单调、不改存量状态、未来时间戳钳 0。
- 产品文案改为「证据质量半衰期约 69 天；σ 按当前有效样本量逐步回升，回升速度取决于节点已有证据量」。

## A2. 写时 γ=0.9 与读时 γd=0.99 交互 — FIX-BEFORE-BUILD

- 写时递推 n∞ = 1/(1-0.9) = 10；两层折扣一个按次数一个按时间，方向成立、非简单 double discount。
- **真正病理是「置信度复活」**：effective() 只用于读排序，quiz-answer 下次评分仍拿原始存储 A,B 调 update() 并立即重写 last_examined。数值例：a=9,b=1 闲置 365 天 → n_eff≈0.255、pick≈0.632；答错 grade=0 后按原始 9,1 更新 → a'=8.1,b'=1.9、μ'=0.81、σ'≈0.118、pick≈0.692。**闲置一年还答错，节点反而更不紧急**——闲置不确定性被原始 n=10 一次评分瞬间恢复。
- 推荐最小修正：`update_after_idle(a,b,grade,days_idle)` = 先 effective() 再 update()；quiz-answer 写入前读旧 last_examined 算 days_idle；时间解析统一 aware datetime（`fromisoformat` + Z→+00:00），未来时间戳钳 0。旧证据最终权重 0.9 × 0.99^d，两折扣对应不同机制，属有意复合。
- 若坚持 effective() 纯读时，则必须改名 `staleness_priority_overlay()` 并承认它只是排序 bonus，否则「不确定度后验」语义不闭合。

## A3. 板级 min(effective_pick) 与三态公平性 — FIX-BEFORE-BUILD

1. 无字段节点（7 个）全走先验 pick≈0.071 → 启动期霸榜；并列时若按名称/扫描顺序，某板可能连续占 top1。
2. **通知节点 ≠ 实际被考节点**：`/start-exam-board from <板>` 会自己按未折扣 pick_score 重新选点；但它已支持 `node <节点名>` 定向。每日输出必须绑定 `node <top_node>`。
3. daily picker 必须复用 start-exam-board 的 eligibility（跳过含「你的 1-2 句精准定义」占位符的未剖析节点），否则可能把无法出题的节点推上手机。
4. 保留 min()，只修并列公平性：sort key = (round(priority,8), board_last_recommended_at, oldest_eligible_last_examined, board_stem)；state 加 board_last_recommended 记录。
5. 今日复习.md 输出三态统计（new/legacy/none/ineligible），启动期霸榜可诊断。

## A4. launchd、幂等和时间窗 — FIX-BEFORE-BUILD

- 官方语义：StartCalendarInterval 睡眠错过 → 唤醒补跑（多次合并为一次）；关机错过 → 不补跑。RunAtLoad 是独立触发器，bootstrap/登录/加载即跑一次。
- 只判「21:00 后不推」不够。正确时间门：`time(9,5) <= now < time(21,0)` 才允许推；RunAtLoad 在 9:05 前只生成不推；窗口内补跑读已有 payload 补推。
- last_generate_date/last_push_date 分开必要但不充分，还缺：持久化 payload（今日复习.json）、原子状态写（os.replace）、运行锁（mkdir lock）、传输成功校验（--fail-with-body + 解析响应）、Bark 端幂等 ID。
- 状态字段建议 `last_push_accepted_date`（HTTP 成功只证明服务端接受，不证明 iPhone 已显示）。
- 网络 exactly-once 本地做不到 → 用 Bark 官方稳定 `id`（同 ID 更新已有通知）：本地 at-least-once + Bark notification ID 幂等更新。
- plist 的 StandardOutPath/StandardErrorPath 不做 ~/$HOME 展开，必须绝对路径。

## A5. Bark 凭据、安全和隐私 — FIX-BEFORE-BUILD

- GET URL 方案四问题：key 进 curl 进程参数、板/节点名进进程参数、URL 编码地雷、shell 拼接注入面。
- 最小修正：只存 key 到 `~/.config/canvas-review/bark.key`（目录 700 文件 600 umask 077）；不 source push.env（source 会执行内容）；改 `POST https://api.day.app/push` JSON body（device_key/title/body/group/id）；最稳是 send_bark.py 让 key 和 payload 不进命令行。
- 隐私二选一：**方案 A** MVP 不上加密 → 远程只发泛化内容（"今天有 1 板 3 节点待复习"），具体名留本地；**方案 B** 锁屏要具体节点名 → MVP 就上 Bark 自定义密钥加密（AES + 16 字节 key + IV + iPhone 端同配置）。裁决：具体节点名 + 公共 api.day.app = 加密应在上线前做；不想维护加密 = 远程降级泛化内容。
- E2E 只保护传输与服务器；锁屏预览是另一隐私面（iOS 通知设置决定）。

## A6. 对本地模型栈依赖与 TCC — PASS

- 每日推送链（Python 读 md → 排序 → 写 md/json → HTTPS Bark → osascript 兜底）零依赖 Graphiti/llama-server/reranker/embedding/Neo4j/LanceDB/Claude API。「零依赖」判断成立。
- 但 TCC 是整个 MVP 的 release blocker（Desktop 路径 + 已有 exit 126 实证）。未授权时：脚本进不了业务逻辑/扫不了节点/写不了输出/推送无 payload/兜底不会发生/health 只见模糊 126。
- 最小运维修正：launchd 入口 wrapper 放稳定非 worktree 路径（~/Library/Application Support/CanvasReview/bin/），先写启动日志 → TCC preflight（test -r vault, test -w outputs/state）→ 再调 repo 脚本；plist 绝对路径；固定绝对 Python/venv；PATH/HOME/LANG 显式；安装用 gui/$(id -u)。

## A7. 上线一周最可能翻车点 — FIX-BEFORE-BUILD

- P0：通知节点与实际考察节点不一致（必须传 node）；生成成功推送失败后无可复用 payload（必须持久化 json）；Bark HTTP 失败未被识别（--fail-with-body + 解析，明确接受才更新 accepted_date）；状态竞争/半写入（锁 + os.replace）。
- P1：节点名 shell/AppleScript 注入（osascript 走 argv heredoc，Bark payload 用 JSON serializer）；时间戳解析混乱（统一 aware datetime，未来钳 0）；launchd 找不到 python3/PyYAML（绝对 venv 路径 + kickstart 验收）；worktree 清理后任务永久失效（wrapper 隔离）；死人开关假绿（解析结构化 state：生成✅ 推送接受✅ 兜底- payload_age）。
- 12 场景验收矩阵：09:05 正常 / 08:00 RunAtLoad / 10:30 唤醒 / 21:01 唤醒 / 生成成功 Bark 超时 / 失败后 15:00 重跑 / Bark 成功但 state 写前被杀 / 手工+kickstart 并发 / 名含空格引号&?#emoji / TCC 未授权 / state JSON 损坏 / 全板占位符。

## B8. MLX-VLM + 大模型建议是否成立 — KEEP，撤回迁移建议适用性

- 三盲区自我修正：①多模态前提在本系统错误（本地只做文本抽取/蒸馏/rerank）；②MLX-VLM 无 /v1/rerank 记录，不能一体替代；③json_schema 框架能力存在但「Qwen 嵌套 schema + 50 次零失败」生产契约未证明。
- MLX-VLM 0.6.8 是 2026-07-27 极新版本，issue 列表有 MoE APC cache 报错、prompt-cache 复用致 silent wrong output 等开放问题。
- 结论：不迁移 MLX-VLM，不升级 122B，不重做多模态网关。当前任务高频小输入严格 schema，35B-A3B 已 1.57s p95 + 50/50。

## B9. llama.cpp 组合回归风险与版本锁定 — 组合可用，但部署未真正锁定

- 相关实锤：llama.cpp #21228（嵌套 $ref/$defs schema 静默退化，明列 Graphiti 受影响）、#21487（--reasoning-budget 相邻构建被忽略且无报错）、#22717（Qwen3.5 reasoning budget 失效烧穿）、LM Studio #1773（JSON 困在 reasoning_content 同型故障）。
- 未锁定项：llama-server --version / binary SHA-256 / GGUF SHA-256 / chat template hash / 参数 hash / graphiti_core schema hash。Homebrew 升级、PATH 替换、HF 重新解析、模型 repo 变化、graphiti_core 升级都会改契约。
- **更严重 gap：canary 不是 fail-closed enforcement** —— llm_factory 只探 /models 可达 + 打一条"须已通过"日志就构造 client；启动脚本只要端口可达就认为服务已运行，不验证模型/binary/参数。
- canary 四缺口：空 entities 列表可通过全部检查、不验证预期实体被提取、只覆盖 ExtractedEntities 单 schema、p95 记录但不参与决策。50/50 的单侧 95% 失败率上界仍约 6%；50 次适合变更门禁，不应宣传为长期零故障证明。
- 最小加固：固定 artifacts（binary/GGUF/template 落盘 + hash 清单）→ canary 通过生成 attestation → backend 启动算 fingerprint 不一致即 disable_worker（不是 warning）→ 扩展 canary（reasoning_field_empty / finish_reason / expected_entity / nonempty / p95 门禁 + 自动枚举 graphiti_core 全 schema）→ 保留 50 次变更门禁 + 每周定时 + 生产累计（300 次→1% 上界，3000 次→0.1%）。

## B10. 16K 上下文与 --parallel 1 — 上下文 PASS 但须 token-aware；并发 KEEP

- distiller 8000 字符截断 + prompt <1000 字符 + 输出 1500 tokens，16384 大概率充足；但字符≠token（中文近一字一 token），应改 tokenizer 截断到 MAX_INPUT = 16384-1500-512，记录 prompt_tokens/completion_tokens/finish_reason/truncated_input，>80% 写 warning。
- **比 context 更重要**：本地 Tier0 无 response_format、temperature=0.2、直接 json.loads；本地返回坏 JSON 时调用本身成功 → 不进 Ollama fallback → 外层捕获返回空 DistillationResult = 静默蒸馏缺失。修正：temperature=0 + response_format=json_schema(DistillationResult.model_json_schema(), strict) + 把该 schema 加进 50-run canary matrix。
- --parallel 1 保留（episode 6-12 次链式调用 ≈ 9-19s 服务时间，单用户合理）。加指标：queue_depth / oldest_queue_age / episode e2e latency / distiller_timeout_count / dead_letter_rate。升 parallel=2 的触发信号与重验清单见原文。

## B11. 升级 122B 触发条件 — 现在没有升级信号

- 先建 100-200 条人工标注 episode gold set（中英混合/公式/代码/错误概念/关系/时间/长对话/注入噪声）。
- 触发表：canary 失败先归因 runtime/template；critical omission >5%；幻觉实体 >2%；relation F1 低于基线或人工修正率 >5%；死信 >0.5%；recall@5 <0.90 或回退 >0.02；跨语言错误持续 top；截断 >1%；队列问题不是升级理由。
- 候选模型十条件：全 schema 50/50、omission 相对降 30% 或 F1 +5pp、recall@5 +0.05 或 MRR +0.03、假阳/重复/泄漏恶化 ≤0.02、单调用 p95 ≤3s 或 ≤2× 现役、单 episode p95 ≤30s、配对 bootstrap 95% CI 不跨 0、人工盲评、完整重做 fingerprint、reranker 独立保留。

## B12. bge-reranker-v2-m3 + bge-m3 — KEEP

- 合理性：BGE-M3 100+ 语言 / dense+sparse+multi-vector / 8192 tokens；bge-reranker-v2-m3 官方允许 sigmoid 映射；llama.cpp 官方列为 /v1/rerank 适用模型。
- 短板：①BGE-M3 只用了 dense（不为用全能力重构 LanceDB）；②reranker 以 max_length=1024 fine-tune（BAAI 维护者建议），长文先切 chunk；③sigmoid 非跨 query 校准，勿建全局绝对阈值；④适配器 sigmoid 对极端负 logit 有 overflow 边界（stable_sigmoid 修复成本极低）；⑤缺 reranker ablation（A=无 reranker vs B=cross_encoder 对比 recall@5/MRR/假阳/延迟）。
- 无可诚实声称的 drop-in 更优替代（bge-reranker-v2-gemma / minicpm-layerwise 无 GGUF+llama.cpp 标准 rerank 路径一手证据）。
