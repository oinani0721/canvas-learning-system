# 独立核实：`_first_calibration_entry_block` 的「含结束边界」措辞不实

> 三方独立收敛：本卡 Workflow 的 (d) 条定性、Codex p2、以及我（作者）逐字核对。

## docstring 的声称

`e22ad10a:backend/tests/regression/test_g3_2_review_ledger.py`：

```python
def _first_calibration_entry_block(text: str) -> str:
    """frontmatter 里 `calibration_log:` 下**第一条**条目的完整字节块（含结束边界）。
    ...
    要证明「这一条一个字节都没变」，必须把**变更后**那一条也按边界切出来整块比。
    """
```

## 实现（逐字）

```python
    _i1 = _i0 + 1
    while _i1 < len(_lines) and _lines[_i1].startswith("    "):
        _i1 += 1
    return "\n".join(_lines[_i0:_i1])
```

- 循环停在**首个不以 4 个空格开头的行**，`_i1` 指向那一行；
- `_lines[_i0:_i1]` 是**左闭右开**切片 ⇒ **不含** `_i1` 那一行；
- `"\n".join(...)` ⇒ **不含末尾换行**。

⇒ **返回值既不含边界行、也不含末尾换行**，「含结束边界」这个说法**不成立**。
（Codex p2 另补一点：`read_text` 会归一化换行符，所以 CRLF/LF 差异也看不见。）

## 这是否推翻「E2 被抓住」？—— 不推翻（但 (d) 因另一原因已降为部分成立）

判据②比较的是「**前后两次用同一个 helper 切出来的块**」是否逐字节相同。
只要切法前后一致，「A 条目内部键序重排」就会让两次切出的块不同 ⇒ 仍被抓住。
本卡对 E2 的推演与 harness 实测（E2 KILLED）都成立。

⚠️ **但 (d) 整体已降为「部分成立」**，原因是同一个截断行为在**另一个方向**上
构成真实漏网：Codex p2 实证「A 条目后插空行 + 同值重复键」能过全部三道判据
（重复键落在被截断区间之外）。即：截断不影响「已被切进块内的改动」被发现，
却让「截断点之后的改动」完全不可见。详见验收单 §三与 §八.15。

**错的是描述，不是行为。** 但这正是 DD-13（名实一致）要管的事：
后人照 docstring 理解，会以为边界行也参与了比较。

## 真实后果：空行会静默截断被比较的区间

空行 `""` 不以 4 个空格开头 ⇒ `while` 提前退出 ⇒ 块被截断。
若 A 条目内部出现空行，**空行之后的内容不进入比较**，那一段的改动这道门看不见。

## 处置

- 本卡零代码改动，**只登记**。
- 建议（给写点边界卡或独立的门加固卡）：
  ① 把 docstring 的「含结束边界」改成与实现相符的措辞；
  ② 若要真的含边界，切片改 `_lines[_i0:_i1+1]` 并说明 `_i1` 越界时的行为；
  ③ 空行截断这个盲区，或者在 helper 里显式跳过空行、或者在门里断言
     「A 条目内不含空行」把前提钉死。
