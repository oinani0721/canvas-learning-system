# 交叉核实：E8 / E10 的负控输入各多拆了一层

> 触发：Codex p1 与本卡 Workflow 的 (b) 条定性**结论冲突**，我（作者）亲自去 diff 里核对，
> 判定 **Codex 正确、我方 agent 的那条结论不成立**。

## 冲突点

| | Codex p1 | 本卡 Workflow (b) 条 |
|---|---|---|
| E8 | 「**同时删除了类型检查和词法检查**」 | 「E4/E8 都是形态干净的**单层拆守卫**」 |
| E10 | 「除引入海象重绑外，**还把 `record` 换成 bytes**」 | （未提及） |

## 逐字证据（`rv-d-p1.diff`，`e22ad10a:backend/scripts/g32ccr1_negative_controls.py`）

### E8

```
描述: "删掉**本次输入 ts** 的词法判据（… 门同时污染两字段，被 review_time 那道喂饱）"
old:  "if not isinstance(_ts_in, str) or not _TS_RE.fullmatch(_ts_in):"
new:  "if False:  # MUTANT E8 拆掉 ts 词法判据"
```

把**整个 `if` 条件**替换成 `False`，于是被一并废掉的有两项：

1. `not isinstance(_ts_in, str)` —— **类型检查**
2. `not _TS_RE.fullmatch(_ts_in)` —— 词法检查（描述里唯一声称拆的那一项）

⇒ **描述比实际窄。** 该负控输入实际拆掉了两层防线。

### E10

```
描述: "用**海象**重绑 record（… 上一版 AST 扫描漏掉 NamedExpr）"
old:  "    shape = value_shape_problems(record)"
new:  '    shape = value_shape_problems(record := b"x")  # MUTANT E10 海象重绑'
```

除了引入 `:=`（描述声称的那一项），还把传给 `value_shape_problems()` 的值
从 `record`（dict）换成了 `b"x"`（**bytes**）。

⇒ **描述比实际窄。** 同时改变了「绑定形态」与「值的类型」两件事。

## 为什么这件事重要（与「特别判」互相咬合）

负控输入的价值在于「拆掉**这一道**防线后，**这一道**门会红」——
它证明的是**那道门承重**。多拆一层就破坏了这个指向性：

- E8 的击杀**可能**来自 `isinstance` 类型检查那一层，而不是它声称验证的词法判据；
- E10 的击杀**可能**来自「bytes 不是 dict」这个更早的形态判断，
  而不是它声称验证的「AST 扫描能否发现 NamedExpr 重绑」。

而 `g32ccr1_negative_controls.py:277` 的判定条件

```python
killed = rc == 1 and gate in out and "failed" in out
```

**不绑定失败断言身份** ⇒ 上面这两种错配**在 harness 输出里看不出来**，
两条都会照常显示 `KILLED`。

这与本卡「特别判」独立得出的结论（假杀面结构性存在、E3 已实际发生误归因）
是同一根因的三个实例：**E3 归因错、E8 多拆一层、E10 多拆一层**，
全部因为判据只回答「哪道门红了」而不回答「哪条断言红了」。

## 处置

- 本条**不修**（纯复审卡，零代码改动）。
- 登记为 Y1-B 的定向输入（与 `:277` 判据同一条修复）：
  修判据时应同时**收窄这几条负控输入的替换文本**，让每条只拆一层；
  或者反过来，把描述改成与实际相符（「拆掉 ts 的类型 + 词法两道判据」）。
- **方法论记录**：这是多来源交叉抓到了单一来源（我方 agent）的错误结论。
  我方 agent 把 E8 判为「形态干净的单层拆守卫」，是只看了描述、
  没有把 `old` 字符串里的**两个** `or` 分支拆开数。

# 附：validator 37 行新增的逐行分类（三方交叉，勘探数字被证伪）

卡文 P1 问题 3 要求「独立核，逐行分类，给出实数」。

| 来源 | 说法 |
|---|---|
| 勘探稿 | 「非注释新增只 **5** 行且全在 docstring」 |
| Codex p1 | 「31 行注释、**6** 行 docstring，可执行语句 0」 |
| 本卡实测 | **31 行注释（`#:` 开头）+ 6 行 docstring 续行，可执行语句 0** |

⇒ **勘探的「5 行」是错的，实数 6 行。** Codex 正确。

## 实测方法与一处自我纠错

先写了个状态机按 `"""` 计数分类，它把那 6 行判成了「可执行语句」——**错的**。
原因：这 6 行是**已有 docstring 内部**的新增，而开头的 `"""` 那一行没有改动、
因此不出现在 diff 里，状态机看不到它、以为自己在代码区。

去 hunk 的**上下文行**（diff 里以空格开头、未改动的那些行）核实后确认：
它们落在 `def value_charset_problems(value: object) -> list[str]:` 的 docstring 内
（上下文行 `第一版查整条，造成一条真实的数据丢失路径…` 等均无 `#` 前缀、缩进 4 空格）。

**教训**：对 diff 做静态分类时，**状态机的初始状态是未知的** ——
diff 只给了变化行加少量上下文，不给文件开头。凡依赖「当前在不在字符串/注释里」
的判断，都必须回到上下文行（或原文件）确认，不能只从 diff 的加号行推。

被删的 2 行同属 docstring 续行（措辞更正），非代码。

⇒ 结论：**`validate_learning_events.py` 在本审面内零行为改动。**
自述 (a) 说的「判据措辞同步落在代码注释 / docstring」属实。
