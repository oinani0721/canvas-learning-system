### 专项 ① — tuple 子类「读底层槽位放行」vs 卡文字面的「一律 fail-closed」：**安全**

对象：`extract_port` :340-386、`port_is_trustworthy` :388-420。

两版语义差集 = 全部 tuple 子类地址。逐类枚举（判据 :493 `port in BLOCKED_PORTS or not port_is_trustworthy(address)`）：

| 子类地址形态 | 新版行为 | 旧版行为 | 安全性 |
|---|---|---|---|
| 底层槽位 port = 7691/7687（精确 int） | `tuple.__getitem__` 读到真值 → 命中 BLOCKED → **拦** | 拦 | 等价 |
| 底层槽位 port = 7692（精确 int，真驱动） | trustworthy=True → **放行** | **误拦** | 新版更好 |
| port 是有状态 `__index__` 对象（TOCTOU） | `type(raw) is int` = False → **拦** | 拦 | **等价，仍 fail-closed** |
| port 是 `bool` | `type(raw) is int` 对 bool 为 False → **拦** | 拦 | 等价 |
| 覆写 `__len__` / `__getitem__` 撒谎 | 走 `tuple.__len__` / `tuple.__getitem__` 绕开重载 → 读到真值 → **拦** | 拦 | 等价 |

### H-1（HIGH）｜记账前的不可信调用抛异常 ⇒「已阻断、零账本」

`live_port_guard.py:382-385`（`extract_port` 只捕获 `TypeError`）、`:246`（`record()` 先做 `repr(address)`）、`:251`（`total += 1` 在其后）、`:491-493`、`:512`。

Codex p1 按纯内存推演提出，**本车道实测坐实**（`evidence-rv-c/P5-*`，直接调用 `_audit_hook` 纯函数，未装钩子未建 socket）：

| 输入 | 逃逸异常 | Δ(total, blocked, records) |
|---|---|---|
| 基线 `('127.0.0.1', 7687)` | 门的 `RuntimeError`（拒因含 `live Neo4j port connect attempted`） | **(1, 1, 1)** ✅ |
| 端口对象 `__index__` 抛 `ValueError` | `ValueError` 逃逸 | **(0, 0, 0)** ⛔ |

对照行是关键：只有 `TypeError` 那一种被 :384 接住并正常走完记账，其余异常类型**全部从 :491 逃逸**，`port_is_trustworthy`（:493）与 `STATE.record()`（:512）都没机会执行。

**危害边界（如实收窄）**：连接**确实没有建立**（异常在 connect 发出前抛出），所以**不是** 7691 写入、不是数据泄漏。失效的是门的另一条承诺——「拦截必然留下失败证据」：调用方 `except Exception` 吞掉后，`unaccounted_blocked()` 与最终总账都看不到这次事件，rc 仍可能为 0。与 r2 HIGH-2「拦截必然留下失败证据」同族，但**触发点不同**（那条是 advisory/预检次序，这条是记账前的异常逃逸），**不归任何已立卡**。

**建议方向（不实施）**：`extract_port` 的 `operator.index` 捕获面从 `TypeError` 放宽到 `Exception`（取不到端口即按不可信处理）；`record()` 的 `repr(address)` 加异常兜底（格式化失败不得吞掉记账）。两处的共同原则：**记账不能依赖被测对象的任何可重载方法成功返回**。

### M-4（MEDIUM）｜import 分支看不见 `importlib.import_module`，两层 uvloop 防御可被同一动作同时穿过

`live_port_guard.py:514`（`elif event == "import" and args and args[0] == "uvloop"`）、`:486-487`（该分支的合法性论证）、`:567-573`（`poison_uvloop`）、`lifespan_isolation_guard_probes.py:289-297`（现有探针）。

**实测（`evidence-rv-c/P9-*`，同一个纯 Python 模块、三种入口对照）**：

| 入口 | `import` 事件里是否出现目标模块名 | 对 :514 分支 |
|---|---|---|
| `import` 语句 / `__import__` | 是 | 可见 |
| `importlib.import_module()` | **0 个事件** | **永不匹配** |
| `importlib.util` + `exec_module()` | 否（只有 `importlib.util` 等中间件） | **永不匹配** |

**两层是否能被同一动作同时穿过（`evidence-rv-c/P10-*`）**：

| 场景 | 模块被加载 | :514 分支命中 |
|---|---|---|
| A 毒化 + `import` 语句 | 否 | 是 |
| B 毒化 + `importlib.import_module` | 否 | 否 |
| C 毒化 + `del sys.modules[X]` + `import` 语句 | **是** | **是** ⇒ 第 2 层接住 |
| **D 毒化 + `del sys.modules[X]` + `importlib.import_module`** | **是** | **否** ⇒ **两层同时脱出** |

场景 C 正是 :486-487 论证里点名的那条规避路径（「毒化会被『del 掉再 import』绕过，而 audit hook 摘不掉」），它成立。
但把最后一步换成 `importlib.import_module`（场景 D），**两层都不响应**——audit hook 确实摘不掉，可它**看不见**这条入口。
该论证在这条入口上不成立。

**可利用性（三条都核过，决定级别）**：
1. uvloop **确实装在共享 venv 里**（`find_spec` 命中 `card-v5-lance/backend/.venv/.../uvloop/__init__.py`）⇒ 不是 `ModuleNotFoundError`，缺口真实可达；
2. 现有探针 `probe_uvloop_reimport_blocked`（:289-297）第 :296 行用的是 **`import uvloop` 语句**，即场景 C——**它测的正好是分支看得见的那条入口**，测不到 D，因而给出了虚假信心；
3. 触发需要**刻意的两步动作**（`del` + `importlib.import_module`），不是意外会发生的；且本仓生产代码对 uvloop 零引用（:572）。

**级别判 MEDIUM 而非 HIGH**：不是当前可被误触的洞（需刻意行为、生产零引用），但 :486-487 的**声明比实际覆盖宽**，且唯一为它作证的探针只覆盖了看得见的那条入口。若 uvloop 真被加载，其 connect 走 libuv、不触发 `socket.connect` 审计事件（:570-571 自述）⇒ 整道门静默失效，后果重。

**建议方向（不实施）**：判据从「`import` 事件 + 模块名」改为不依赖入口的形态（例如在 `sys.meta_path` 最前插一个拒绝 finder，或在 :605 装门后立即断言 `sys.modules['uvloop'] is None` 并在每个用例边界复核）；并把探针补一条走 `importlib.import_module` 的对照。
