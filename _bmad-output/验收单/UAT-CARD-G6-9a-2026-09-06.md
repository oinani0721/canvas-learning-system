## 4-B 用户可感（先看这段）

**这次做了什么，对你意味着什么：**

1. **给"日期"这件事加了一道体检，而不是改了它。**
   这张卡一行功能代码都没动。它做的是：把几件此前只写在注释里、或者只是"大家默认
   应该如此"的事，变成电脑每次都会自动核对一遍的检查。检查不通过就会当场报警。

2. **体检查出一个真问题：早上那条提醒算的"今天"，和网页上显示的"今天"，
   用的不是同一把尺子。**
   提醒是按**你电脑当前设定的时区**算今天；网页固定按**北京时间**算今天。
   你现在的电脑设的就是北京时间，所以两边一致，**眼下没有出问题**。
   但只要电脑时区变了（出差改了设置、换台机器、或者在服务器上跑），
   两边就会对不上——而且不会有任何报错，只是日期悄悄错一天。

3. **更值得说的是"为什么会这样"：同一个功能的两条路，只有一条被加固过。**
   网页那条路，之前有人专门写了代码**强制**它用北京时间，还在注释里留了实测记录。
   但定时提醒那条路，从头到尾**没有任何一处把时区钉死**——它靠的是"电脑时区
   恰好设对了"。这次把这个不对称写成了检查项：哪天有人给定时任务也补上，
   检查会主动报红提醒"这条记录可以销账了"。

4. **另外确认了三件本来就该如此、但从没被验证过的事：**
   - **半夜不会算错日**：北京时间 23:59 生成的清单，和 00:01 生成的，
     该在"今天"的留在今天、该到"明天"的挪到明天，一条不错。
   - **电脑睡醒后不会重算**：早上 8 点（还没到推送时间）先把清单存好但不发；
     10 点那次只把提醒补发出去，**清单本身一个字都不重新算**；到了第二天才重新算。
   - **提醒发失败了，清单还在**：手机推送失败的时候，今天的复习清单**已经完整
     存在电脑上**了——不会因为发不出去就连清单也没了。

5. **还登记了一件"目前看不见"的事（本卡不修）**：提醒发送失败时，
   **网页上完全看不出来**。你会看到一份正常的清单，不知道今天那条提醒其实没发出去。
   要在页面上加个提示，是另一张卡的事（已登记 CARD-G6-9b，这批不做）。

**你需要做什么**：无。这次没有改变系统的任何行为。

**felt-sense**：这张卡的产出不是"修好了什么"，而是**把几句原本靠人记住的话，
变成了机器会替你记住的话**。最有意思的一条是第 3 点——问题不在于哪条路写错了，
而在于**两条路被照顾的程度不一样**：一条有人专门加固过并留了实测记录，另一条
从来没人想起来。这种"不对称"平时看不见，只有把两条路摆在一起比才会现形。

### 二 (a) 两套时钟：16 组合，8 组分叉

**机制自证先行**（`test_tz_fixture_actually_moves_the_local_clock`）：
四个时区给出**四个不同的 UTC 偏移**，且夏令时时区在 7 月落在夏令时那一档
（NY `-04:00` 而非 `-05:00`、London `+01:00` 而非 `00:00`）。
没有这条，下面 16 个用例可能全跑在同一个时区上，全绿也毫无意义。

| 瞬间（上海时间） | Asia/Shanghai | UTC | America/New_York | Europe/London |
|---|---|---|---|---|
| 夏 07-31 11:30 | ✓ | ✓ | **⛔ 分叉** | ✓ |
| 夏 08-01 00:30 | ✓ | **⛔ 分叉** | **⛔ 分叉** | **⛔ 分叉** |
| 冬 01-15 11:30 | ✓ | ✓ | **⛔ 分叉** | ✓ |
| 冬 01-16 00:30 | ✓ | **⛔ 分叉** | **⛔ 分叉** | **⛔ 分叉** |

8 组分叉全部以 `xfail(strict=True)` 登记，reason 写明「哪个时区 / 哪个时刻 /
哪两个日期」并点名移交卡号。`strict=True` 的意义是**跨卡交接**：哪天有人统一了
两套时钟，这些用例会 XPASS 而报红，提醒把登记项转正（沿第十批 X3 先例）。

**根因**：`daily_review_run.py:215-216`
```python
local = now.astimezone()          # ← 机器本地时区
today = local.date().isoformat()  # ← 驱动 last_generate_date / last_push_accepted_date
                                  #   / board_last_recommended 的值
```
而显示侧恒按 `Asia/Shanghai`（`review_overview.py:80` `_DISPLAY_TZ_NAME`）。

**防自证的两道设计**：
1. `KNOWN_DIVERGENT` 是**硬编码字面量**（不由被测公式现算）——期望值与被测量同源时，
   缺陷会让两边一起退化、断言假通过（CARD-G2-9 的 M1 就栽在这上面）。
   用例内另有一条"登记表的值必须与实测逐字相符"的断言，表过期会当场暴露。
2. 显示侧用**两条独立换算路径**交叉验证（`_gate_buckets` 的 `fromisoformat` + 转上海，
   与 `_sh_day` 吃 UTC-Z 串），两条给出同一日期才继续 —— 否则就只是在复述被测代码。

**覆盖了生产注释警告的那个具体窗口**：`review_overview.py:1296-1298` 写着
「后端容器 TZ 为空、`/etc/localtime -> Etc/UTC`，于是上海 00:00-08:00 这 8 小时里
refresh 产出的是**昨天**的日期」。矩阵的两个 `utc1630` 瞬间换算到上海正是
`00:30`，落在该窗口内，且 `TZ=UTC` 组合被登记为分叉 —— 本卡把那句实测叙述
变成了会随代码演进翻红的门。

### 四 (b)(c)(d) 与两处自查加固

- **(b) 午夜跨界**：用真实 `picker.build_payload` 在上海 23:59 与 00:01 各生成一次，
  跑 `_gate_buckets` 的**完整调用链**（`_gate_due_groups` / `_gate_upcoming` /
  `_gate_boards_rollup` 三个 helper 只 import 调用，不改）。那颗"上海 08-01 00:30 到期"
  的节点从 `future` 桶翻到 `due_today` 桶，两次门禁都放行。**未发现缺陷。**
- **(c) 唤醒补跑**：**不 monkeypatch `PUSH_WINDOW`**（窗口判定正是被测物）。
  08:00 → `skip-window` 且已落盘、无推送；同日 10:00 → `generate:cached` 且
  `generated_at` 与文件 mtime **都不变** + `push:accepted`；次日 10:00 → `generate:new`。
- **(d) Bark 失败**：替身 `send` 返回 1，断言 `last_error == "bark-send"` /
  `last_result == "generated_push_failed"` / **不落** accepted 日期。

> **两处自查加固（在 Codex 返回之前自己发现的）**：
>
> 1. **(c) 的 "cached" 原先分不清是「缓存门起作用」还是「这个分支恒返回 cached」**。
>    `ensure_payload` 有四道门（当日已生成 / sha 匹配 / 未越过 `next_due_utc` /
>    节点池不比 payload 新），原用例只证明了四道**同时**放行。补了第 4 步负向：
>    同日内动节点池 mtime → 必须 `generate:new`。该步骤在"同日、sha 匹配、
>    `next_due_utc` 为空"的条件下，唯一能触发重扫的就是 mtime 门 —— 它变绿即证明那道门承重。
> 2. **(d) 的「推送时文件已存在」是结构性恒真的**：`ensure_payload` 在 `main()` 里
>    无条件排在推送之前（`:219` vs `:245`），`exists()` 永远不会红。已在代码里
>    **标注它不承重**，改用「推送发生时投影必须**已完整可解析**」承重
>    （`atomic_write` 是写临时文件 + rename，半写会在这里抛/缺键），
>    并补一条「推送失败后投影仍在盘上且未被回滚」。

**夹具的进程级污染实测无外溢**：`machine_tz` 改的是 `os.environ["TZ"]` + `time.tzset()`
（进程全局）。判据不是"代码里写了 try/finally"（那是复述代码），而是**两种顺序同进程混跑**：
矩阵在前 / 在后，两次都是 **122 passed + 8 xfailed**（= 矩阵 16+8 与既有 106 之和），
与各自单跑一致。
且第一种顺序里那 8 条 xfail 是**内部真失败**后才跑的其余 106 条 ——
这同时证明了 teardown 在**失败路径**上也执行了。证据 `tz-fixture-no-leak-*.txt`。

### 六之二 ⛔ 一起并发污染事故（如实登记，含处置与复核）

**发生了什么**：我在跑变异 harness（原地改文件 → 跑 → `finally` 还原）的同时，
起了一轮对抗复核 workflow，而**它的子代理有写权限**。某个代理为验证自己的假设
把被测文件改成了变异态，并在 `backend/tests/regression/` 下留了三个 581 行的副本
（`test_g69_mutprobe_tmp.py` / `zz_mutated_g69_probe.py` / `test_g69_refute_probe.py`）——
那个目录下的文件**会被 pytest 收集**。

**为什么最保险的自检没拦住**：我的 harness 第二轮启动时读
`ORIG = TGT.read_text()`，**读到的正是代理的变异态**；跑完 `finally` 忠实地把那份
**污染基线**写了回去，并报「还原对账: OK 逐字节相同」。
**自检没说谎——它比较的是自己捕获的基线，错在基线本身是脏的。**

**怎么发现的**：靠一个**外部结构不变量**——文件里 `_real_runner_today` 应出现 3 次
（1 定义 + 2 调用），实测只有 2 次。sha 对不上只说明"变了"，说不出"变成了什么"。

**处置**：
1. 中止 workflow（因此 §八 无结论）；
2. 还原被污染的两行（`runner_today` 的真实调用）；
3. 逐个清掉三个代理副本；
4. 结构核对：8 个用例定义 / `_real_runner_today` 3 次 / 可疑注释 0 处；
5. **独立佐证还原成功**：修好后的 sha 回到了**第一轮干净基线**那个值
   （`d6f09333d198`）——两次独立捕获给出同一个值才算数；
6. 事故后**重跑 `tests/regression/` 全目录**（**1400 passed / 6 skipped / 10 xfailed**），
   因为代理副本可能已污染过某次判据；
7. 定稿后所有证据重新绑定最终 sha `8d803c27…`。

**教训（已写入长期记忆）**：审查类子代理**不给写权限**；变异 harness 运行期间
目标文件**必须独占**；残留清扫要按目录扫未跟踪文件而不是按名字猜
（三个副本命名各不相同）。
