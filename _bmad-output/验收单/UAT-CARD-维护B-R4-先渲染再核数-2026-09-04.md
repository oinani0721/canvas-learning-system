## 4-B 用户可感（先看这段）

**这次改了什么，对你意味着什么：**

1. **回顾报告里编造的数字会被自检打回——包括写在「派生」小节里的那些。**
   在此之前，`## 台账` 下的 `### 派生` 小节是一个洞：报告里随便写一行
   `- 某节点 — 批注 999 条`，自检照样说"通过"。而机器扫出来的真实数据
   （`ledger.derived`）一直就在旁边的 JSON 里，从来没人拿它对过。现在对了。

2. **合法的写法不再被误拒。** 缩进的小标题、带全角括号的段名、真报告里
   `（理解度未闭环 3 条）；…` 这类尾巴，都不会再因为"正则没写到"而被判违规。

3. **自检看不懂的排版，会说"我看不懂"，而不是假装读懂。**
   报告里写数学公式 `$3$`、脚注 `[^1]`、图片，或者一个自检不认识的 HTML 标签，
   现在会被明确拒绝并告诉你是哪一行。以前它会**悄悄把这些标记剥掉**再去数数字——
   剥掉之后数出来的，未必是你在 Obsidian 里看到的那个数。

**你需要做什么**：不需要。回顾报告由 `/board-recap` 按模板生成，模板本来就不写
这些排版。这条改动挡的是"生成侧出错"和"人手改报告改错"两种情况。

### 七 测试基础设施的两处真缺陷（本卡顺带修）

1. **`_load_recap_scan` 的 importlib 用法缺陷**：动态加载后**未注册 `sys.modules`**。
   Python 3.14 的 `dataclasses._is_type` 会做 `sys.modules.get(cls.__module__).__dict__`，
   取到 `None` ⇒ `AttributeError`。被测物一引入 `@dataclass`，**50 条门一起变红**，
   而症状伪装成"被测物坏了"。生产路径不受影响（那边是 `__main__`，本来就在册）。
2. **`write_report` 的派生行是硬编码**：`tips 未闭环 2 条`，而 scan 里是 0 或 1。
   种子行早在 round-6 就改成"按 scan 渲染"（注释里还留着"一直没露馅"这句话），
   派生行没跟上。**连测试自己的基线报告都在编造派生数字**——这是 BLOCKER② 最直接的证据：
   不绑定的地方，连我们自己都会写错。

### 8.1 ⭐ 章节树的树语义造成了一个**放行面**（已修）

`Section.hi` 用的是树语义：终点 = 下一个**同级或更高级**标题。这在结构上正确，
但它替换掉的旧代码不是这个语义：

| | 旧实现 | 树语义 | 差别 |
|---|---|---|---|
| `## 台账` 段终点 | 下一个 `^##[^\S\n]`（**恰好** H2） | 下一个 level ≤ 2（含 **H1**） | H1 会提前结束台账段 |
| `### 种子` 段终点 | 下一个 `^#{2,3}[^\S\n]` | 下一个 level ≤ 3（含 H1） | 同上 |

后果**实测**（探针 `probe_h1_narrowing.py`，两版同语料对跑）：

```
## 台账 / ### 种子 / - S — 批注 2 条 / # 插入的一级标题 / ### 其他 / - Ghost — 批注 9 条
  重切前(7b94f318): 漏网行被抓 = True
  重切后(未修时)  : 漏网行被抓 = False   ← problems 完全为空，编造的行被放行
```

**这是一次真实的回归**：报告中间插一个 `# 一级标题`，其后台账段里的编造行就出不了审计面。
修法 = `Doc.audit_span(sec)`：终点 = 下一个 `2 <= level <= 本级` 的标题
（H2 ⇒ level==2；H3 ⇒ level ∈ {2,3}；H1 **不**终止），与旧实现两处扫描逐字同义。
树语义与审计语义**并列保留**，各有单一定义点、各自答一个问题（"内容有哪些" vs "覆盖到哪"）。
修复后探针两版输出**逐字相同**。

> **教训**：把 N 份手抄合并成一个抽象时，抽象的语义**未必**等于被合并者的语义。
> "更整洁的那个定义"和"原来那个定义"不是一回事，而差出来的部分正好是放行面。

### 8.1b 同型第二处：缩进标题「不能开段、却能断段」（已修）

同一个抽象/被合并者语义不等的问题，在**缩进**这一维上又发生一次：
`_DOC_HEADING_RE` 允许 0-3 格缩进（CommonMark 正确），而旧的两处扫描是**顶格**判据。
于是缩进标题变成一个不对称件——`_SECTION_RE` 只认顶格所以它**不能开段**，
但它能让 `audit_span` 断段。实测：

```
## 台账 / ### 种子 / - S — 批注 2 条 / (三空格)## 缩进的二级标题 / ### 其他 / - Ghost — 批注 9 条
  重切前: Ghost 被拦 = True (2 条诊断)
  重切后(未修时): Ghost 被拦 = False (0 条诊断)
```

修法：`audit_span` 的终止判据补上「顶格」，与旧的两处扫描逐字同义。
两处发现现已固化为门 `test_r4_audit_span_not_narrower_than_legacy`（4 个 case：
h1 / indent_h2 / indent_h3 / h4）。

> ⚠️ 这道门我第一版写成 `assert any("不受任何认可小节覆盖" in x ...)` —— **判据写死了
> 单一拒因**，于是 indent_h3 与 h4 两个 case 假红（Ghost 其实被拦了，只是走了绑定
> 路径报「不在 ledger 里」）。判据应当是「这一行被拦下了」，不是「被某一条特定
> 拒因拦下」。

### 8.3 ⭐ BLOCKER② 的修复本身造出了一个同形态的洞（已修）

把 `### 派生` 纳入绑定面后，`covered` 集合随之扩大。而 `covered` 原来的语义是
「这些行落在某个认可小节里」——它被当成「这些行已经检查过了」来用（漏网扫描跳过它们）。
两者在**绑定面取不到**时会分叉：

```
## 台账 / ### 种子 / - S — 批注 2 条 / ### 派生 / - D — 批注 1 条
       / (三空格)### 种子 / - Ghost — 批注 999 条 / ## 末
ledger = {"seeds": [...]}          ← 没有 derived 键
```

`### 派生` 小节的 `audit_span` 延伸过缩进 H3（缩进不终止），把 Ghost 行吸收进
`covered`；而 `_ledger_rows(scan, "derived")` 因缺键 fail-closed 后 `continue`，
于是 Ghost **既没被绑定、也没进漏网扫描**——**与本卡开头要闭合的 BLOCKER② 是
同一个形态**（"两边都不管"），只是换了触发条件。是既有门
`test_domain_r32_indent_h3_and_zero_token_claim` 抓住的。

修法：`covered` 的语义收紧为「这些行**确实被检查过**」——绑定面取不到的小节
不算已覆盖，其中的行退回漏网扫描。

> **教训**：一个集合叫 `covered`，但它实际表达的是「落在某个小节里」而不是
> 「被检查过」。两个语义在正常路径上重合，在 fail-closed 路径上分叉，
> 而分叉处正好是放行面。**命名与语义不符，是缺陷的温床**（DD-13 的同一条道理，
> 只是这次不是函数名，是变量名）。

### 8.4 扁平 `ledger` 形态被新绑定误拒（已修）

`ledger` 的历史形态是**扁平 list**（无角色信息）。重切前 `_verify_seed_ledger_counts`
只管种子小节，派生小节根本不受绑定 ⇒ 扁平形态下报告照过。
重切后我把非 seeds 角色的扁平取值写成 `[]`，于是 `_bind_derived_section` 的
「零派生板不得写台账形状行」把**合法**的派生行判成无中生有。实测同一份扁平 scan：

```
重切前: 0 条诊断  []
重切后(未修时): 1 条诊断  ['…台账『派生』小节出现台账形状行, 但 ledger.derived 是空的…']
```

⇒ 扁平形态的正确答复是 `None`（**无法绑定**的能力边界），不是 `[]`（**查过了，没有**）。
**两者差一个语义，而这个差别是可观测的。** 已固化为门
`test_r4_flat_ledger_shape_does_not_false_reject`（含反向 case：扁平形态下种子绑定
必须照常生效，能力边界只限派生角色）。

> 与 §8.3 是同一类病：**一个值的语义被当成另一个语义来用**。
> §8.3 是 `covered`（"落在小节里" 当 "被检查过"），这里是 `[]`（"空集" 当 "无信息"）。
> 四个缺陷里有两个是这一类 —— 值得作为下一张卡的检查项。

### 8.5 ⭐⭐ 身份解析写了第二份，那份放行伪造数字（Codex 发现，已修）

**这是唯一一个不是我自己发现的**，也是全卡最严重的一个——它直接违背了 verifier
的核心承诺（伪造的数字通过了）。

Codex 第一轮在被内容过滤器拦下**之前**已经构造并验证出这个案例，
我从它的 stderr 抢救到构造并逐字复现：

```
ledger.derived = [{"node_id":"D_A","tips_open":1}, {"node_id":"DA","tips_open":999}]
报告            = "- D_A — 占位 · tips 未闭环 999 条"

派生侧: 🔴 放行 []                     ← 报告写真实节点 D_A，数字取自另一个节点 DA
种子侧: ✅ 拒绝 "…tips_count 是 1…"    ← 它有「先 raw 精确、再归一候选」两段式
```

**根因**：我在 `_bind_derived_section` 里**重写**了一份身份解析
（`match(visible) or match(raw)`，再拿 visible 的名字去查），而渲染会剥掉 `_` / `*`
（`D_A` → `DA`）——**先归一再查**，就让 `D_A` 绑到了另一个真的叫 `DA` 的节点。
种子侧本来是对的：round-25 就立过「先 raw 精确、再归一候选（唯一才绑，撞车拒绝）」。

**修法不是给派生侧补一段**，而是抽出 `_resolve_ledger_node()` 让两侧共用。
只修派生侧 = 把 BLOCKER 堵上却把成因留着：下一个人加第三个角色时，
会照着种子侧那份内联逻辑再抄一遍。

> **这一条最该被记住的地方**：本卡从头到尾在论证「一个原则只应有一个应用点」，
> 而我在实现这个论证的过程中，**自己又造了一份副本**，并且那份副本正好是错的。
> 论证一件事和做到一件事是两回事。

| # | 缺陷 | 类型 | 发现者 |

| 8.1 | 树语义让 H1 断台账段 | 抽象语义 ≠ 被合并者语义 | 自审 + 探针 |

## ⛔ 本卡未证明什么（必填）

这一节是本卡最重要的部分。**下面每一条都是"仍然可能让编造的数字通过"的面。**

   它比"逐条补正则"强的只有两条，一条也不多：① 归一与结构只有**一个**定义点，
