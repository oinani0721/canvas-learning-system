## 一句话：这张卡让你多了什么

跨库复习总览页（`http://localhost:8011/api/v1/review/overview/page`）上，**每个库卡片下面多了一个「🔄 刷新投影」按钮**。

以前：今日复习的数字只有 launchd 每小时跑批时才会更新——你刚做完一道题、卡片重新排期了，总览页要等下一个整点才看得见。
现在：点一下按钮，那个库的今日复习立刻重算，页面刷新回来就是新数字。

按钮是纯 HTML 表单（零 JavaScript），点了会回到同一页。

1. 浏览器打开 `http://localhost:8011/api/v1/review/overview/page`
2. **预期**：每个库的卡片底部都有一个蓝色小按钮「🔄 刷新投影」，包括那些显示"无投影"的库。

### 步骤 2 — 点一下，看数字变化（本卡的主戏）
1. 找到 `canvas-vault` 那张卡片，**先记下它现在显示的样子**：

   - 「生成于」是什么时间？
2. 点「🔄 刷新投影」。
3. **预期**：页面自己跳回总览页（不是白屏、不是 JSON），并且：
   - 「生成于」变成**刚刚**的时间；
   - 如果原来**没有**「分层」那一行，现在应该**出现了**——这说明盘上的旧投影被升级成了带五桶位的新格式（卡文 (d) 预告的那一幕）。

### 步骤 3 — 连点几下，确认它不会把机器点冒烟
1. 快速连点「🔄 刷新投影」5～10 次。
2. **预期**：第一次正常跳回总览页；**后面几次会出现一页写着「XXX 刚刚才刷新过」的提示**，
   明说「10 秒内已经重建过一次，本次没有重新计算」，并告诉你还要等几秒。
3. **不该出现的**：后面几次也悄悄跳回总览页装作成功——那样你会以为刷新了，其实没有
   （这正是收官审计抓出来并修掉的一条：**凡是没真重建的，都不许跳回总览页**）。
4. 等 10 秒以上再点一次，**预期**这次正常跳回，「生成于」才更新。

### 步骤 4 — 确认它没动别的库
1. 点 `canvas-vault` 的刷新按钮。
2. **预期**：只有 `canvas-vault` 那张卡片的「生成于」变了，`test-vault` 等其它库的数字和时间**一个都不动**。

### 步骤 5 — 点一个"没配过每日复习"的库，看它老实说话
1. 如果总览页上有 `test-vault` 这类从没跑过复习的库，点它的「🔄 刷新投影」。
2. **预期**：出现一页写着「刷新失败」的白页，上面有一条黄底的 💡 提示，
   大意是「该库还没为『每日复习』配置好: 缺 节点 与 .claude/scripts/decay_beta.py」，
   底下有「← 回到总览页」。
3. **不该出现的**：跳回总览页假装成功、或者一大段看不懂的 Python 报错堆栈（都有，但堆栈在提示下面，不是唯一内容）。

### 步骤 6 — 确认推送没被搞坏（次日早上看）
1. 第二天早上照常收 Bark 推送。
2. **预期**：推送照常来，内容合理。（本卡完全没碰推送链；这一步只是替你确认没有意外副作用。）

### 步骤 5b — 用手机 / 局域网打开时（如果你这么用）
1. 用手机浏览器打开 `http://<你Mac的局域网IP>:8011/api/v1/review/overview/page`，点刷新。
2. **预期**：照常工作。

## 如实边界声明（我做不到的 / 故意没做的）

1. **刷新出来的"推荐白板"可能与推送通知里的不是同一个板。**
   生产器在多个板打平时，会用 `board_last_recommended`（runner 记的"这个板上次哪天被推荐过"）来轮转。refresh **不读这本账**——读它需要 `send_bark.vault_key` 的命名规则，而 `send_bark.py` 在本车道硬边界之外。为了一个排序细节去耦合它不划算。
   影响面：只在多个板得分完全并列时出现（启动期、节点普遍没有 mastery 字段时更常见）。

2. **`rebuild_count` 是进程内计数**，后端重启或多 worker 时会归零。它是"去抖确实生效了"的证据，不是持久化审计账。

3. **去抖窗口固定 10 秒**，目前不可配置。

4. **跨进程并发的保证只到"单个文件的原子发布"**，不是"互斥"，也不是"md 与 json 配成一对"。
   - 单文件：宿主 launchd 跑批和你点刷新撞在一起，最坏结果是**后写的覆盖先写的**（两份都是完整合法的投影），
     不会是拼接损坏物。
   - **配对**：`今日复习.md` 与 `今日复习.json` 是分两次发布的，理论上可能一个来自这次、另一个来自上次
     （Codex 用确定性交错实测出来了）。我把窗口收窄了（先把两份内容都渲染好，再连着发布），但**没有消除**——
     真正的配对原子性要目录级换名或跨进程锁，而 VirtioFS 上锁的行为无法证明。见裁决点 D-6。
   - 也**没有**接上 launchd 那把 C1a 跨进程锁：接它要复刻 `send_bark.vault_key` 的命名规则，
     而 `send_bark.py` 在本车道硬边界之外。

5. **点「刷新投影」会执行那个库自己的 `.claude/scripts/decay_beta.py`。**
   这是生产器的既有设计（库自带衰减参数），宿主 launchd 每小时跑批同样在执行它——本卡**没有提升任何权限**，
   只是多了一个触发它的按钮。如果哪天你从别处拷来一个不认识的 vault 放进 VAULTS_ROOT，点它的刷新按钮
   就等于运行它带的那段代码。我已经做的收窄：子进程的环境变量改成白名单（后端的 API key 之类不再进去），
   并加了同源门（别的网页不能借你的浏览器发这个请求）。**根除做不到**，见裁决点 D-5。

6. ⛔ **这个端点没有挂本仓的写侧鉴权，而它本该挂** —— 这是本卡最需要你拍板的一条。
   - 本仓有成体系的约定：会写数据的端点都挂 `require_internal_api_key`（`sync` / `boards` /
     `memory` / `exam_sessions` / `system` 都挂了，现网的 key 也确实配了）。
   - **但那个依赖读的是一个自定义请求头，而纯 HTML 表单发不出自定义请求头。** 卡文硬要求
     "刷新按钮是纯 HTML 表单、零 JavaScript"。所以二者不可兼得：挂了鉴权按钮就必死（403），
     保住按钮端点就对"能连到这个端口的人"是敞开的。
   - 我加的同源门**只是防 CSRF**（防"别的网页借你的浏览器发请求"），**不是鉴权**——
     局域网里一条命令行请求可以随手把那两个头填成同源。别把它当成这条的答案。
   - 现实风险面：后端监听 `0.0.0.0`（既有登记项），所以同一个 Wi-Fi 下的机器能直接触发一次重建，
     并连带执行那个库的 `decay_beta.py`。→ **裁决点 D-7**。

   ⚠️ 附带更正：我在给 Codex 送审时说过"本仓全站无鉴权"，那是错的（我 grep 的范围太窄）。
   已在审查存档里更正。

   round-3 里 Codex 还指出我原来的同源门有个**新绕过点**：期望的来源是拿请求自己的 Host 拼的，
   用一个解析到本机的域名就能让三个头同时"合法"。已加 Host 白名单堵住（见步骤 5b）。

7. **本卡没有做 live 部署**（卡文明写"live 部署另行确认"）。上面 §开始验收前 的三选一就是这件事。

8. **卡文 (c) 里写的"并发 refresh × runner `--now`"，我用的第二个写者是 `daily_review_pick.py --write` 而不是 `daily_review_run.py`。**
   理由：撕裂门要证的是 `outputs/` 两文件的原子发布，而 runner 落盘走的正是 `picker.atomic_write` 这同一段代码；真跑 runner 会连带写 `backups/` state 并触发推送链，与本卡"不写 runner state"的裁判自相矛盾，且 `daily_review_run.py` 在硬边界之外。这条替换写在测试的 docstring 里，不假称跑了 runner。
