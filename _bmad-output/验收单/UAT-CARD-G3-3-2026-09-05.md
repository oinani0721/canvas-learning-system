### 判据为什么是**全文 sha256** 而不是只比 `last_review` / `attempt_count`

写点从 `s = open(NODE).read()` 那一刻起就把 `body` 留在内存里、发布时**整份覆盖**。
只比 revision 两字段的话，「用户在 Obsidian 里补了一段正文」这种改动 revision 确实没变，
于是覆盖照做、那段正文**静默消失**。
门 `test_cas_body_only_change_is_a_conflict` 锁这条；变异 **M5**（改成只比 revision）
把它打红 ⇒ 这条判据承重。

revision 两字段没有被浪费：它们负责把冲突**归因**说清楚（是别的评分插进来了，还是正文被改）。

### 两处冲突处置口径**故意不同**

| 块 | 冲突时 | 为什么 |
|---|---|---|
| 写分主块 | **fail-closed 零写** + 明说重跑 | 它的产物含它算了一整路的 frontmatter；自动重算会拿**内存里的旧正文**盖掉别人刚写的编辑——那是把一种丢数据换成另一种 |
| A3 增量归纳块 | **自动重读重算**（≤4 轮） | 它的产物只由「盘上当前 body + 本次 callouts」决定（逐条按内容查重后 append），重算不丢任何人的改动 |

「重跑」在主块这一侧**就是**重读重算：重跑会重新拿锁、重新读盘、重新算，
而 write-ahead + `event_id` 幂等保证它收敛。
门 `test_cas_conflict_refuses_and_rerun_converges` 把这一整圈走完：
外部写者插队 → rc≠0 且节点未推进 → 换回正常 bridge 重跑 → rc=0、`attempt_count=1`、
账本仍 1 行、外部写者那段正文**还在**、validator rc=0。

## 二 (b) 跨进程锁：粒度与超时口径

| 锁 | 目标 | 粒度 | 超时 | 覆盖区间 |
|---|---|---|---|---|
| per-node 写锁（`quiz-answer` 主块 / A3 块） | `<VAULT>/.locks/node-<sha1(realpath(NODE))[:16]>.lock` | 单个节点 | **60 s** | 「读节点 → 读账本 → 算 → 发布」整段，到进程退出 |
| 账本追加锁（`quiz-answer` 主块） | `learning_events.jsonl` 本体的 fd | 单个 vault 的账本 | **30 s** | 「LF 守卫 → write → fsync」 |
| 账本追加锁（`start-exam-board`） | 同上 | 同上 | **30 s** | 「查重 → write」（该块失败契约不变：写失败不阻断出题） |
| 账本追加锁（`learning_event_log.append_event`） | 同上 | 同上 | **30 s**（`LEDGER_LOCK_TIMEOUT_S`） | 「查重 → LF 守卫 → 写」整段 |

`threading.Lock` **保留**为进程内快路径，并在定义处写明它**不是**并发防线
（账本真实写者有**四方**：backend 进程、quiz-answer 的独立 `python3`、start-exam-board、
ai-linked-doc —— 最后一个**未参与**本锁协议，理由见 §十.12）。

### 三条选型理由（都在代码注释里，且都实测过）

1. **锁必须在「读」之前**，不是在「写」之前。两个进程若各自读到同一份旧 frontmatter，
   之后无论谁先发布，后发布的那份都是按**旧基线**算出来的。
2. **用 `fcntl.lockf`（POSIX 记录锁）而不是 `flock`**：`flock` 锁的是 open file
   description，同一进程用两个 fd 锁同一文件会**自锁死**——而 `test_g3_2` 门⑬ 会在
   pytest 进程里 `exec` 这段静态块。本机实测：同进程二次 `lockf` 0.000 s 通过，
   跨进程真阻塞 1.49 s。
3. **per-node 锁必须落在专用锁文件上**：POSIX 记录锁在本进程**任意一个** fd 关闭时
   整体释放——若拿节点文件本体当锁目标，紧接着那行 `open(NODE).read()` 关闭时锁就没了，
   得到一把看起来存在、实际不锁任何东西的锁。

**超时不静默降级**：取不到锁一律 fail-closed（写点 `SystemExit` 零写 / `append_event`
返回 `False` + `logger.error`），不存在「没锁也写」的分支。
门 `test_lock_exclusive_times_out_instead_of_writing` + `test_append_event_refuses_when_ledger_locked` 锁这条。

### ⛔ 实现过程中自查抓到的一个真缺陷（BLOCKER 级，已修，附回归门）

三处账本锁**第一版全是坏的**，而当时六条负控变异全绿、三道锁门全绿。

POSIX 记录锁的释放语义是**按「进程 × 文件」**，不是按 fd：
本进程关掉指向该文件的**任意一个** fd，这个文件上的全部记录锁就整体消失。
于是查重扫描里那句人畜无害的 `with open(path) as f: ...` 一收尾，锁就没了 ——
后面的 `os.write` 是**裸奔**的。

- 这条语义我在 per-node 锁的注释里写对了（所以那把锁用的是**专用锁文件**），
  却在账本锁上自己踩了进去 —— 同一条规则，只应用了一半。
- **既有三道锁门为什么全绿**：它们测的都是「取锁那一刻」
  （`test_lock_exclusive_times_out_instead_of_writing` /
  `test_append_event_refuses_when_ledger_locked` / `test_writer_waits_for_held_ledger_lock`），
  没有一道测「持锁**全程**」。
- **本机实测确认**（2026-09-05, macOS）：持锁后做一次无关的 `open`+`close`，
  另一个进程立刻就能拿到同一把锁。
- **修法**：持锁期间只用 `os.lseek` / `os.read` / `os.write` 操作那**一个** fd
  （`learning_event_log._read_all()`；两个 SKILL 块的 LF 守卫与查重同改），
  fd 从 `O_WRONLY` 改为 `O_RDWR`。
- **补的三道门**：
  `test_posix_record_lock_is_released_by_any_unrelated_close`（把 OS 语义本身钉成门）、
  `test_read_all_does_not_drop_the_lock`、
  `test_append_event_holds_lock_across_the_whole_scan`（真行为门：父进程在子进程
  临界区内轮询抢锁）+ 变异 **M7** 专杀它。
  写点侧那个窗口只有几十微秒、行为门无法确定性复现，故用形态门
  `test_skill_ledger_section_opens_no_second_fd` 防复发，**并如实标注它是形态门**。

⚠️ 这道行为门自己也出过两次假判定，都已修并留痕：
① 首版固定 `sleep(0.15)` 后才开始探针，而临界区只有 49 ms ⇒ 探针跑了 0 次，
   被门自带的「本门是空的」前提断言抓住；
② 第二版把「抢到锁」直接判成中途丢锁 —— 而子进程**正常收尾**时也会先释放锁
   再去写 done 文件，那一瞬间同样能被抢到（假阳性）。
   真判据是**抢到之后它还剩多少活**：正常收尾只剩毫秒级，中途丢锁则后面还有约 200 ms。
③ 形态门首版被**自己生产代码注释里引用的反面教材字符串**命中（判据自指），
   改为剥掉注释行再扫。

### ⚠️ 一个如实声明的判据盲区

per-node 锁在**任何**一次运行开头就 `makedirs(<VAULT>/.locks/)`，**包括后来 fail-closed
零写的那些运行**。既有的「零写」断言（`test_g3_2` 的 `_write_face`）比的是
**节点 sha + 账本 sha**，`.locks/` 不在其中 ⇒ 那些门**看不见**这个新增目录。
本卡的判断是：锁文件是运行期产物、内容无意义、已进 `.gitignore`，
不构成「零写」语义的破坏；但「零写门管不到它」这件事本身是真的，写在这里而不是藏起来。
（这一条也已列进 Codex prompt 的第 2 问，供人审复核时对照。）

### 五.1 两路独立审查的发现与处置（全部已修）

| 编号 | 发现（都带对方的实测复现） | 处置 |
|---|---|---|
| **H1** | 线程锁先退出、`os.close` 后执行 ⇒ A 的 close 撤销 B 正在持有的 POSIX 记录锁（同进程记录锁是 per-process，B 取锁**不阻塞**）。实测两调用都返回 True、账本同 ID 两行 | open→lock→scan→write→close **全进线程锁**；新增顺序判据门 + M8 |

| **M1** | CAS 冲突路径不满足「节点+账本零写」——write-ahead 已追加一行 | 拒因措辞改为「**已入账待恢复**」，不再自称零写 |
| **M2** | 三条防线无负控；A3 两道门确定性漏检 | 负控 7→14；A3 锁门改成真 lost-update 门（持锁方**整份重写**而非追加）+ 新增 A3 CAS 门 |

| **M4** | SURVIVED 时脚本仍 rc=0 | 退出码要求「有选中 + 无锚漂 + 全 KILLED + 还原干净 + 无残留」 |
| **L1** | 「flock 同进程自锁死」这条选型理由被实测**证伪**（旧 fd 关闭后即可取得；全仓只有一处同进程 exec 且未参数化） | 注释改成经实测的真实理由，并写明 per-process 语义不能掩盖 fd 生命周期问题 |
| **L2** | CAS 自称「全文字节 sha256」，实测 LF→CRLF 时原始 sha 变了而判无冲突 | 改述为「文本规范化后的内容 sha256」，并说明为何有意如此 |
| **L3** | 「零写」claim 过宽（`.lock` 仍会创建）；形态门可被别名绕过 | 措辞收窄；形态门如实标注为形态门，其承重面由 backend 侧真行为门 + M7 补上 |

### 五.2 第一版里被证伪、现已改正的说法

1. 「**M1 拆锁 → 并发门红 ⇒ 锁承重**」——**不成立**。当时红在 `rc == 0` 这条断言上，
   而 rc≠0 是**仍在场的 CAS 层**贡献的；卡文声称的 lost-update 断言（`attempt_count == 2`）
   从未被打红过。这是**带层变异 + 假杀**。现已把状态不变量提到 rc 断言**之前**，
   M1 现在红在 lost-update 判据本身。
2. 「三个账本写点已上锁」——**不完整**。`ai-linked-doc/SKILL.md` 是**第四个**写者，
   完全不参与锁协议（见 §十.12 的处置与理由）。
3. 「CAS 保住并发正文编辑」——**说宽了**，见 H6。
4. 「CAS 冲突 = 节点+账本零写」——**说宽了**，见 M1。
5. 「flock 会自锁死」——**事实错误**，见 L1。

重跑一次就好——分数不会重复记。
