## 一 本卡做了什么（对应卡文 (b)~(e)）

### (b) Web 手动刷新走 CLI 时带 `board_done`

从前浏览器点「重新算一遍」时，`_run_pick` 的 argv 里没有 `--state`，完成账根本流不进生产器 —— 页面把板折进「已完成」区了，榜首却纹丝不动。

- `_run_pick(script, vault_dir, state_file=None)` / `_rebuild_projection(..., state_file=None)` 加性参数；非 None 时 argv 追加 `--state <path>`（原五项不动、不改序）。
- `review_overview_refresh` 用新增的 `_refresh_state_file()` 取 runner 的 state 路径。**读松**：runner 不可达 → 不传，响应加性字段 `state_passed: false`，刷新本身**不** 503。
- `_rebuild_projection` 的写侧承诺 ② 改写：不再是「不传 `--state`」，而是「传 `--state`，但本函数一个字节都不往 state 里写」；原「代价如实登记」段删除（那个代价已经付清）。
- pick `main()` 从**同一次** JSON 解析里取 `board_last_recommended` 与 `board_done` 两个键，`--state` help 同步更新。

**顺带修掉两个既有缺陷**（都是本卡把 refresh 接上 state 之后才可达的新输入面）：
- 顶层非 dict 的 state（如 `[]`）会让 `.get` 抛 `AttributeError`，整轮生成崩掉 → 刷新 503；
- 值错型（`{"board_last_recommended": {"A": 7}}`）会让排序键拿 `7` 和另一块板的 `""` 比大小 → `TypeError`（Codex round-3 M3）。
  现在 `_str_pairs()` 逐值过滤成 `{str: str}`，与读侧 `_read_board_done` 同一条纪律。

### (c) RMW 窄窗 = 专用文件锁 + 锁内三方合并

- **锁**：`runner.state_lock_path(vault) = BACKUPS / "daily-review.<key>.state.lock"` —— **文件**锁，与 `push.sh` 的 mkdir **目录**锁 `.daily-review.<key>.lock` 既不同名也不同形，与 `_state_tmp_path` 的 `*.tmp` 不同形。
- **原语是 `fcntl.flock` 不是 `lockf`**（Codex round-4 H1 根治，见 §五）。
- **可重入**（卡文定死的方案 ①）：模块级 `_STATE_LOCK_FDS: {resolve 后路径 → [fd, depth]}` + per-path `RLock` + `threading.local` 记本线程持有；`save_state` 检测到本线程已持锁就复用那把 fd，**不再 open/close 锁文件**；未持锁时先取锁再自调一次（而不是把主体包进 `with` —— 那两行 `O_EXCL|O_NOFOLLOW` 与 `os.replace` 是 Y2-B 的修复面，卡文钉成逐字节不动，换缩进就是动了）。
- **`load_state` 的读取 / 损坏判断 / 隔离改名整段也在锁内**，且隔离前锁内**再读一次**（Codex round-2 H1 + round-3 残余）。
- **合并律**：`load_state` 把**归一化之后**的磁盘内容深拷贝为 `base`；`save_state` 锁内重读磁盘为 `theirs`；某顶层键 `mine != base`（含被删）⇒ 写 `mine`，否则 ⇒ 写 `theirs`；`theirs` 缺键则写 `mine`。`schema_version` 另走**单调取大**。base 缺席（这条路径本进程从没 load 过）或 `theirs` 读不出 ⇒ 整写 `mine`（= 本卡之前的行为，既有「改了就写」语义逐字节不变）。
- Web 侧 `_write_board_done` / `_write_board_undone` 的 `load → 改 → save` 三步在同一把锁内；既有 per-file `threading.Lock` 保留为第二层。

## 二 §Y2-B 审后 `+471/−11` `save_state` 重写复审结论（卡文 (f) 单列）

Codex 六轮里对这段的结论，逐条抄原文要点：

- **round-1 起每轮都答「保留」**：`O_EXCL|O_NOFOLLOW`、失败后尝试 unlink、`os.replace` 原子发布**均保留**；判据 `git diff BASE HEAD -- scripts/daily_review_run.py | grep -c '^-.*O_EXCL'` = **0**，`os.replace(tmp, state)` 删行同样 = 0（§三.5）。
- **round-1**：「普通独立锁 inode 下，tmp 的 open/close 不释放锁；整体锁安全存在 H3」→ H3 已修（O_NOFOLLOW）。
- **round-2**：「正常 tmp 是独立 inode，其 open/close 不释放锁；整体锁独立性仍有 H2」→ H2 已修（nlink）。
- **round-4（换 flock 之后）**：「唯一名、`O_EXCL|O_NOFOLLOW`、失败清理、`os.replace` 仍在；成功新建的 tmp inode 独立，**tmp 自身的 open/close 不释放锁**。」
- **round-6（末轮）**：「未找到新的失锁、并发丢账或测试写入 live 业务数据的可达路径。」
- 唯一保留的观察（LOW，登记不修）：**unlink 自身失败仍可能留下残渣** —— 这是 Y2-B 当时就登记过的既有边界，本卡未改也未加门。

**结论**：Y2-B 审后那两个 commit 的 `save_state` 重写在叠加本卡的锁与合并之后，四条性质全部仍成立；本卡对它的唯一改动是在其外层加锁与合并，那两行逐字节未动。

### 五.1 四轮 HIGH 的共同根因与根治

round-1 H3 / round-2 H2 / round-3 H1 / round-4 H1 是**同一个根因的四种形态**：POSIX 记录锁（`fcntl`/`lockf`）按「进程 × inode」释放 —— 本进程对同一 inode 的**任何一次**额外 open+close 都会把锁整个丢掉，而登记表毫无察觉。四种利用方式：锁是软链指向 state / 锁是 state 的硬链接 / 反向软链 `state→lock` / 跨库别名 `A.state.json → B.state.lock`。

前三轮都在**逐条堵路径形态**（`O_NOFOLLOW` → `st_nlink` → inode 比对）；第四轮认识到这堵不完（只要有任何别名让某次读盘碰到锁 inode，锁就没了），改为**换锁原语**：`fcntl.flock` 的锁绑在**打开文件描述**上而不是 inode，这一整类在原语层面消失。三条形态检查保留为防御深度（它们仍挡住 `O_CREAT` 在库内造文件那半条）。
**代价如实登记**：flock 在 NFS / 网络盘上语义不同（本机 APFS 实测为准），不支持字节范围（本模块不需要）。
