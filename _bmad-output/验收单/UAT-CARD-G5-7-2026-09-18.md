## 2 做了什么

**`undo_journal.py`（共用模块，不认识收件箱也不认识白板）**

- `BatchJournal(work_dir, batch_id, root=, fingerprint=)` —— 一个批次 = 一个目录 =
  一本账。`root` 是创建目录的上界；`fingerprint` 让这本账**绑死在某个 vault 上**。
- `backup(src)` —— 动手**之前**的逐字节快照，拷完两侧比 sha。撤销的真相源是它，
  不是「把写进去的东西逆解析剥掉」。
- `plan()` / `commit()` —— 先落 `planned` 再动手，动完落 `done`。一行一条记录，
  单次 `O_APPEND` write + `fsync`；坏尾行 / 缺换行的尾行都会先封口再追加。
- `undo()` —— 逆序还原，四种入口（已 done / 已动盘未 done / 已还原未记账 / 已记
  undone）。`move`/`recycle` 搬回原路径并还原修改时间与权限位；`copy`/`link` 的产物
  **移进** `recycle/undone/`。目录时间只在「能证明这期间没人动过」时才回写。
- `write_provenance()` —— 溯源 frontmatter，全程 bytes 进 bytes 出、唯一名 tmp +
  `os.replace` + 回写 mtime 与权限位；看不懂结构的文件一个字节都不动。
- `write_pair_atomically()` —— 回执成对发布：两份都写好 tmp 才双双就位，不预建
  0 字节产物、全程零 unlink。

**`inbox_apply.py`（执行侧 CLI）**

准入次序铁律（全部守卫跑完**再**碰工作目录）：vault 非 symlink → preview
`schema_version == 1` 且 `vault_fingerprint` 一致 → decisions `schema_version == 1`
→ 工作目录不在收件箱内 → 每条 `stable_id` 已知且不重复、且与账上同序号对得上 →
源路径祖先链无 symlink → 源材料新鲜度（已完成 / 可续跑的除外）→ `target` 白名单
→ **落点归属**（已存在的落点必须能证明是本批次造的）→ `recycle` 双重显式确认。

任一不过 = **整批拒绝**，连 `outputs/` 这一级都不建出来。

### 四个设计取舍，写下理由

1. **祖先链 symlink 守卫复用 `split_preview.assert_symlink_free`，不自带第二份。**
   理由与 `inbox_preview.py:266-290` 的 docstring 同一条：「自己简单写一下」等于在
   安全面上开一个没人审过的旁路；两份手抄的实现必然漂移。
2. **回执的成对发布**改为自带 `write_pair_atomically`，**不**复用
   `write_pair_atomically_checked`。后者先 `O_CREAT` 把两个目标建出来，失败时按
   路径 `unlink` 回滚 —— 并发下会删到别人刚放上去的同名目录项（Codex round-1 #12）。
   自带版本两份都写好唯一名 tmp 再双双 `os.replace`：不预建 0 字节产物、零 unlink。
   代价如实：两次 `os.replace` 之间被杀仍可能只就位一份。
3. **`fmt_utc` / `parse_now` 从 `inbox_preview.py` 加载复用。** preview 的
   `mtime_utc` 是它格式化的，执行侧要拿实盘 mtime 去比，格式必须逐字同源。
   （`vault_fingerprint` 在 preview 里是内联算式不是函数，只能重算 —— 一致性由
   行为门反证：真 preview 必被接受、换 vault 必被拒。）
4. **撤销用备份覆写，不做「把 provenance 文本剥掉」的逆解析。** 逆解析遇到用户
   原本就有同名键、或 YAML 缩进变体就会失真；备份是逐字节副本，还原结果可验证。

- 判据：注入同样的两处变异后，该门**变红**（`1 failed`）。跑前 / 还原后 `1df73596…` 逐字同。

> ⛔ **改对诱饵之后，同一条用例里另一条断言立刻变成恒红** —— `leftovers` 的过滤条件是
> 「名字里含 `undo-journal-tmp`」，而正确的诱饵**自己**就满足它。这是「换了正确输入之后
> 才显形的连带影响」：一个恒真的断言被修好，隔壁那个一直沉默的断言就开始说话了。
> 修法是把诱饵本身排除出残片集合。

### 4-B 用户体验（零技术词）

**一句话**：盘点单上我勾了哪些要归档、哪些要放回收站，它一件一件照做，做完给我一张

**felt-sense**：

- 最让我松一口气的是「删」这件事被做成了**两道关**。我得先说「这一批允许放回收站」，
  再在那几件上各自点一次头，少一样它就整批不动 —— 不是弹个框问我「确定吗」，而是
  真的什么都没发生。而且所谓「删」其实是挪进一个回收的地方，原样躺在那儿。
- 第二是**撤销**。我最怕的不是它做错，是做错之后回不去。现在撤销之后，连每份文件
  「上次修改是什么时候」都和动手前一模一样 —— 不是「内容看起来一样」，是真的一样。
- 第三是它**不含糊地报完成**。中间卡住了它就停下，明明白白告诉我卡在第几件、为什么、
  已经做完几件；我把卡住的原因弄好再跑一次，它只补没做完的那几件，不会把做过的又
  做一遍。
- 有一条我一开始觉得烦，后来觉得对：如果我在盘点之后又动过收件箱里的材料，它会拒绝
  执行，让我重新盘点一次。拿着一张过期的单子干活才真的吓人。
- 还有一条是我完全没想到、但看完很安心的：如果我在它做到一半的时候自己往那个位置

一个只有这道守卫能拦下、别的守卫都放行的输入。分不出来时，就用点名变异逐条问

## 6.12 守卫覆盖普查（102 道）—— 以及我差点报错的那个数字

§5 里登记过一条未证明项：「本卡自己的门里曾有 8 条断言不了它声称的事，但 128 条里
还有多少是这种情况，**没做过系统性普查**」。这一节把它做了。

**做法**：AST 枚举两份脚本里每一道守卫（`die(...)` / `raise JournalError(...)` /
`raise OSError(...)`，共 **102 道**），逐个中和成 `pass`，跑全套 128 条门（`-x` 快速判
「有没有门会响」）。全程在**镜像树**里，仓库一个字节都不碰，每次变异后断言还原逐字同。
用时 46.3 分钟。存档 `evidence-g57/guard-sweep-20260919T060730.txt`（首部有结论更正）。

**原始结果**：102 道里有 **69 道**中和之后整套仍全绿。

### ⛔ 但这个数字不能按字面报 —— 我的脚本给它贴错了标签

脚本把「中和后仍全绿」标成「**无门覆盖**」。那是错的 —— 名单里赫然有
`target 含 '..', 拒绝越界`、`账上的路径含 '..'`、`rel_path 不是 vault 内的相对路径`
这些**我一小时前刚配过门、并且在归档树上验过会红**的守卫。

**实测验伪**（同一棵镜像树）：中和 `inbox_apply.py:227` 的「target 含 `..`」之后，
`test_target_escape_variants_are_rejected_zero_write` 与
`test_target_whitelist_is_case_insensitive` **两条门仍然全绿** —— 也就是说 `../外面`
这个输入**仍然被拦下**了，只是被**后面一道**守卫（`:239` 的 realpath 边界判定）拦的。

**正确的结论只能写成**：

> 对这 69 道守卫，**没有任何一条门的判定依赖于它单独存在**。

这和「没有门覆盖那条性质」是两回事。本卡的准入是**有意分层**的
（词法 → realpath → 祖先 symlink 三层各拦一次），所以单点中和不改变任何门的判定，属预期。

### 这个普查分不出的两件事（如实声明）

- **(a) 冗余纵深**：中和它之后，**另一道**守卫仍拦得住同一个输入（上面实测的那一类）。
- **(b) 真空洞**：中和它之后那个输入就过去了，只是**没有任何门喂过那个输入**。

要分开，必须为每道守卫构造一个「恰好只有它能拦」的**独占输入** —— 那等于给 69 道守卫
各写一条门。**本卡没有做**，所以 69 里各有多少属 (a)、多少属 (b)，**至今未知**。

### 它确实说明的一件真事

**这 69 道守卫里任何一道被后人删掉，现有 128 条门都不会响。** 那是**维护期**的风险
（下一次重构、下一张卡复用 `undo_journal.py` 时），不是当下的正确性缺口。

### 教训：同一个坑，一小时内踩了两次

L11 那道门的单点变异不红，我当时就写下了「并列同层判据 ≠ 换了一层：单点变异证明不了
一道被双重守卫保护的门」。然后**我把同一个单点变异手法放大到 102 道守卫上跑了 46 分钟**，
还差点把「69 道守卫没有门」当成结论报出去。

写下一条教训 ≠ 在下一个场景里认出它。判据的**方向**要在跑之前就想清楚：
「中和后全绿」推不出「没有门」，只能推出「没有门**单独依赖**它」。

### ⛔ 又是标签问题：「整组仍全绿」有三种含义，处置完全不同

**备份仍在**」，并在 docstring 里写明不预设是哪一层开火。

### 这一节踩的三个坑（都验伪后修正，写下来免得后人重犯）

1. **第三轮报「基线不是全绿」是假的** —— 我在上一轮 sweep 没跑完时就启动了下一轮，
   两轮在**同一棵镜像树**上互相踩，后一轮的基线跑在前一轮的变异态上。
2. **等待器无限空转** ×2 类：`until ! pgrep -f "<脚本路径>"`（`pgrep -f` 匹配到**等待器自己**
   的命令行）、`until grep -q "<成功标记>"`（任务**失败**时输出里只有 Traceback，没有那个标记）。
   前者让 5 个等待器转了 46 分钟，后者让 2 个等待器等一个已经报错退出的跑。
3. **探针自己吞掉了被调进程的失败** —— `subprocess.run(..., check=False)` 且不看 stderr，
   于是真正的原因（macOS 的 `mkdtemp()` 返回 `/var/folders/…` 这个 symlink，
   而 `inbox_preview` 拒绝含 symlink 组件的输出目录）被埋在一句 `StopIteration` 底下。

### 教训

**判据的方向要在跑之前想清楚。**「中和后全绿」推不出「没有门」——
逐道中和时它推出的是「没有门**单独依赖**它」，整组中和时才逼近「没有门**盯着**它」，
而即使到了那一步，还要再分「真放行 / 退化成崩溃 / 死分支」三种。
我在 L11 上刚写下「并列同层判据 ≠ 换了一层」，转头就把同一个单点手法放大到 102 道守卫上
跑了 46 分钟 —— **写下一条教训 ≠ 在下一个场景里认出它**。

⛔ **HIGH-1 与 MEDIUM #2/#3/#7 是同一个根因：我把 `_dir_retime_plan` 的形状违规写成了
fail-closed 抛出。**

我混淆了两件事：

| | `src` / `dst` / `backup` | `dir_mtimes` 的键 |
|---|---|---|
| 驱动什么 | **用户材料的搬动** | 收尾那句 `os.utime`（装饰性） |
| 放行的后果 | 材料被搬出 vault | 某个目录的 mtime 没回去 |
| 正确响应 | **拒整批**（fail-closed） | **登记跳过** |

把前者的口径套到后者身上，换来的是：

1. **整批撤销被否决** —— 用户材料卡在落点，CLI 无任何跳过开关 ⇒ 这一批再也撤不回来，
   而 stderr 还打「修好原因后再跑一次只会补做剩下的」这句**不实**的恢复建议。
2. 抛出点落在**会写回执**那一支 ⇒ 把上一次成功撤销留下的 undo-receipt 原地换成
   「共 0 件」—— **M5 那条不变量是前几轮专门修好的，被我这次整改重新打破**。

**安全性从来不依赖那个抛出**：跳过就不会有任何 `os.utime`，越界写照样发生不了。
真正承重的是 realpath 正向包含判定。所以改回「登记跳过」是**严格更优**：安全性不变，
可用性不再受损，且与同 commit 里 `undo()` 收尾循环对同一输入类的处置一致
（原先两处对同一输入给出相反答案）。
