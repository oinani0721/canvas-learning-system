## 一 这张卡到底做了什么

用户裁定 D-18 把「今天」钉在**机器本地时区**，归日靠两份同源的 TZ 解析器
（`scripts/local_tz.py` ↔ `backend/app/core/display_tz.py`）。第十四批 T3-A 在车道上把解析器
重写到与 C 库接受域对齐，但 Codex r12 仍留 4 条 HIGH、末 commit 未送审 ⇒ 整卡不合，
**主干今天跑的仍是第十三批 U6-A 那版解析器**。

本卡三件事：

1. **移植**（commit ①）：把 `a8cefab4` 的五文件代码面原样落到 `9c4e7e82` 之上，一行不改。
2. **去 3.11+ 正则语法**（commit ②）：R2 用占有量词 `[0-9]++` / `*+` 与原子组 `(?>…)` 修四条
   HIGH，但那是 Python **3.11+** 专有语法，而 launchd 链有一条兜底解释器路径用系统自带的
   `/usr/bin/python3`（本机 **3.9.6**）。那一版在 3.9.6 上 **import 即 `re.error`**。
3. **三件尾巴**：`daily_review_pick.py` 模块级 `_DISPLAY_TZ` 改每次现取；负控 runner 入树；
   补一处 r12 H4 的漏网入口。

### 5.1 四条 HIGH 在移植时就已经绿了 —— 本卡的贡献是「保住」它们

| H2 冒号偏移误判 dst | `AAA1:` | 拒（UTC） | 拒 | ✓ |

| H4 长数字未捕获异常 | `AAA`+4300×`0`+`1` | 收（−01:00） | 收，冬夏均 −01:00 | ✓ |
| H3 灾难性回溯 | `'A'+'١'*n+'+'` | — | n=202 0.000008s，比 ≤1.6 | ✓ |

所以这四条的修复**归 R2 commit**，本卡负责的是：**在撤掉 3.11+ 语法的前提下让它们仍然成立**，
并用 (g) 的回归门 + (k)/negctl 的变异证明它们真被锁住。这个归属如实写在测试文件的段首注释里。

### 5.2 线性性质换了承载层 —— 所以计时门在本卡是承重判据

平方回溯的根因不是「量词无界」，是**「std 名与 dst 名共用同一个字符类，而夹在中间的
`std_off` 可选」**：两段能任意瓜分同一串名字字符，std 有 n 个退让位置、每个位置 dst 再扫
一遍剩余 ⇒ O(n²)。

- R2 的解法：占有量词 —— **引擎**层面禁止回溯。代价是 3.11+ 语法。
- 本卡的解法：`std_off` 在正则里**必填** —— **文法**层面消除歧义分割点。std 名的贪婪终点
  唯一（必须吃到第一个 `[0-9+-]`），退到更短位置时 std_off 首字符检查立刻失败 ⇒ 每次回溯 O(1)。

**「改必填不改变接受域」有判据不是推断**：校验层 ⑥ 本来就对空 `std_off` `return None`，所以
「匹配成功后被 ⑥ 拒」与「根本不匹配」两条路返回值相同；31 万条样本在**当时**语义分歧 0（⚠️ 该数字已被 r1 修复作废，更正见 §五.25），
3.9.6 与 3.14.4 两解释器判定指纹逐字节相同。

⇒ 计时门（negctl 段 `H3QUANT`：把 `std_off` 改回可选）是**唯一**能证明平方没被放回来的东西。

### 5.3 卡文的计时判据本身有误，已更正并登记

卡文写「n=202/404/808 的耗时比 ≤3」，核心裁判 2 明确成 `808/202 ≤ 3`。但**长度从 202 到 808
是 4 倍，真正线性的实现该给 ≈4**。本卡基线实测（min-of-5）：

| 判据 | 基线（线性） | `std_off` 改回可选（平方） | 能否区分 |
|---|---|---|---|
| `t(808)/t(202) ≤ 3` | **3.55** ⛔ 误红 | 13.49 | ⛔ 门限比线性值还紧 |
| 相邻比 ≤ 3 | 1.75~1.92 ✓ | 3.46~3.97 ⛔ | ✓（但平方侧余量仅 15%） |
| **n=3232 ≤ 0.05 s** | 0.000094 s（余量 ≈530×）✓ | 0.527 s（超标 ≈10×）⛔ | ✓ **最可靠** |
| n=808 ≤ 0.05 s | 0.000028 s ✓ | 0.035 s ✓ | ⛔ 抓不住（平方态仍在门内） |

本卡的处置：保留卡文原始绝对门 `n=202 ≤ 0.05s`；把比值按**相邻比**读（这是让「耗时比 ≤3」对

（微秒量级上调度噪声与被测量同量级 —— 同一份代码单次采样实测给出过 2.43 与 3.80 两个值）。

### 5.4 三段 R2 存活变异的真因：不是空操作，是「拆错了层」

卡文推测存活是「变异是空操作」（old==new 或 AST 没变）。本卡实测**三段都不是**：

| 段 | R2 拆的位置 | 实测结果 | 真因 |
|---|---|---|---|
| `COLONPOSIX` | `display_tz()` 的 `if not env_tz.startswith(":")` | 改成 `if True:` 后 `parse_posix_tz` 层与 `display_tz` 层**都零观测差异** | 它与正则第三支的 `(?![<:])` 前瞻**互为冗余**，拆任一层都看不见 |
| `ASCII` | ⑤ 的 `all(x.isascii() and x.isdigit() …)` | 删掉后零观测差异；**但**把正则 `[0-9]` 放宽成 `\d` 之后它**会**接住，删了就接不住 | 它是真正的**纵深第二层**，第一层（正则的 ASCII 数字类）太严，平时轮不到它说话（192 条匹配样本触发 **0** 次） |
| `RULEA` | 规则字段的 `isascii()` | 同上 | 同上 |

**方法论**：变异「存活」有三种可能 —— 门真有缺口 / 变异是空操作 / **变异拆的不是承载那条性质
的那一层**。第三种最容易被读成第一种，然后有人去给一道本来就有效的门再加一层，缺口却仍在
别处。本卡的处置：
- `COLONPOSIX` 的 negctl 段改打正则前瞻、oracle 打在 `parse_posix_tz`（那是它单独承载的一面）；
  (k)① 的端到端负控则**同时拆两处**（那两处的合取才是「一层」），让 `test_tz_path_forms_match_libc` 真红。
- `ASCII` / `RULEA` 的 oracle 先把**该模块自己的**正则放宽成 `\d` 再问第二层 —— 这样测到的
  恰好是它们各自承载的东西。

### 5.4-bis negctl 的 9 段变异清单（每段红在**点名**的那个 oracle）

| # | 段 | 拆的是什么 | 红在哪个 oracle | 守的性质 |
|---|---|---|---|---|

### 5.5 发现并修掉一个 R2 漏网的真缺陷（r12 H4 只修了一半）

r12 H4 原文说「偏移、切换时刻、M/J 规则的多个数字字段均可触发」。R2 只在

### 5.11 negctl 的一个已知弱点（自我对抗审查，如实登记）

`test_mutation_is_caught_by_its_named_oracle` 的主判据是
`with pytest.raises(AssertionError): oracle(mutant, mutated_src)`。
它验证的是「这个 oracle 对变异体抛了 AssertionError」，但**不验证抛的是哪一条断言**。

已经排除的两类假绿：

- **oracle 本身坏了** → 预检④（原件必须先让同一个 oracle 通过）会先红；
- **变异体语法坏了 / 加载失败** → `_load_source` 抛的不是 AssertionError，测试 **ERROR** 而非 pass。

**仍未排除的一类**：同一个 oracle 内部有多条断言时，变异可能红在**不是它设计要红的那一条**上。

若某个变异让后者失败，这道门同样记 PASS。

**为什么本轮不加固**：加固办法是给每段变异声明一个 `expect_msg` 关键词、断言它出现在失败
消息里。改这一处要连带重跑承重套件（negctl 在套件里，单跑不够）。按协议，审后改代码必须
再送一轮 Codex 并在当前 HEAD 重跑全套裁判 —— 所以把它留到 Codex 明确点名时一次做完，
而不是先改一遍再被指出别的、改两轮。**这一条已写进 Codex prompt 的问题 ③ 主动请对方核**。

### 5.12 ⛔ 第二跤：我给这张卡自己引入了一个测试间污染

### 5.13 ⛔ 第三跤：负控的 trap 还原用了相对路径，差点把变异态留在生产文件里

(k)① 第一版的 trap 写作
`trap 'git show HEAD:scripts/local_tz.py > scripts/local_tz.py; …' EXIT`。
trap 在**子 shell 退出时**执行，那时 cwd 已经是 `backend/`（跑 pytest 时 `cd` 进去的）：

- `> scripts/local_tz.py` 在 `backend/` 下**创建了** `backend/scripts/local_tz.py`
  （`>` 会建文件，所以**不报错**），而真正的生产文件留在**变异态**；
- `> backend/app/core/display_tz.py` 指向不存在的 `backend/backend/app/core/`，
  只有这一条喊了 `no such file or directory`。

**教训**：还原命令的 cwd 必须与写它时的假设一致；`>` 的「静默创建」让路径错误不表现成报错。
与记忆里「`cd backend` 后再写 `-- backend/app/x.py` 指向不存在的 `backend/backend/…`」同族。

### 5.15 一条贯穿本卡的教训：「两跑不可比」，我犯了两次

### 5.18 本轮的改法：不再「被指出一处补一处」，改为按结构枚举

既然一个形状能出现两次，就该问它会不会出现第三次。本轮**按正则结构枚举**了全部候选：
8 个命名组，任意相邻两组若能吃同类字符且中间项可空即为候选分割点。

| # | 分割点 | 为什么封住 | n=3232 实测 |
|---|---|---|---|
| ① | std / dst（名字类） | 中间 `std_off` **必填** | 0.000053 s |
| ② | std_off / dst_off（数字） | 中间 dst 名可空 ⇒ 本轮改成「空名须跟符号」 | 0.000255 s |
| ③ | stime / etime | 中间有必填的 `,`+start/end | 0.000190 s |
| ④ | start / end | 中间 `,` 必填 | 0.000166 s |
| ⑤ | std_off 内部三段 | 冒号分隔、段数 ≤3 | 0.000018 s |
| ⑥ | dst 名 / dst_off | 字符类互斥（名字类排除数字） | 0.000356 s |
| ⑦ | 引用名内部 | 单段，无相邻同类 | 0.000025 s |
| ⑧ | 规则 M 内部小数点段 | `.` 分隔、段数固定 3 | 0.000083 s |

**8 种全部线性**（比值 4–15，线性理论值 ≈16，平方 ≈256）。存档
`g69cr3-split-point-enumeration-*.txt`；这份枚举已交给 Codex r2 **核它完不完整**
（而不是让它重新找一遍）。

### 5.19 修掉平方后，整套测试快了 5 倍 —— 「跑得慢」本身就是缺陷的症状

### 5.20 负控的还原基准：`git show HEAD:…` 在「卡内多轮整改」时会冲掉当轮修复

跑 Codex r1 MEDIUM 的负控时（验证加强后的 H4 门能抓住误拒），我沿用了协议 §2.2 的写法：

    trap 'git show HEAD:scripts/local_tz.py > scripts/local_tz.py' EXIT

它把 `local_tz.py` 还原到了 **HEAD**（`69dbcc62`）—— 而那时本轮的 HIGH 修复**还没 commit**。
于是修复被一起冲掉，两副本当场不同源（`display_tz.py` 还有修复、`local_tz.py` 没了）。

**这条写法的隐含前提是「工作树 == HEAD」**。卡内多轮整改的场景恰恰不满足：
改完、还没提交、就要跑负控验证新门 —— 这时 HEAD 不等于"变异前"。

**处置**：还原基准改为**变异前的工作树快照**（`cp` 出临时文件，trap 里 `cp` 回来）。
这比 `git show` 更弱（不依赖 git 状态），但恰恰因为弱所以在任何工作树状态下都对。
恢复靠的是同源副本 `display_tz.py`（它没被 trap 碰过），行为判据复核通过。

**连带的两个假信号**（都是判据形态问题，不是真缺陷）：
1. 跑前 `shasum` 打的是**变异态**（子 shell 里施变异脚本先于那次采样执行），
   于是"跑前 ≠ 跑后"看起来像没还原。这正好印证 Codex r1 的一句话：
   *前后 SHA 相同只能证明两个采样时点内容相同，不能证明中途未修改* —— 反过来也一样，
   **采样时点搞错时 SHA 不同也不代表出了问题**。
2. `grep -c '(?!<)[^0-9'` 没加 `-F`，`(?!<)` 被当正则解释 ⇒ 0 命中 ⇒ 看起来像"修复丢了"。

**真相靠行为判据定**：`parse("A1<B>>2") is None` + 数字段计时 —— 它不依赖文本转义规则，
也不依赖采样时点。**结构判据出分歧时，先用行为判据定真相。**

### 5.22 分割点枚举 v1：结论对，论证不成立

### 5.25 ⛔ 第六跤：r1 的修复作废了我先前写下的等价断言，而我没有重测

验收单 §四 #5 原写：「**314,702 条**样本，`parse_posix_tz` 语义分歧 **0**」。
那个数字在测的时候（`dadfc2c2`）是真的。但 **r1 的 HIGH-1 修复**
（dst 引用名不退裸名，加 `(?!<)`，commit `6242aff4`）**改变了接受域**，
而我把它当成「修一个缺陷」而不是「改一次语义」，没有重跑等价测量。

Codex r2 ⓪ 在更宽的面上测出 **9,492/279,072** 处分歧。本卡复核分三步：

| 版本 | 枚举面 | 分歧 | 结论 |
|---|---|---|---|
| v1 | 21,600 组（名+偏移+dst名+dst偏移+规则 五段拼接） | **0** | ⛔ 假绿 |
| v2 | 7,280 组（dst 段改为**整段畸形形态**，含闭合 `>` 之后还有字符） | **1,600** | Codex 是对的 |
| v3 | 同 v2，按「接受/拒收是否与 libc 对齐」分类 | — | 见下 |

**v1 为什么给出 0**：它按五段**拼接**生成串，dst 名一旦是 `<B>` 就必然紧跟偏移，
于是**生成不出** `A1<B>>2` / `A1<B>C>2` 这类「闭合 `>` 之后还有字符」的串 ——
而 r1 HIGH-1 修的正是那一族。这是「证据量大 ≠ 证据面宽」的又一例：
21,600 组是真的，0 分歧也是真的，但它证明不了「所有输入等价」。

**v3 的分类结果**（1,600 处分歧逐条判）：

| 类别 | 条数 |
|---|---:|
| 当前与 libc 一致、`a8cefab4` 不一致 | **1,600** |
| `a8cefab4` 与 libc 一致、当前不一致（= 回退） | **0** |
| 两者都对 / 都错 | 0 |

样例：`A1<B>>` —— libc 给 `(('UTC','UTC'), 0, 0, 0)`（= **不认这个规格串**，退化 UTC），
`a8cefab4` 却**接受**并编出一个偏移，当前版本返回 `None`（拒收，与 libc 同侧）。

**⇒ 正确的说法不是「零分歧」，而是「全部分歧朝 libc 靠拢、零回退」。**

这一跤的形状与 §五.21 的两跤同源，但更隐蔽：那两跤是**新写的判据**本身错了；
这一跤是**旧判据的结论**被后来的修复作废，而判据本身没错、也不会红——
它早就跑完了，躺在存档里，看起来是绿的。
教训：**每次改变接受域的修复，都要回头问「哪些已落档的结论依赖旧接受域」。**
