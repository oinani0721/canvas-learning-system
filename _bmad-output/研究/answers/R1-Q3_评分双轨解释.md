# R1-Q3 · 评分双轨解释

## 批注位置

`_bmad-output/研究/2026-07-12-全景状态报告-PRD对照-Graphiti实证-对抗审查.md:198`（§9-Q3）

## 批注原文

> **User：** 请你解释一下

## 一句话核心结论

系统里现在**并存两套互不知道对方存在的评分体系**：一套是 PRD 时代设计的后端大管道（现已一半死、一半结果被扔进垃圾桶），一套是检验白板 v1.1 的本地轻量版（真正在设计上服务你，但从未被真实使用过）——Q3 要你拍板的是：**正式承认轻量版是 v1 的唯一评分主轨**，还是花成本把大管道修活并让两套合流。

## 深度解释

### 轨道一：后端 AutoSCORE 大管道（PRD 时代的设计）

- **设计**: 你用插件的 Quick Exam（命令面板「Quick Exam 单题考察」）→ 后端出题 → 你在 md 里答题按 Cmd+S → 插件自动把答案发给后端 `/exam/grade` → 后端调 LLM 按 4 维评分 → 返回分数和熟练度变化（mastery_delta），下游本应接 BKT/FSRS 科学复习算法
- **现状（本次审查真机实证）**:
  1. **评分 LLM 调用是死的**——配置拼出了 litellm 不认识的模型名（`google/...` 应为 `gemini/...`），每次评分都 502 报错。你答了题永远等不到分数（B1，修复成本一行）
  2. **就算修好，分数也进垃圾桶**——插件收到 mastery_delta 后没有任何代码使用它（全插件 grep 零命中），不写回任何笔记
  3. 出题端同样因这个配置错误，永远退化成无 LLM 的模板题（「请用自己的话解释：…」）
  4. 更上游的完整考试会话管道（exam_service + 4 维 AutoSCORE 链）在 S3 清理插件死命令后就没有调用方了，整体休眠
- **一句话**: 这条轨道现在是「出题装样子、评分必报错、报错修好了分数也没人要」。

### 轨道二：quiz-answer 本地 EMA（检验白板 v1.1 的诚实版）

- **设计**: 你走 `/start-exam-board` 出题 → 手写答题 → `/quiz-answer` → Claude（你的订阅，不走后端）按 4 维评分 → **静默**写进检验白板 frontmatter（不当场显示分数，保护测试效应）→ 用 EMA 公式（新分数和旧掌握度加权平均）更新节点的 `mastery_score` → Dashboard 显示掌握度变化
- **现状**: 链路代码完整、数学正确（沙盒验证过），但**你还从来没有真实跑完过一次**（唯一一张检验白板还停在"进行中"没答题）。本次审查沙盒首跑发现两个小数据缺陷（极端情况下掌握度可能写出 3.5 超界值、校准记录可能存错位置），都是几行的修复（已列入 P0 队列第 6 项）
- **一句话**: 这条轨道是活的、是为你当前工作流设计的，就等你真实用起来 + 打两个小补丁。

### 为什么必须"确认主轨"而不是放着不管

两套并存的代价：① 假管道占维护成本（每次改动都要考虑它，审查也要审它）；② 用户困惑（插件里的 Quick Exam 看起来能用，实际评分永远失败——这就是"名实不符"）；③ 数据分裂风险（万一哪天两套都活了，同一个节点的掌握度被两套公式各改各的）。

### 两个选项的真实含义

| 选项 | 动作 | 代价/收益 |
|---|---|---|
| **A · 本地 EMA 为 v1 主轨（我推荐）** | 轨道二转正；轨道一封存（插件 Quick Exam 命令标注降级或隐藏，后端管道保留代码不删但明确 DEAD 状态）；顺手修 B1 一行让 Quick Exam 出题至少不是模板题 | 零维护负担，聚焦你实际在用的工作流；BKT/FSRS 科学复习是 v2 再激活的事（那时再设计合流） |
| B · 修活合流 | 修 B1 + 插件接收 mastery_delta 写回 frontmatter + 两套公式对齐 | 工作量数天，且当前没有真实使用数据来校准两套公式——在"基本功能先实现好"的优先级下不划算 |

**推荐 A 的核心理由**: 你的真实工作流（检验白板 + 手写 + 静默评分）只需要轨道二。轨道一是为已弃用的 Tauri 交互设计的遗产，现在修活它服务不了任何现行场景。
