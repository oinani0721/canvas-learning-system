# 批注回复 — CARD-A1 验收单：跨 vault 复习进度 Web UI 方向

> **批注来源**: `验收单/Story-CARD-A1-fsrs新卡修复.md` 批注区（2026-08-25）
> **批注原文**: "我们的主 goal 也提过，最后打算把 dashboard 转为 web UI，而且这个是横跨了多个 vault，每个 vault 需要复习进度，都可以查看排期"

---

## 一句话回应

方向收到并已在主计划里（G6 每日复习 Web UI + G2 多 vault 隔离），你这条批注还提供了一个**重要的决策信号**——"横跨多个 vault"意味着 Web UI 的形态选择要重新权衡（详见下方 §3）。这条不影响 CARD-A1 本身的验收，A1 修的排期引擎正是这个终局的地基之一。

## 1. 你要的东西在主计划里的位置

| 你批注里的诉求 | 主计划对应 | 当前状态 |
|---|---|---|
| Dashboard 转 Web UI | 计划书 G6（每日复习 Web UI）+ D3 设计门 | 排在复习闭环（本批 A1-A3）之后 |
| 横跨多个 vault | 计划书 G2（统一 VaultScope、多 vault 隔离） | 未启动；已知硬缺口见 §4 |
| 每个 vault 的复习进度/排期可查看 | G3 Review Projection（本批 A2 刚落地了单 vault 版） | ✅ 单 vault 版本已上线（今天你 Dashboard 上那个带时间戳的数字） |

## 2. 好消息：这两天的活恰好是它的地基

- **A2 刚做的 Review Projection v3** 就是未来 Web UI 的数据源：每个 vault 一份标准化的"今日复习"投影（到期明细 + 待剖析积压 + 生成时间）。将来跨 vault 视图 = 把 N 个 vault 的投影聚合展示，数据格式已经定型，不用推倒重来。
- **A1 修的排期引擎**保证每个 vault 里的"复习进度"是真实的智能排期，而不是之前那种静默退化的假数据——没有 A1，跨 vault 看到的进度就是错的。

## 3. 你的批注改变了一个待决策项（重要）

主计划 D3 设计门原来推荐"Obsidian 插件内嵌视图"（方案 A），理由是与当前产品同进程同 vault。但**"横跨多个 vault 查看"这个诉求天然更适合方案 B（独立的本地网页应用）**——因为 Obsidian 一次只开一个 vault，插件内视图很难聚合其他 vault 的数据；而独立网页可以同时读所有 vault 的投影文件。

**处置**：不现在翻案（G6 还没到），但把你这条批注登记为 D3 的正式决策输入。等 G6 启动时，会拿"方案 B + 聚合各 vault 投影 JSON"作为首选方案向你确认。

## 4. 到达终局前的已知硬缺口（按主计划顺序，供你了解全貌）

1. **复习状态按 vault 隔离**（G3 遗留）：目前后端的排期状态键没有 vault 维度，两个 vault 同名概念会互相干扰——这是"每个 vault 各自的复习进度"的前提，优先级最高；
2. **VaultScope 统一**（G2）：请求路径上 vault 身份的统一解析与防串写；
3. **投影聚合 + Web UI 本体**（G6）：多 vault 投影读取、展示、点击跳回对应 vault。

以上均**不进当前批次**（防功能蔓延，先收口复习闭环 A3），作为第二批之后的规划输入。

## 5. 对 CARD-A1 验收的影响

无。这条批注是方向性输入而非缺陷报告——A1 验收单的"第 1 步：日常使用无感知异常"照常勾选即可；满意就说"CARD-A1 通过"。
