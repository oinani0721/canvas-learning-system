## 二、目标与 SLO（照抄已批准裁决）

- 保存笔记后 **60s 内可检索**（事件路径正常 ~10s）
- 删除/改名后 **60s 内不可检索**（无幽灵 chunk）
- freshness lag > 5min → status 申报 `stale: true`
- 全程无「假成功」：每条 API 返回结构化真实状态

## 三、架构设计

### 双机制触发（事件加速 + anti-entropy 兜底）
- **主力（正确性保证）**：60s 周期 anti-entropy 扫描 —— 指纹 diff（复用 `_get_changed_files`）→ 差异入 pending 队列。206 文件 SHA256 全扫 <2s，5000 文件量级依然可行。**SLO 由扫描确定性保证，事件丢失从正确性问题降级为延迟问题。**
- **加速（体验优化）**：`watchfiles` 库监控 vault 目录（compose 已 bind-mount /vaults），文件事件即时入 pending。Docker virtiofs 事件不可靠时自动被扫描兜底。
- **启动 reconciliation**：lifespan 非阻塞跑一轮全量指纹 diff，补齐停机期间变更。

### durable per-path pending（38.1 骨架升级）
- JSONL v2 schema：`{op: upsert|delete, rel_path, vault_id, state: pending|in_flight|dirty, attempts, enqueued_at}`
- 同 path 覆盖、**异 path 绝不互相 cancel**（废 `vault:{root}` 单槽 key）、索引中新事件标 dirty 完成后重放
- 入队即持久（意图日志），非失败后才写；启动 recovery 重放

### 统一索引原语（新服务 `vault_index_orchestrator.py`）
`should_index(path)`（黑名单单源）/ `upsert_file(path)`（修复版 index_single_file）/ `remove_file(path)` / `reconcile()`（指纹 diff→pending）/ `full_rebuild()`。全量与单文件共用同一套黑名单、chunk 参数（settings 500/50 单源）、embedding 路径（Ollama batch 优先）、subject 赋值（build_vault_group_id）。FTS 重建改批量：每批 pending 处理完成后重建一次，不再每文件一次。

### 与 ChatGPT 原文的两处实现偏离（透明声明，请用户知悉）

**偏离 1 — generation publish 改为「全量 = 增量的极限情形」**：原文要求 generation 影子表+指针切换防全量重建空窗。侦察发现该方案成本远超预期：读路径有 drop 表副作用（E2）、B0.7 裸表 fallback 会在切换窗口漂移到跨 vault 数据、进程内 ≥4 份独立 client 需进程外指针、8 个裸表漏网点、表名被测试钉死。**替代实现**：full_rebuild 不再 drop 表，改为逐文件 delete-before-insert 重灌 + 收尾清理 orphan——表全程存在、读侧永远有数据，同样达成「无空窗发布」的意图，机构小一个数量级。schema 变更场景（罕见）保留 drop 路径并强制申报 stale。
**偏离 2 — 事件加速用 backend watchfiles 而非 Obsidian 插件钩子**：插件的索引调用链已死（零调用实锤），重建插件钩子涉及 TS 构建部署链且受 DD-12 范围约束；backend watcher 纯 Python、与扫描兜底天然配套。插件钩子留作阶段 2 可选加速。

## 六、契约测试四组 27 条（§九 反推重建）

**组 A 写侧正确性**：A1 同 path 快速两次保存→合并一次索引；A2 异 path 并发→全部被索引（不互 cancel）；A3 索引中新事件→dirty 重放不丢；A4 pending 跨进程重启恢复；A5 单文件=全量 chunk 参数同源；A6 单文件路径文件名黑名单生效；A7 单文件 subject=全量一致；A8 delete op→chunks 清零+指纹移除；A9 rename→旧路径零幽灵+新路径可检索；A10 黑名单无第二份默认拷贝；A11 chunks/ 与 .quarantine/ 被排除；A12 指纹表带 vault 前缀且 `_cache_tables` 不 drop 它
**组 B API 诚实**：B1 disabled→报 disabled 非 scheduled；B2 excluded 路径→excluded；B3 accepted=真实入队数；B4 status 对前缀表报 indexed:true；B5 status 含 freshness 四字段；B6 lag>5min→stale:true
**组 C SLO（integration，真 LanceDB tmp）**：C1 新文件→一轮 reconcile 后可检索；C2 修改→内容更新可检索；C3 删除→不可检索；C4 启动 reconciliation 补齐停机变更
**组 D 防回潮**：D1 新写路径必产出 FTS；D2 refresh-changed 真触发 LanceDB 写；D3 coalesce key 含 path；D4 主表存在时 B0.7 不漂移裸表；D5 增量与全量端点共用 orchestrator

## 七、风险与回滚

- watchfiles 在 Docker virtiofs 下事件可能不完整 → 设计上已由扫描兜底，watcher 故障只降体验不降正确性
